## 1. 站台代理與平台各存一份同樣的驗證規則（高 × 高）

**根因**：`abf_station`（在站台上跑的代理）需要和 `abf_platform` 用同一套路徑與費率規則，但規則是複製貼上而不是被 import；其中已經有一處複製後行為分叉。

**項目**
- `platform/abf_station/rules.py:12-13,23-37` 的 `MAX_PATH`、`_PATH_CHARS`、`path_problem` 與 `platform/abf_platform/compute_envs.py:66,76,79-93` 逐字相同（只差 docstring）。理由：同一檔 `abf_station/rules.py:10` 已寫著 `from abf_platform import compute_envs  # the same rules ... as the platform applies`，等於承認該共用，卻只共用了一部分。改一邊的字元白名單、長度上限，另一邊就靜默放寬或收緊，而這是擋路徑穿越的那一層。
- `platform/abf_platform/cloud_cost.py:30-37` 與 `platform/abf_platform/su.py:34-41` 的 `load_rates` 本體完全相同（只差 docstring）。
- **已分叉**：`cloud_cost.py:40` 的 `_number` 多一個 `math.isfinite(v)`，`su.py:44` 的 `_number` 沒有。`su.py` 因此會把 `NaN`／`Infinity`（Python `json.load` 預設接受）的因子或費率視為合法數字（`su.py:78-126` 的各處判斷都經過這個 `_number`）；是否真的流進金額，本輪未實測。
- 命名陷阱：`platform/abf_platform/compose.py:82` 的 `normalize(graph, data)`（模組圖正規化）與 `platform/abf_station/rules.py:51` 的 `normalize(value)`（路徑正規化）同名不同義；照抄時很容易把錯的那個 import 進來。

**建議修法（依優先序）**
1. 改架構：`abf_station/rules.py` 直接 `from abf_platform.compute_envs import MAX_PATH, path_problem`（它已經依賴 `compute_envs`）；`su.py` 改 `from .cloud_cost import load_rates, _number`（或把兩者移到 `common.py` 公開成 `number`、`load_json_object`）。
2. lint／CI：加一個測試，掃全部 production `.py`，同名且 AST 正規化後相同的 `def` 出現在兩個以上檔案就失敗（可帶白名單，如 `main`、`render`）。
3. 測試：對 `rules.path_problem` 與 `compute_envs.path_problem` 做同輸入同輸出的對照測試，並為 `su` 加 `NaN` 費率案例。
4. 文件：最後才是在兩處互相註明「改這裡也改那裡」。

## 2. 安全網 hooks 內刻意複製的 helper，沒有任何檢查它們保持一致（中 × 高）

**根因**：`CLAUDE.md` 明定 hooks 不 source 共用檔（「缺 helper 就失效的閘門比沒有閘門更糟」），所以每個 hook 內嵌一份相同 helper；這個取捨是對的，但「相同」這件事沒有任何機器檢查（`tests/` 內沒有任何檔案提到 `abf_emit` 或 `abf_cap`，已 grep）。

**項目**
- `abf_emit`：`hooks/confirm_cleanup.sh:245`、`hooks/confirm_launch.sh:244`、`hooks/confirm_walkthrough.sh:203`、`hooks/guard_plugin_files.sh:247` 四份。三份相同；`confirm_cleanup.sh` 的內文註解標籤是 `jq-broken-cleanup`，其餘是 `gate-emit-empty-object`，已經出現第二種寫法。
- `abf_cap`：`confirm_cleanup.sh:235`、`confirm_launch.sh:234`、`confirm_walkthrough.sh:193`、`guard_plugin_files.sh:237` 四份，目前相同。
- `abf_jq_works`：`confirm_launch.sh:164`、`confirm_walkthrough.sh:121`、`plugin_intro.sh:210` 三份；逐字雜湊有三種結果，經人工比對，邏輯行相同、差異只在註解（`plugin_intro.sh` 沒有「a trailing CR is jq.exe on Windows」那句說明），但這正說明「相同」目前只靠人眼。另有 `deny` 在 `confirm_cleanup.sh:287`、`confirm_walkthrough.sh:223`、`guard_plugin_files.sh:266`，`ask` 在 `confirm_cleanup.sh:300`、`confirm_launch.sh:289`。

**建議修法**
1. 改架構：保留「執行期不 source」，但把 helper 寫在單一來源檔，由建置步驟（或 `tests/` 內的產生器）貼進每個 hook，並以檢查確認每份與來源逐字一致。
2. CI：新增一個測試，抽出各 hook 內的 `abf_emit`／`abf_cap`／`abf_jq_works` 函式本體，雜湊後要求同名者一致（允許明文列出的例外，例如 `plugin_intro.sh` 的 `abf_jq_works`，並寫明理由）。
3. 文件：在每份旁註明來源，優先度最低。

## 3. `CLAUDE.md` 與程式註解裡會過期的寫死事實（高 × 低）

**根因**：把「會變的數字、版本、目錄名」寫成散文，沒有東西在它變時叫它一起變。`tests/run_all.sh:7-10` 自己就寫著「found and counted at run time, so no number is written here to go stale」，但 `CLAUDE.md` 反而寫了數字。

**項目**
- `CLAUDE.md:137`：`# all 73, ~100s`。實際 `tests/*.sh` 有 137 個檔（含 `run_all.sh`，即 136 個被執行），另有 `platform/tests/test_*.py` 165 個；且 CI 已切成 4 個 shard（`.github/workflows/tests.yml`），平台套件單檔就有 100–200 秒，「~100s」不成立。
- `CLAUDE.md:10-11`：寫「constitution 6.0.0」，憲法現行版本為 6.1.0（`.specify/memory/constitution.md:681`）。這類版本引用在 repo 內散見 `Constitution 2.0.0`（26 處，多數是「何時引入 in-use 範圍」的歷史指涉，仍正確）到 `6.0.0`（11 處），分不出哪些是「當前版本」、哪些是「歷史指涉」。
- `CLAUDE.md:131`：「on every PR and every push to `main`」。`.github/workflows/tests.yml:53` 實際是 `branches: [main, v3]`，另有 `merge_group`；開發分支 v3 的事實沒寫進去。
- `hooks/confirm_walkthrough.sh:7`：「commands/launch.md has said for two versions…」；`hooks/plugin_intro.sh:277`：「every commands/*.md file's ‘Before anything else’ section」。`commands/` 目錄已不存在（`docs/TESTING.md:487` 也寫「`commands/` does not exist」），現在是 `skills/*/SKILL.md`。（`docs/TESTING.md:522-531` 記錄了刻意保留 `commands/` 的測試夾具例外，但這兩處是註解、不是夾具。）
- `docs/TESTING.md:368` 指 `platform/tests/__pycache__`、`:590` 指 `configs/cloud/rates.json`：兩者是「不應存在」的檢查語句，屬正確的負面敘述，**不算過時**，列在此處僅為說明已查過、排除。

**建議修法**
1. 改架構：刪掉這些數字，改成指令（「見 `bash tests/run_all.sh` 最後一行」）。
2. lint：加檢查，`CLAUDE.md` 內不得出現 `all \d+`／`\d+ tests`；`hooks/` 與 `scripts/` 的註解內若出現 `commands/` 路徑（排除 `tests/` 夾具），就要求該路徑存在。
3. 測試：已有 `tests/platform_direction_docs_test.sh` 之類的釘字檢查，可擴充為「CLAUDE.md 的憲法版本 ≥ 該檔 `**Version**` 行」，或改成不寫版本。
4. 文件：直接修正上述各行，最後做。

## 4. scripts 內重複或同名不同義的 shell helper（中 × 中）

**根因**：`scripts/utils/portable.sh` 本來是「機器差異只有一個地方知道」的單一來源，但新 helper 沒有規則要求先去那裡找或放進去，於是各腳本自己再寫一份。

**項目**
- `rsync_local_path`：`scripts/fetch.sh:131` 與 `scripts/push.sh:111` 逐字相同（Windows 磁碟機代號轉 `/c/...`、`cygpath`），正是 `portable.sh` 該收的那種機器差異。
- `to_gb`：`scripts/tune_resources.sh:75`（吃 `"4GB"` 這種字串，輸出小數 GB）與 `scripts/why_pending.sh:86`（吃「數字 單位」兩個參數，輸出向上取整的整數 GB，裸數字視為 MB）**同名但簽名與語意都不同**。照抄一邊貼到另一邊會靜默換算錯誤。
- `alive`／`pid_of`：`scripts/agent_ctl.sh:44-45` 與 `scripts/egress_ctl.sh:35` 各自寫了「讀 state JSON 取 pid 再 `kill -0`」，後者還把 `python3 -c "import json;print(json.load(open('$STATE'))[…])"` 內嵌六次（`egress_ctl.sh:35,42,73,115,124,126`）。
- `die`（8 份：`egress_allow.sh:49`、`fetch.sh:61`、`init_workspace.sh:109`、`input_checksums.sh:68`、`on_site.sh:100`、`push.sh:58`、`record_adapter.sh:46`、`reset_master.sh:41`）與 `usage`（8 份）：各自定義，輸出前綴與退出碼是否一致需逐一看；此項僅記錄，未逐份比對行為。
- `say`／`fix`：`scripts/launch_recheck.sh:20-21` 與 `scripts/preflight.sh:35,38` 各一份。

**建議修法**
1. 改架構：`rsync_local_path`、`to_gb`（先統一語意再命名，例如 `mem_to_gb`／`mem_to_gb_ceil`）移進 `scripts/utils/portable.sh` 或新建 `scripts/utils/units.sh`，原處改 source。
2. lint：擴充 `tests/portable_userland.sh`，同名 shell 函式出現在兩個以上 `scripts/*.sh` 且本體不同就失敗（本體相同的也失敗，要求搬到 utils）。
3. 測試：為 `to_gb` 兩種輸入各寫一個表格式案例。
4. 文件：最後。

## 5. 死碼：沒有呼叫端的函式（中 × 低）

**根因**：功能改版後，舊入口沒有一起刪；沒有任何工具會告訴你某函式已經沒人用。以下每項都已用全 repo token 計數＋逐一 grep 確認 production 程式碼零呼叫。

**項目**
- `platform/abf_platform/web_board.py:1201` `render_settings`：全 repo 只有定義；設定頁現在由 `web_settings.py` 負責，這個「sections that are all still to come」的占位頁已被取代。
- `platform/abf_platform/web_settings.py:121` `_when_epoch`：全 repo 只有定義（旁邊的 `_when_iso` 有被用）。
- `scripts/utils/file_discovery.py:133` `find_index_file`、`:172` `detect_input_type`：全 repo 只有定義；同檔的 `discover_files` 才被 `scripts/generate_samplesheet.py:46` 使用。
- `scripts/methods_text.py:166` `assets_dir`：沒有任何呼叫端；`tests/package_gaps_test.sh:146` 還去 monkeypatch 它（`m.assets_dir = lambda …`），測試因此在替一個不存在的呼叫路徑造假。
- `platform/abf_platform/su.py:190` `month_total`：production 零呼叫，只有 `platform/tests/test_estimate_su.py:214,217,240,242` 在用；對照 `cloud_cost.month_usage` 有被 `actions/__init__.py:222` 使用，推測是尚未接上的 SU 月報入口。
- 已排除的假陽性（掃描有報、人工確認有呼叫）：`mcp_server.py` 的 `launch_tool`／`cancel_tool` 等（以裝飾器註冊）、`oauth.py` 的 `get_client`／`load_*`（框架介面覆寫）、`pipeline_files.py:57` `redirect_request`（`urllib` 覆寫）。

**建議修法**
1. 改架構：決定 `month_total` 是「要接上」還是「刪掉」（它有測試，所以不能只靠覆蓋率發現它是死的）；其餘直接刪。
2. lint／CI：加 `vulture`（Python）或自寫的 AST 掃描，白名單列出裝飾器與框架覆寫；以「不計測試的呼叫端為零」為失敗條件。
3. 測試：刪 `assets_dir` 後同步移除 `tests/package_gaps_test.sh:146` 的 monkeypatch。
4. 文件：無需。

## 6. 沒有任何測試以名稱碰到的公開函式／檔案（低 × 中）

**根因**：測試以「每個不變量或腳本一個檔」組織，沒有把「公開函式至少被一個測試提及」當成檢查，所以新增的函式不會被提醒補測試。

**項目**
- `scripts/dev/check_settings_mobile.py`：`tests/` 與 `platform/tests/` 完全沒有提到此檔名，只有 `docs/TESTING.md` 提到。
- `scripts/utils/file_discovery.py`：檔名未被測試提及（但 `tests/generate_samplesheet_test.sh` 會間接走 `discover_files`）；其中 `find_index_file`、`detect_input_type` 同時是第 5 類的死碼，`count_files_by_type` 無測試名稱命中。
- `platform/abf_platform/common.py:105,138,150` 的 `run_failure_reason`、`offline_after_seconds`、`token_from_header`：測試未以名稱提及；它們在 `receiver.py:254`、`jobs.py:145`、`agents.py:31,126` 被呼叫，影響「離線判斷」與 token 解析（認證路徑），代價較高。
- **啟發式清單（需人工複核）**：排除 `cmd_*` 與 `main` 後，`platform/abf_*/`、`scripts/utils/` 下共 144 個公開函式沒有任何測試檔以名稱提及，集中在 `web_launch.py`（19）、`jobs.py`（16）、`web_board.py`（14）、`abf_launch/build.py`（11）、`store.py`（8）、`scripts/utils/schema_roles.py`（7）。其中許多會被端對端測試（HTTP 請求、CLI 子程序）間接走過，名稱沒出現不代表沒被執行，因此**這 144 項不計為確認缺口**，只當作覆蓋率工具的查核起點。

**建議修法**
1. CI：在平台測試加 `pytest --cov`（含 `--cov-fail-under` 的逐檔下限，先設為現況），把「間接走過」與「完全沒走過」分開，取代名稱比對。
2. 測試：優先補認證路徑的 `token_from_header`（空值、大小寫、非 `Bearer`）與 `offline_after_seconds`（環境變數壞值）。
3. 架構：`scripts/dev/` 若是一次性工具，在檔頭標明並排除；若是常用檢查，納入 `tests/run_all.sh`。
4. 文件：無需。
