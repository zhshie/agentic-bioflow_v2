## S1 — path-rule duplication between `abf_station/rules.py` and `abf_platform/compute_envs.py`

**Evidence.**
- `platform/abf_station/rules.py:12-13` (`MAX_PATH`, `_PATH_CHARS`) and `:23-37` (`path_problem`) match `platform/abf_platform/compute_envs.py:66,76,79-93` token for token. `rules._QUEUE` (`rules.py:14`) matches `compute_envs._QUEUE` (`compute_envs.py:65`).
- The sweep did not list a second pair with the same shape: `abf_station/readfile.py:24,29-44` (`MAX_PATH = 512`, `path_problem`) against `abf_platform/jobs.py:51,56,430-445` (`RUN_FILE_PATH_MAX = 512`, `run_file_path_problem`). Also `readfile.MAX_BYTES` (`readfile.py:23`) against `jobs.RUN_FILE_MAX_BYTES` (`jobs.py:50`). The two sides word their messages differently, but they must give the same verdict.
- **The duplication is intended.** `rules.py:1`: "it is a second lock on purpose, written separately from the platform's so one mistake cannot open both". `readfile.py:23` and `jobs.py:50` say "written separately" as well.
- No test pins the copies to each other. `test_launch_bundle.py:526-545` checks each side for one input (`"/data/w1\n"`), not that the two sides agree.

**Divergence today: none.** A seeded differential run of 200,020 inputs (edge cases plus random strings over the allowed and forbidden characters, NUL, CR, bidi, `~`, `\`) found 0 inputs where `rules.path_problem` ≠ `compute_envs.path_problem`. It also found 0 inputs where `readfile.path_problem` and `jobs.run_file_path_problem` disagree on accept/refuse. The constants are equal (1024/1024, 512/512, and the same `_PATH_CHARS` pattern).

**Root cause.** The design chose two independent locks but never added the check that would make "independent" safe: that both locks still give the same verdict. If one side is edited alone (its character list, length cap or `..` rule), that side loosens or tightens silently, and nothing fails.

**Fix (recommended).**
- Add a parity test. Do **not** refactor. This is the sweep's own fix #3 (`docs/reports/sweep-2026-11.md:35`), which also asks for a `su` NaN-rate case; that part belongs with the `su._number` task below.
- I refute the sweep's fix #1 ("`rules.py` should `from abf_platform.compute_envs import MAX_PATH, path_problem`"). It contradicts `rules.py:1`, because with one shared function, one mistake opens both locks. See *Refuted*.
- Sweep fixes #2 (an AST duplicate-def lint) and #4 (comments) are optional.
- A lint would need `path_problem` on its whitelist, because it is a duplicate on purpose, so a lint adds little here.

**RED test (pure addition, so mutation proof per RULES §5.3).**
- New file `platform/tests/test_station_rule_parity.py`, with the header `# Nothing existing: …` per repository convention.
- The prototype was run in a scratch copy.

**Root cause.**
- `platform/abf_station/launch.py:337-344` `path_cells` judges a cell as a path only when its column is named in `path_columns` or matches `DEFAULT_PATH_COLUMN` (`:62`), or when the cell starts with `/`.
- Every checker trusts that list: Slurm `:371` and the cloud checkers `:835` (gcb), `:1013` (aws), `:1195` (azure), `:1389` (k8s).
- So does the platform's upload-area confinement: `platform/abf_launch/build.py:241` imports the same `path_cells`.
- The safety therefore rests on "every column that holds a file is recognised by name", which is false for nf-core/mag (`short_reads_1`, `long_reads`), taxprofiler (`fasta`), and any `bai`, `crai` or `vcf` column.
- The params side already solved this by value: `build.py:211-228` `_param_path` (the "116b ruling") judges any value that starts with `/` or `~`, has a `.`/`..` part, or is `file:`. Samplesheet cells never received the same rule.
- The `slurm-url-cells` plan (`specs/slurm-url-cells/plan.md`, Scope) says "`file:`, `s3://`, `gs://`, `az://` and any other scheme stay refused". Today that holds only in recognised columns.

**Fix (recommended: Option A, stricter only, no existing contract changed).**
- Add a value rule to `path_cells`. A cell is a path cell when its column is a path column **or** its value can only be a location:
  - it starts with `/` (today's rule);
  - it starts with `~`;
  - it has a part (split on `/`) equal to `.` or `..`;
  - it starts with `file:` or `<scheme>://`.
- Bare words and free text with `/` but no dot-part, such as `WT/KO`, `free/relative text` or `chr1:100-200`, stay text. That keeps the confirmed TC-007/008/009/018 of `samplesheet-suffix-path-column` green (`platform/tests/test_launch_bundle.py:407-415`).

## F2 — a scoped `resourceLimits` is hoisted to a global limit

**Reproduction.** `python3 -I docs/reports/audit-2026-11/02_resource_limits_scope_hoist.py` at the sha above. The output matches the audit: `inside withName` → `process.resourceLimits = [cpus: 2, memory: 4.GB]`; `inside a profile` → the same.

**Wider than the audit reported (measured on origin/v3, CE `maxvCpus=64`, `maxMemoryGB=256`).**

| Shape of the user's line | origin/v3 | Correct |
|---|---|---|
| `process.resourceLimits = [cpus: 2]` (top level) | `[cpus: 2, memory: 256.GB]` | merge ✓ |
| `process {` / `resourceLimits = [cpus: 2, memory: 4.GB]` / `}` | `[cpus: 2, memory: 4.GB]` | merge ✓ (this is global) |
| `process { withName: 'BIGJOB' { resourceLimits = […] } }` (multi-line) | **global `[cpus: 2, memory: 4.GB]`** | refuse |
| `process { withLabel: process_low { resourceLimits = [cpus: 2] } }` (multi-line) — new | **global `[cpus: 2, …]`** | refuse |
| `profiles { small { process.resourceLimits = […] } }` (multi-line) | **global** | refuse |
| `/*` ↵ `process.resourceLimits = [cpus: 2]` ↵ `*/` (block-commented out) — new | **global `[cpus: 2, …]`** (an inert line becomes a limit) | refuse (or ignore) |
| `process.withName:BIGJOB.resourceLimits = […]` | refused | refuse ✓ |
| `process { resourceLimits = [cpus: 2] }` (one line) | refused | refuse ✓ (unchanged) |

**Root cause.**
- `platform/abf_station/launch.py:713-740` `_user_limits` collects the lines that are not `//`-comments and contain `resourceLimits`, then matches the single hit with `_LIMITS_LINE` (`:700`). That pattern allows any leading whitespace and an optional `process.` prefix.
- Nothing tracks which `{ }` block the line sits in. A line inside `withName`/`withLabel`/`profiles`, or inside `/* */`, therefore reads as a limit for every process.
- `_resource_limits_line` (`:748-768`) merges it into the one global line that the three cloud renderers append (`:787`, `:972`, `:1154`).
- The plan's decision 3.4 (`specs/cloud-ce-memory-cap/plan.md:49`) defines "readable" as "the whole line is `process.resourceLimits = [...]` or `resourceLimits = [...]`" and never considers scope. It does say "deliberately narrow, rather refuse than guess", which the fix below follows.
- *(Nextflow semantics, not run here)*: a `withName`/`withLabel` selector outranks generic `process` settings, and a profile applies only when selected.
  - Hoisting therefore clamps every process to the selector's limits (slow runs, OOM).
  - Simply leaving the scoped line in place would let that one process **exceed** the CE ceiling, because the selector outranks the platform's global line. That is a paid-cloud ceiling bypass.
  - Hence **refuse**, not "keep both".

**Fix (recommended).**
- Track block scope and merge only a line whose scope is the top level, or exactly `process { }` with the unprefixed form. Anything else raises the existing `_limits_unreadable`.
- That error's text already says what to do: "請改成單行 process.resourceLimits = […]，或刪掉它、改設環境的 maxvCpus／maxMemoryGB" ("write it as one line, process.resourceLimits = […], or delete it and set the environment's maxvCpus/maxMemoryGB instead").
- Any brace structure the tracker cannot follow (`/*`, `*/`, an unbalanced line, a stray `}`) makes the scope unknown, and an unknown scope is refused.
- Prototype diff (scratch only). The anchors are `\Z`: with `$`, `tests/regex_end_anchor_test.sh` fails ("no new bare-$ validator regex"); I measured this on the first draft.
