## Scope

Other files (`su.py`, `cloud_cost.py`, `compute_envs.py`, `releases.py`, `jobs.py`, `store.py`, `web.py`, specs and docs) were read only where a candidate's claim depended on them. ## Method

1. **Three lenses.** Three independent reviewers read the unit and produced 16 candidate findings between them. Their candidates covered three areas: whether the numbers agree with their contract (the SU/cost path), trust boundaries (caller scoping, caches, redaction, name rules), and drift (dead code, stale text, clocks).
2. **Refutation.** I tried to break each candidate. I re-read the cited code at the sha, checked the spec or ruling that might make the behaviour intended, and re-ran every measured claim. The default was "refuted" unless the evidence held. Re-runs used the platform venv (`/root/.cache/abf-platform-venv/bin/python`, `PYTHONDONTWRITEBYTECODE=1`, pytest `-p no:cacheprovider`). They imported the existing test fixtures (`platform/tests/test_web_cost.py` `World`/`seed`/`usage`, `platform/tests/test_settings_pick_installed.py` `World`) from Python stdin scripts, so nothing was written into the worktree. The reviewers' own scratch tests at `/tmp/cb/scratch_ar01/test_ar01_usage.py` and `test_ar01_aws.py` were re-run and reproduce their numbers.
3. **Merging.** Duplicates were merged: 16 candidates became 11 surviving findings plus 3 refuted, and parts of several candidates were corrected or refuted. Candidate 9 broke into three separate defects: (a) a usage gap, (b) a running run, and (c) the site used for pricing. Part (c) was then measured on the shipped nano4 configuration, which changed how serious it is.

Candidate-to-finding map: F1 ← #1, #9a; F2 ← #9c; F3 ← #2, #9b; F4 ← #3; F5 ← #6; F6 ← #4; F7 ← #7; F8 ← #5, #16; F9 ← #15; F10 ← #10, #14; F11 ← #13. Refuted: #8, #11, #12, plus parts of #1, #10, #15 and #16 (see "Refuted").

## Surviving findings (most severe first)

### F1 (P1): my_usage gives a definite SU month total when one of its runs is "unknown" because of a usage gap

- **Evidence.** The per-run rows use `_su_of_run` (actions:210). It returns unknown, with the reason "N succeeded tasks have no usage record", when the run has fewer COMPLETED `task_usage` rows than `view["tasks"]["succeeded"]` (actions:132-136). Its docstring says "never a partial sum" (actions:126). The month total does not use that check. Its loop (actions:187-199) calls `su.run_su` directly (actions:192), and `su.run_su` adds whatever rows exist (abf_platform/su.py:174-178). The contract for the card is "any one analysis cannot be worked out → None with the reason, no partial sum" (specs/cost-page/plan.md:48; docs/PLATFORM.md:766 says the same: "never a partial sum"). So the page shows a run as "—" with a reason and, on the same page, a month card made from that run's partial rows with `unknown_reasons: []`.
- **Side note (doc drift).** docs/PLATFORM.md:766 says the card is `su.month_total`. `my_usage` does not call it, and `su.month_total` (su.py:190-202) has no production caller (it is also flagged in docs/reports/sweep-2026-11.md:102). `su.month_total` has the same blind spot.
- **Reproduction (measured).** Seed one finished run with one usage row of 2.0 h, then raise its succeeded count to 3:
  `seed(w,'gap-a',ann,hours=2.0)`; `UPDATE runs SET n_succeeded=3 WHERE run_name='gap-a'`; `actions.my_usage(...)`.
  The row shows `su=None, ['有 2 個成功的 task 沒有用量紀錄 (2 succeeded tasks have no usage record)']`, while the total is `2.0` with reasons `[]`. This is `/tmp/cb/scratch_ar01/test_ar01_usage.py::test_gap_row_unknown_but_total_known`. (The candidate said "1 task" in the reason; with that seed the count is 2.)
- **Proposed fix.** In the total loop, apply the same per-run judgement the rows use. When a finished HPC run has `done < view["tasks"]["succeeded"]`, set `total = None` and add the gap reason. The cleanest way is to factor the "is this run's SU knowable" part of `_su_of_run` (actions:129-136) into a helper that both loops call. Keep the total's site rule as it is unless F2 is ruled otherwise, because TC-073 (specs/cost-page/test-case.md:111) pins `site = default_site`. Correct docs/PLATFORM.md:766 so it no longer names `su.month_total` (or make the action call it).
- **Proposed RED test.** `test_my_usage_total_is_unknown_when_a_run_has_a_usage_gap`. A new file under `platform/tests/` would be outside the HOT list; `test_web_cost.py` is HOT.
- **HOT?** Yes (`actions/`; `docs/PLATFORM.md`).
- **Suggested tier.** C: a bug fix inside the existing contract (plan.md:48 already says "no partial sum").

### F2 (P2): the SU month total prices every run at `default_site` while the rows use each environment's `suSite`, so on the shipped nano4 config the card is "—" with a false reason

- **Evidence.** The total uses `site = rates["default_site"]` for every run (actions:182, :192). Each row uses `_su_of_run`, which prices at `su.site_of_run`, the `suSite` of the run's compute environment (actions:128; su.py:154-171). The shipped files disagree on purpose: `configs/sites/nchc-nano4-ce.json:15` sets `"suSite": "nano4"`, while `configs/sites/su_rates.json` has `default_site: taiwania3`. The two sites' partitions do not overlap: nano4 has `ngs*` and `big-mem*`, and taiwania3 has `ct*`. As a result, every finished nano4 run is priced on its row but makes the month total unknown with "no SU factor for partition ngs…". Where partitions do overlap with different factors, the total would instead be a wrong number. TC-073 (specs/cost-page/test-case.md:111) pins `su.total == su.month_total(…, default_site, …)` and `su.site == default_site`, so the code follows its contract and the contract itself conflicts with the per-environment `suSite` rule.
- **Reproduction (measured).** CE `nano1` (slurm) has config `{"suSite":"nano4"}`. Seed `t3-a` (5.0 h, queue `ct56`) and `nano-b` (2.0 h on `nano1`, queue set to `ngs53G`) with the real rates file, then call `my_usage`. Rows: `nano-b 2.0 []` and `t3-a 5.0 []`. TOTAL: `None ['task T: 分區 ngs53G 沒有 SU 係數 (no SU factor for partition ngs53G)']`, site `taiwania3`. Every row has a number, yet the card shows a dash with a reason that is not true of any row.
- **Proposed fix.** The maintainer chooses one site rule for card and rows. Option (a): the total adds each run's own `_su_of_run` value (each priced at its own suSite), and `su.site` becomes the site list or None when mixed. Option (b): the card counts only runs whose suSite equals `default_site` and states that the others are left out. Either way, update TC-073 and PLATFORM.md:766 to match.
- **Proposed RED test.** `test_my_usage_total_agrees_with_rows_for_a_run_on_an_environment_with_its_own_su_site`.
- **HOT?** Yes (`actions/`, `docs/PLATFORM.md`; TC-073 lives in a `test-case.md`, which is FORBIDDEN for cloud agents).
- **Suggested tier.** B: it changes a pinned test case and a user-visible number.

### F4 (P2): my_usage labels AWS Batch, Azure Batch and Kubernetes runs as national HPC, and their missing SU factor blanks the whole month's SU card

- **Evidence.** `where` is `"cloud"` only when `_launch_facts(...)["cloud"]` is true, and that is true only for `googlebatch-platform` (abf_platform/cloud_cost.py:171, `CLOUD` at :19). That happens even when the user's real HPC runs are computable. Cloud pricing for AWS, Azure and K8s is out of scope by ruling (specs/cloud-cost/plan.md:30, :166), but calling such a run national HPC is a wrong fact, not a missing feature.

### F5 (P2): latest_release serves one user's agent answer to every other user for 24 hours (the tag cache is shared and ignores the caller)

- **Evidence.** The other lookups in this unit are scoped to the caller: `jobs.latest_pipeline_files` only sees jobs on the caller's own environments (abf_platform/jobs.py:596-599), and `pipeline_files`/`nfcore_catalogue` reuse only the caller's own job row. `latest_release` first reads one platform-wide file, `<dir of platform.db>/release-tags.json` (actions:829). On a fresh hit it returns `ready` before any caller-scoped job is looked at (actions:831-833). When some user's agent answers a `tags` job, that agent's text is parsed and written into the same file (actions:848-849 → abf_platform/releases.py:149-151). Every other user then gets it as `source: "cache"` for 24 h, and afterwards as `stale-cache` (actions:834, :860). The agent runs on its user's own machine, so this is input from one user that reaches another. A modified agent can make every other user's guided-launch default an old real release (a silent downgrade) or a tag that does not exist (that pipeline fails to launch for a day). The spec chose one file beside platform.db (specs/release-lookup-job/plan.md:103, :281 ruling 2) and does not discuss the per-caller boundary. The guided launch page calls this action (docs/PLATFORM.md:760), so it is live.
- **Reproduction (measured).** Run `releases.lookup("nf-core/rnaseq", lambda r: ["1.0","1.1"], cache_path=<dir>/release-tags.json)`, which is exactly what actions:849 does with user A's job answer. Then `actions.latest_release(pp, "nf-core/rnaseq", caller=Caller(2,"bob","lab"), enqueue=False)` returns `{'state':'ready','revision':'1.1','source':'cache','releases':['1.1','1.0'],…}`. Bob has no environment, no agent and no job.
- **Proposed fix.** Key the cache by owner: entries under `(owner_user_id, repo)`, or one file per user id, with the local caller (None) keeping its own entry. Alternatively drop the file and reuse the caller's own finished `tags` job within `TAGS_CACHE_SECONDS`, which is what `nfcore_catalogue` already does. Any change needs the A-17/A-18 cases of the release-lookup-job test cases revisited.
- **Proposed RED test.** `test_latest_release_cache_is_not_shared_between_callers`: user A's agent answers tags `["1.0"]`; `latest_release` for user B (own environment, no job) must answer `loading` and queue a job for B, not `ready` with 1.0 from `cache`.
- **HOT?** Yes (`actions/`).
- **Suggested tier.** B: it reverses a spec ruling about where the cache lives.

## Refuted

- **#8 "Site messages are redacted fail-open" (P3 as proposed): refuted as a defect of this unit.** The pattern gaps are real: `compute_envs.looks_like_credential` misses URL userinfo, bare `ghp_`/`glpat-` tokens, `Bearer …` and a short `sig=` (all four strings came back unchanged from `_outputs_reason`). Messages at actions:386 and :982 also pass `jobs.wait_for_result`'s message unfiltered (jobs.py:1316; `clean_result` only shortens it, jobs.py:1096-1098). But the filter is not a security boundary in this unit, for three reasons:
  1. The message comes from the caller's own agent and goes back to the same caller.
