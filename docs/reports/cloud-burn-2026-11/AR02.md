## Method

1. **Three lenses.** Three independent reviewers read the unit and produced 17 candidate findings. One looked at the job state machine (claim, take_result, expiry, prune and the hand-off record). One looked at trust and storage (tokens, users, file modes, clocks). One looked at drift (docstrings and docs against code, dead entry points).
2. **Refutation.** I tried to break each candidate. I re-read the cited code at the sha and looked for a spec, doc or test that makes the behaviour intended. I re-ran every repro with `python3 -I` against the worktree, using scripts that put `/tmp/cb/ro-AR02/platform` on `sys.path` and write only to `tempfile.mkdtemp()` folders. I also checked the callers, to see whether a claimed effect reaches a person. The default was "refuted" unless the evidence held. Several candidates turned out to be more serious than claimed:
   - F1: a pruned refused attempt blocks resume and relaunch of the whole analysis.
   - F2: the launch command would print a forged number as "submitted".
   - F7: AR01 F7 is a live consumer that fails open for a user named `.`.

   One was less serious than claimed:
   - F5: the launch command already recovers.
3. **Merging.** The 17 candidates became 12 surviving findings and 3 refuted; 2 were duplicates.

## Surviving findings (most severe first)

### F1 (P2): when the 7-day prune removes a refused launch job, the launch reads as "unknown": the freed run name is taken again, and the refused attempt starts to count, which blocks resume and relaunch of the whole analysis

- **Evidence.**
  - **What deletes the job.** Every queued job runs the prune `DELETE FROM jobs WHERE finished_at IS NOT NULL AND finished_at < now-7d` (jobs:156). It removes finished jobs of every kind, including a `launch_nextflow` job the agent `refused`.
  - **What reads the gap as unknown.** `launch_job` returns `'unknown'` when the launch row's job cannot be found (jobs:785-786). So a hand-off row whose launch the agent refused (slurm_job_id NULL) is reclassified from `refused` to `unknown` as time passes.
  - **Broken promise 1 (run name).** `latest_launch` says a refused launch "leaves its row and the name can be used again" (jobs:567-568), and `name_problem` restates it (jobs:803-805). After the prune, `_name_problem_of` returns the "result unknown" sentence (jobs:822-824). That sentence tells the person to search the site for leftovers that cannot exist.
  - **Broken promise 2 (attempt numbers).** `standing_attempts` (jobs:761-769) and docs/PLATFORM.md:653 say a refused attempt "does not use up its number". After the prune, the refused attempt stands. Its number is used up (`next_attempt`, jobs:772-773), and a request confirmed before the prune is refused by `_lineage` at jobs:870 ("another attempt was started meanwhile").
  - **Worse than the candidate said.** `abf_launch/build.py:473-478` refuses a resume or relaunch of any attempt that has a newer *standing* attempt ("已有較新的一次 … 只能對最新的一次"). Resuming the newer one is then refused by `build.py:462-463`, because the refused attempt has no Slurm number. So once the refused attempt's job is pruned, no attempt of the analysis can be resumed or relaunched. The person has to start a new analysis.
  - **Nothing records the refusal elsewhere.** The `launch_confirmation` docstring (jobs:662-665) says no column links a launch row to its confirmation, "and none is added", so no other copy of the refusal survives.
  - **What the tests cover.** TC-152 / D9 (`platform/tests/test_resume_platform.py:396-407`, `specs/009e-resume-relaunch/test-case.md:210`) pins `PRUNE_AFTER_SECONDS == 7 * 86400` and says retention must not be made longer. TC-053 (`test_resume_platform.py:380-393`) covers the prune of a *done* launch job only. No test covers a refused one.
- **Reproduction (measured).**
  - Name. Use `rig(t0, seen_until=t0+20*86400)`, `confirm.confirm_launch(st,'ce1',{run_name:'r1',run_folder:'/x/r1',agent:'ag'}, clock=t0)`, `jobs.claim(…, t0+1, tok)` and `take_result(…, 'refused', {ok:False}, t0+2)`. At day 0, `name_problem(con,'r1',t0+3)` returns `None`. Then call `jobs.enqueue_preflight(st,'ce1',clock=t0+8d, offline_after=30d)`, which prunes. Now `name_problem(con,'r1',t0+8d)` returns "the run name r1 was used already … 上一次送出的結果不明，請先查國網上的專屬資料夾與 nf-r1…".
  - Attempts. Insert run `x` (attempt 1, slurm 11, job done) and `x-a2` (parent_run x, attempt 2, resume, slurm NULL, job `refused`). At day 0, standing is `[('x',1)]`, `next_attempt` is 2, and nothing is newer than x. After an enqueue at day 8, standing is `[('x',1),('x-a2',2)]`, `next_attempt` is 3, and build.py's newer-than-x list is `[(2,'x-a2')]`, so the resume of x is refused. `name_problem('x-a2')` now says "result unknown".
- **Proposed fix (maintainer decides).**
  - (a) Leave out of the prune any `launch_nextflow` job in state `refused` whose launch row has slurm_job_id NULL. This lengthens retention only for that case. It still modifies the documented retention (docs/PLATFORM.md:878 "7 days after the job ends"; TC-152/D9), which under the constitution's Development Workflow (.specify/memory/constitution.md:250) needs the maintainer's explicit yes.
  - (b) Record the refusal on the hand-off row when it happens (a `refused_at` column written by `_apply_handover` / `claim`'s refusal path), and have `launch_job` read it when the job is gone. This adds a column, which the `launch_confirmation` docstring says is not done.
- **Proposed RED tests.** `test_a_refused_launch_still_frees_its_name_after_its_job_is_pruned`, `test_a_refused_attempt_does_not_use_up_its_number_after_the_prune`, `test_a_pruned_refused_attempt_does_not_block_resume_of_the_analysis`. They would go in a new file `platform/tests/test_prune_refused_launch.py`, which is not HOT.
- **HOT?** Yes (jobs.py; docs/PLATFORM.md if (a)).
- **Suggested tier.** B, the maintainer's lane. Option (a) touches a documented requirement.

### F2 (P2): take_result accepts and applies an answer to a job that was never handed out once that job has expired, so a Slurm number, a cancel time or fetched records are written for an order the agent never received

- **Evidence.**
  - **What is promised.**
    - The take_result docstring says "409 … not handed out" (jobs:1221).
    - The module docstring says an expired job "is never handed out" (jobs:8-9).
    - docs/PLATFORM.md:678 says a launch "that no agent takes" never even gets a token.
  - **Why the guard misses this case.** The not-handed-out guard is only `job["state"] == "queued"` (jobs:1247). When a waiter's deadline passes, `wait_for_result` calls `_expire` (jobs:1319), which sets `expired` on a job still `queued` (jobs:1294). `claimed_at`, the confirmation's `used_at` and the run token all stay unset.
  - **What the late branch then writes.** From then on an answer goes down the late branch (jobs:1253-1256), and `_apply_handover` runs:
    - For a launch it writes `launches.slurm_job_id` and `submitted_at` (jobs:1203-1204).
    - For a cancel it writes `cancel_requested_at` (jobs:1209-1210).
    - For a clean it writes `work_cleaned_at` (jobs:1211-1214).
    - For `fetch_run_records`, the pre-transaction peek accepts state `expired` without asking whether the job was claimed (jobs:1230-1232). It calls `records.store_files` into `records/<run>/`, which `rebuild` reads as truth.
  - **A forged number spreads.** `name_problem` then reports the run as submitted with that number (jobs:817-820). `enqueue_confirmed` accepts cancel and clean requests against it (jobs:927).
  - **The launch command would print it.** `abf_launch/cli.py:_report_launch` re-reads `submitted_at` *before* it looks at `claimed` (cli.py:228-235 vs 237). A forged late answer that arrives within the grace window is therefore printed as "已送出：Slurm 工作編號 … （代理在期限之後才回報；這個編號已記下。）".
  - **Who can do it.** Only the job's own agent (jobs:1243). The shipped agent answers only jobs it claimed, and resends only the identical body after a network error (`abf_station/agent.py:157-166`), so this needs a buggy or compromised agent. Hence P2 (risk), not P1.
  - **Is there a legitimate case?** No. `claimed_at` is written in the same transaction that hands the job out (jobs:982), and the column has existed since the jobs table was created (commit 4c043d42). No legitimate answer can reach a job whose `claimed_at` is NULL.
- **Reproduction (measured).** Use `rig(now)`, then `cid,jid = confirm.confirm_launch(st,'ce1',{run_name:'r1',run_folder:'/x/r1',agent:'ag'}, deadline_seconds=1)`.
  - `wait_for_result(…, clock=now+5)` returns `expired` with `claimed False`.
  - Then `take_result(st,'ag',jid,'done',{ok:True,slurm_job_id:4242}, now+6, tok)` returns `(200, {'accepted': False, 'late': True})`.
  - The launch row then holds `slurm_job_id 4242` and `submitted_at` is set. The job row is `expired` with `claimed_at None`, and `confirmations.used_at` is None.
  - `name_problem('r1')` returns "…它已送出過，Slurm 工作編號是 4242…".
  - The same answer while the job is still `queued` gets 409.
- **Proposed fix.** In `take_result`, answer 409 "This job was not handed out" whenever `job["claimed_at"] is None`, whatever the state, before the late branch. Add `peek["claimed_at"] is not None` to the `fetch_run_records` peek condition. Every existing late-answer test claims its job first (`test_cleanup_confirm.py:536-546`, `test_pipeline_files_queue.py:522-529`, `test_byte_channel_a.py:498-501`, `test_launch_platform.py:535-553`), so none of them changes.
- **Proposed RED tests.** `platform/tests/test_late_answer_guards.py::test_an_answer_to_a_job_that_expired_unclaimed_is_409_and_writes_no_slurm_number` and `::test_fetch_records_of_an_unclaimed_expired_job_are_not_stored`.
- **HOT?** Yes (jobs.py).
- **Suggested tier.** B.

### F3 (P2): index.db, tokens.db and platform.db, and their folder, are created with the process umask (0644 / 0755 under the default 022), while every neighbouring file the platform writes is owner-only

- **Evidence.**
  - **Where the files are made.** `store.connect` (store:318-324) and `store.connect_state` (store:652-656) call `path.parent.mkdir(parents=True, exist_ok=True)` and `sqlite3.connect` with no mode and no umask.
  - **Nothing tightens them later.** `git grep -E 'umask|chmod|0o700|0o600'` over `platform/abf_platform` finds only `records.py:60-62` (folder 0700, files 0600), `uploads_web.py:229,295,303`, `actions/uploads.py:73,78`, `web.py:117` (signing key 0600) and `cli.py:190`. None of them touches the databases.
  - **The shipped units add nothing.** The systemd user units (`deploy/systemd/*.service.in`) set no `UMask=`, so the default 022 applies.
  - **What is exposed.**
    - tokens.db holds `users.password_hash`, which is scrypt and can be cracked offline (store:100-106), plus token hashes, web sessions and OAuth state.
    - platform.db holds confirmation bundles and screen text: parameters and paths.
    - platform.db's `jobs.result_json` also holds `read_run_file` bytes (results up to 25 MB, jobs:50), task logs and site listings.
  - **The inconsistency.** The same result files are kept owner-only under `records/` (0700), yet readable in platform.db.
  - **The project wants owner-only.** docs/OPERATIONS.md:94 and docs/PLATFORM.md:706 call the signing key next to these files "owner-only".
  - **What limits it.** A home folder of mode 0700/0750 limits exposure. A 0755 home, or `ABF_PLATFORM_DB` / `ABF_PLATFORM_STATE` / `ABF_PLATFORM_TOKENS` pointing at a shared folder, exposes everything to other local users of the platform host.
- **Reproduction (measured).** Run `os.umask(0o022)` with `XDG_DATA_HOME=<tmp>`, then `store.init_index`, `store.init_state`, `store.create_user(tp,'ann','lab')` and `store.set_web_password(tp,'ann','correct horse')`. Result:
  - `abf-platform/` is `0o755`.
  - `index.db`, `tokens.db` and `platform.db` are `0o644`.
  - `sqlite3.connect(tokens.db).execute('select password_hash from users')` returns `scrypt$16384$8$1$…`.
- **Proposed fix.** In `store.connect` and `store.connect_state`:
  - Create the parent folder with `mode=0o700`, and chmod it when this call created it.
  - Pre-create a missing database with `os.open(path, O_CREAT|O_EXCL|O_WRONLY, 0o600)`.
  - Run `chmod 0o600` on an existing database the process owns.
  - Cover the `-journal`/`-wal`/`-shm` companions, for example by wrapping the connect in `os.umask(0o077)`.

  Optionally add `UMask=0077` to the three unit templates (deploy/ is not HOT).
- **Proposed RED test.** `platform/tests/test_store_file_modes.py::test_the_three_databases_and_their_folder_are_owner_only`.
- **HOT?** Yes (store.py).
- **Suggested tier.** B.

### F4 (P3): an expired job takes any number of late answers, and each one re-runs `_apply_handover`: a contradicting second answer overwrites the Slurm number or revokes the run token of a run recorded as submitted

- **Evidence.**
  - **The guard does not cover expired jobs.** The "answered already" guard is `job["state"] in _STATES` (jobs:1250). `expired` is not in `_STATES` (jobs:995), so every later answer to an expired job goes down the late branch again. Each one overwrites `late_result_json` (jobs:1254-1255) and calls `_apply_handover` (jobs:1256).
  - **Contradicting answers.**
    - The launch UPDATE has no `slurm_job_id IS NULL` guard (jobs:1203), so a second late `done` replaces the first number.
    - A late `error` after a late `done` makes `_apply_handover` return the run name (jobs:1206), and `take_result` then revokes every run token of that name (jobs:1275-1276). The Nextflow run the record calls submitted can then no longer report.
    - Later cancel and clean requests take their number from that row (jobs:886, 927). The agent's own check (`abf_station/cancel.py:64-70`) stops a wrong number from cancelling another job, so the damage stays in the record.
  - **With the shipped agent.** It resends the identical body after a network error (`abf_station/agent.py:157-166`). For a late cancel or clean, that moves `cancel_requested_at` / `work_cleaned_at` forward, because those UPDATEs have no `COALESCE` (jobs:1209, 1213). That is harmless but not idempotent.
  - **Severity.** Contradicting answers need a misbehaving agent, hence P3. The docstring promises 409 for "already answered" (jobs:1221).
- **Reproduction (measured).**
  - Token. Claim a launch (`deadline_seconds=10`), so it gets a run token. A late `done {slurm_job_id: 77}` at t0+20 leaves the token live. A second late `error` at t0+21 returns `(200, late)`, and `lookup_token(run_token)` is then `None`, while `launches.slurm_job_id` stays 77.
  - Number. On an expired job, `done 4242` then `done 9999` both return `(200, late)`, and the launch row ends with `slurm_job_id 9999`.
- **Proposed fix.** In the late branch, return 409 "This job was answered already" when `job["late_result_json"] is not None`. Add `AND slurm_job_id IS NULL` to the launch UPDATE in `_apply_handover` as a second guard. The shipped agent's retry after a lost reply then gets 409, which it already treats as final (`abf_station/agent.py:165-167`: any status other than 401/403 ends the retries).
- **Proposed RED test.** `platform/tests/test_late_answer_guards.py::test_a_second_late_answer_is_409_and_keeps_the_first_slurm_number_and_the_token`.
- **HOT?** Yes (jobs.py).
- **Suggested tier.** B, to be done with F2 since both fixes are in the same branch.

### F5 (P3): wait_for_result says "the job was dropped and will not run later" for a job the agent took, and for one answered on time while the waiter was expiring it

- **Evidence.**
  - **The race.** The waiting loop ends on the clock with the last row it read still `claimed` (jobs:1306-1310). `_expire` then updates only rows still `queued`/`claimed` and ignores the rowcount (jobs:1294). `take_result` decides "on time" from a `now` read *before* the peek, `records.store_files` and `BEGIN IMMEDIATE` (jobs:1227-1237). That lock may wait up to 30 s (`store.connect_state`, timeout=30). So an on-time `done` can commit between the waiter's last read and `_expire`. The waiter still returns `expired` with "The job was dropped and will not run later" (jobs:1319-1323) while the row is `done`.
  - **The same words for a claimed job.** The sentence is the same when `claimed` is true (jobs:1321-1323). In that case the agent holds the job and may act: `abf_station/cancel.py` has no deadline check, so a claimed cancel still runs `scancel`.
  - **What a person sees.**
    - The candidate said the launch command would mislead. That part is refuted: `abf_launch/cli.py:223-235` re-reads `submitted_at` after an expiry and prints the submission.
    - The cancel command does not recover. On `expired` it prints `未取消：` followed by the "will not run later" sentence (`abf_launch/cli.py:273, 293-294`), even when the cancel was sent and `cancel_requested_at` is written.
    - The preflight command prints `refused:` (`platform/abf_platform/cli.py:503-506`) even when the answer was applied.
- **Reproduction (measured).** Claim a launch with `deadline_seconds=10`. Wrap `jobs._expire` so that it first calls `take_result(…,'done',{ok:True,slurm_job_id:88}, t0+9.99)` and then the real `_expire`. `wait_for_result(…, clock=t0+10)` returns `expired | The agent did not answer (代理沒有回應)…`, while the job row is `done` and `launches.slurm_job_id` is 88. No test pins the sentence (`git grep 'will not run later' platform/tests` finds nothing).
- **Proposed fix.** Have `_expire` return the rowcount. When it is 0, re-read the row: if the state is in `_STATES`, return that answer through the same branch as jobs:1313-1318, and if the row is `expired` with a late answer, say so. When `claimed` is true, say the agent took the job and did not answer in time, that it may still have acted, and that its late answer will be recorded, instead of "will not run later".
- **Proposed RED tests.** `test_wait_for_result_returns_the_answer_that_landed_just_before_it_expired_the_job`, `test_wait_for_result_does_not_say_will_not_run_for_a_claimed_job`.
- **HOT?** Yes (jobs.py).
- **Suggested tier.** B, because it changes what a person sees.

### F6 (P3): lookup_token keeps a disabled user's agent token alive, while every other credential of that user is refused

- **Evidence.**
  - **The lookup.** `lookup_token`'s SQL has no join to `users` and no `disabled_at` test (store:987-989).
  - **The other lookups do refuse.** `lookup_pat` (store:901-903), `lookup_oauth_access` (store:916-919), the web session and login (store:1219-1223, 1252-1257) and `oauth.py:361-371` all refuse `disabled_at IS NOT NULL`.
  - **Docs and specs.** docs/PLATFORM.md:752 says "A disabled user's tokens stop working at once", and `specs/009c-human-channel/ledger.md:12` says the same for cookies.
  - **Where it is used.** Agent auth (`agents.py:124-126`) uses `lookup_token` only. A disabled user's agent therefore keeps polling, claiming that user's queued jobs (launches with fresh run tokens included) and posting answers.
  - **Why P3.** No production code sets `disabled_at` (`git grep disabled_at` finds only reads, and `specs/009d-pat-identity/plan.md:70` says "no CLI command to disable a user in this slice"), so this is latent until a disable command exists.
- **Reproduction (measured).** `create_user(tp,'ann','lab')`, then create a `pat` token and an `agent` token (`agent_name='ann-agent'`, `user_id`), then `UPDATE users SET disabled_at=now`. `lookup_pat` returns `None`, while `lookup_token(agent)` returns `{'kind':'agent','agent_name':'ann-agent','user_id':1,…}`.
- **Proposed fix.** In `lookup_token`, `LEFT JOIN users u ON u.id = tokens.user_id` and require `tokens.kind <> 'agent' OR tokens.user_id IS NULL OR u.disabled_at IS NULL`. An agent token made before 116, with no user, keeps working as today. Alternatively, have the future disable command revoke the user's agent tokens.
- **Proposed RED test.** `platform/tests/test_pat.py::test_a_disabled_users_agent_token_is_refused_at_poll`, or a new non-HOT file `test_disabled_agent_token.py`.
- **HOT?** Yes (store.py).
- **Suggested tier.** B. It only makes a gate stricter, but it is authentication.

### F7 (P3): store.create_user accepts any name (`.`, `..`, `a/b`, `""`, control characters), and the name is later joined into folder paths and cloud prefixes, where one consumer fails open

- **Evidence.**
  - **No check at creation.** `create_user` checks nothing but uniqueness (store:796-807), and `cmd_user_add` passes the typed name through (cli.py:145).
  - **Consumers that check.** Most consumers check the name themselves: `actions.caller_area` and `confined_samplesheet` (actions/__init__.py:1328-1347) and `cloud_store._single` (cloud_store.py:103-106). The last runs before `jobs._uploaded_file` joins `Path(uploads_dir)/owner_name` (jobs:234, reached only after `cloud_store.object_url` at jobs:278).
  - **The candidate's own refutation is wrong.** The candidate called this "not exploitable today", but did not try `.`. AR01 F7 measured that `actions._uploads_problem` (actions/__init__.py:353-365) lets a user named `.` list every user's upload folder. So one consumer already forgot the rule, and validating the name once at creation removes the root cause.
  - **Why P3.** Only an administrator can create a user.
- **Reproduction (measured).** `store.create_user(tp, n, 'lab')` for `'..'`, `'a/b'`, `''` and `'x\ny'` returned new ids 2-5. `'.'` is accepted the same way, since there is no check.
- **Proposed fix.** Validate in `create_user` against one pattern, for example `^[a-z][a-z0-9_.-]{0,63}\Z` (which also excludes `.` and `..`). Raise `ValueError` with a bilingual sentence, and have `cmd_user_add` print it. Keep the consumers' own checks.
- **Proposed RED test.** `platform/tests/test_user_names.py::test_create_user_refuses_a_name_that_cannot_be_a_single_folder`.
- **HOT?** Yes (store.py, cli.py).
- **Suggested tier.** C, defence in depth that pairs with AR01 F7.

### F8 (P3): the late-answer contract is stated three different ways, and none of them matches the code

- **Evidence.**
  - **What is written.**
    - The module docstring (jobs:9-11) and take_result's docstring (jobs:1222-1223) say only "a launch or a cancel" write their fact late.
    - docs/PLATFORM.md:207 says a late answer "is kept apart and changes nothing".
  - **What the code does.**
    - `_apply_handover` also writes `work_cleaned_at` for a late `clean_work` answer (jobs:1211-1214). TC-061 asserts exactly that (`platform/tests/test_cleanup_confirm.py:536-546`), so the behaviour is intended and the text is stale.
    - A late `fetch_run_records` answer is stored to `records/` before the transaction (jobs:1230-1232).

## Refuted

- **#5, "enqueue_confirmed does not hold a cancel's content to the hand-off record".** The code does not compare `bundle["slurm_job_id"]`, `ce_name` or the agent with the record for `cancel_run` (jobs:924-932). The claimed consequence, a cancel "sent to whatever agent and job number it names", does not hold, for three reasons:
  - Every shipped path builds the cancel bundle from the newest hand-off row (`abf_launch/build.py:296-336`: run_name, slurm_job_id, run_folder and agent are copied from the record, and a different current agent is refused).
  - The content is hash-bound to what a person confirmed (jobs:529-531), and `enqueue_confirmed` already refuses an agent other than the environment's (jobs:906).
  - The agent refuses unless `squeue` says the job is named `nf-<run>`, is owned by the site user and runs in the bundle's `run_folder` (`abf_station/cancel.py:64-70`). A wrong number therefore stops nothing.

  Comparing the number with the record, as `_check_clean` does (jobs:886), would add symmetry only. No reachable defect.
- **#9, "ABF_PLATFORM_CLOCK_OFFSET=-inf revives expired tokens".** The offset is a documented knob whose stated effect is exactly this: docs/PLATFORM.md:904 says "It also moves the clock by which a run token expires", and TC-020 / test_pat.py:734 use it. It is read only from the server's own environment: the systemd `EnvironmentFile=%h/.config/abf-platform/env`, which the operator owns (deploy/systemd/*.service.in). Whoever can set it can already write tokens.db. It is not a trust boundary, and `-inf` is a contrived misconfiguration rather than an input any other party controls.
- **#17, "enqueue_launch / enqueue_cancel have no production caller".** True: only tests call them (`git grep -lw` finds jobs.py plus tests). It is not a defect, though:
  - They go through the same `enqueue_confirmed` guard, so they cannot queue anything without a confirmed, unspent, hash-matching confirmation.
  - The docstring at jobs:894 that names them as callers is accurate.
  - Moving them would edit about 7 test files (some HOT: `platform/tests/mcp/`) for no change in behaviour.

  The candidate's own sub-items were re-checked and are refuted too:
  - (a) `actions/__init__.py:556-560` catches `RunFileRefused` and then `JobRefused` separately.
  - (b) `reload_site_inventory` checks ownership through `compute_envs.get(owner=…)` (actions/__init__.py:1110).
  - (c) The ten kinds and the "six only read" count match the CHECK (store:242).
  - (d) The deadline defaults match docs/PLATFORM.md:198-202.
- **Duplicates merged.** #6 is #1 (now F2). #11 is #1 plus #3, and was split between F2 and F4.
- **Part of #4 refuted.** "The CLI … would tell the person that the run will not happen while the hand-off record holds its Slurm number": the launch command re-reads `submitted_at` after an expiry (`abf_launch/cli.py:223-235`). The remaining effect is on cancel and preflight (F5).
