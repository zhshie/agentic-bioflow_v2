## Surviving findings (most severe first)

### F1 (P1): `snapshot()` tests `"config" in row`, and on a `sqlite3.Row` that compares column values, so an environment with any field equal to `config` can get no preflight, listing, upload, fetch, task-log or file-read job (IndexError)

- **Evidence.** `ce:933`: `v = row_or_view if "config" in row_or_view else view(row_or_view)`. `sqlite3.Row` has no `__contains__`, so `in` falls back to iterating the row's values. Every production caller passes a Row from `_target` (`jobs.py:117`): `jobs.py:215` (preflight, list_site_files), `:282` (put_upload), `:396` (fetch), `:424` (task log), `:478` (read_run_file). When any column value is exactly `"config"`, the Row is mistaken for a view, and `v["config"]` (`ce:934`) raises `IndexError: No item with that key`. That is not `JobRefused` or `CEError`. All of these values pass the rules: name (`_NAME`, `ce:64`), description (`ce:625`), credentialsId (`_CRED_NAME`, `ce:69`) and agent (`ce:631`). `queue_first_preflight` (`ce:856`) calls `jobs.enqueue_preflight`, so `abf-platform ce create`/`ce update` (`cli.py:436`, `:450`) and site-pipeline registration (`actions/__init__.py:1136`) crash with a traceback after the row is already committed. The environment then stays `creating` for good.
- **Correction to the candidate.** Launch and cancel are not affected directly. Their bundles use `abf_station.launch.snapshot_ce` on a view (`abf_launch/build.py:328`, `:405`). A new environment still cannot launch, because it never leaves `creating`. An `available` environment whose description is later changed to `config` still launches, but its preflight, listing, upload, fetch, task-log and file-read jobs all crash.
- **Reproduction (measured).**
  ```
  python3 -I - <<'EOF'
  import sys, os, tempfile; sys.path.insert(0, '/tmp/cb/ro-AR03/platform')
  from abf_platform import compute_envs as ce, jobs, agents
  db = os.path.join(tempfile.mkdtemp(), 'platform.db'); agents.register(db, 'ag', '1')
  for n, kw in (('plain', {}), ('config', {}), ('byDesc', {'description': 'config'}), ('byCred', {'credentialsId': 'config'})):
      ce.create(db, dict(name=n, platform='slurm-platform', agent='ag', config={'workDir': '/w', 'headQueue': 'q'}, **kw))
      try: jobs.enqueue_preflight(db, n); print(n, 'queued')
      except Exception as e: print(n, type(e).__name__, e)
  EOF
  ```
  → `plain queued`, then `config / byDesc / byCred IndexError No item with that key`. The same happens for an agent named `config`. A plain-Python check gives `'config' in Row(name='config')` → True and `'name' in Row` → False.
- **Proposed fix.** `v = row_or_view if isinstance(row_or_view, dict) else view(row_or_view)`.
- **Proposed RED test.** `platform/tests/test_ce_snapshot_row.py::test_snapshot_of_a_row_whose_description_is_config_is_still_a_snapshot` and `::test_enqueue_preflight_for_an_environment_named_config` (new file, not HOT).
- **HOT?** No (the fix is in `compute_envs.py`; the HOT callers in `jobs.py` need no change).
- **Suggested tier.** C (a bug fix inside the existing contract).

### F2 (P2): `update()` never invalidates the last preflight, so an `available` environment keeps `available` (and `enable()` restores it) for settings that were never checked

- **Evidence.** `update()` (`ce:804-837`) rewrites `config_json`, `agent` and `credentials_id`. It resets `status`/`checked_ok` only for an `unsupported` row (`ce:831-834`). After the update, `queue_first_preflight` writes its note only while `status == creating` (`ce:863`, `only_status=CREATING`). So an `available` environment keeps the message "preflight passed (預檢通過): …" for the old settings. When the agent is offline (code `no_agent`), nothing at all shows that the new settings are unchecked. `jobs._target` lets `launch_nextflow`, `list_site_files` and `put_upload` through on `available` (`jobs.py:148`). For a disabled environment, `cmd_ce_update` skips the preflight (`cli.py:449`) and `_target` refuses one (`jobs.py:139-140`). `enable()` then reads the stale `checked_ok == 1` and sets `available` with "enabled again; the last preflight had passed" (`ce:904-905`). docs/PLATFORM.md:394 defines `available` as "the last preflight passed every check". No doc or test says an update keeps the old verdict.
- **Reproduction (measured).** Create a Slurm environment, record a passing preflight with `apply_preflight(con, 'e2', True, …)`, then call `ce.update(db, 'e2', {'config': {'workDir': '/other/unchecked'}})` → `available | preflight passed (預檢通過): workDir | /other/unchecked`. Then `disable`, `update` the workDir to `/nowhere/never/checked`, and `enable` → `available | enabled again; the last preflight had passed (重新啟用) | /nowhere/never/checked`.
- **Proposed fix.** In `update()`, when the stored config (`json.dumps(…, sort_keys=True)`), `agent` or `credentials_id` actually changes, set `checked_ok = 0` in the same UPDATE. If the status is not `disabled`/`unsupported`, also set `status = creating` and the message "waiting for the first preflight". `enable()` is then right without change. The maintainer may want sitePipelines-only changes exempt (`actions/__init__.py:1133` registers through `update`). If so, compare the config with that key removed.
- **Proposed RED test.** `test_update_of_an_available_environment_waits_for_a_new_preflight`; `test_enable_after_a_config_change_while_disabled_waits_for_a_preflight` (new file, e.g. `platform/tests/test_ce_update_invalidates.py`).
- **HOT?** No for the fix. The settings page (`web_settings.py`) and `actions/` callers are HOT and only report the queued preflight, but any HOT test that assumes "still available after registering a version" would need the verifier's attention.
- **Suggested tier.** B (what a user sees changes: an edited environment goes back to `creating` until the agent answers).

### F3 (P2): `looks_like_credential` misses common token shapes (`tower { accessToken = … }`, `GH_TOKEN=`, `NXF_TOWER_TOKEN=`, bare `ghp_…`/`AIza…`/JWT), so they are stored, shown over MCP, sent to the agent, and in typed fields echoed back

- **Evidence.** The assignment pattern needs a word boundary right before the keyword (`ce:122`, `\b(?:password|…|token)\w*\s*[=:]`). In `GH_TOKEN=`, `NXF_TOWER_TOKEN=` and `AZURE_STORAGE_KEY=` the `_` is a word character, and in `accessToken` the keyword sits inside a camelCase word, so none of them has that boundary. The `export` pattern (`ce:121`) needs the word `export`. No pattern knows the prefixes of GitHub, Google API, Slack or JWT tokens. `clean()` relies on this one scan (`ce:640-642`) for `description`, `credentialsId` and all of `config`. The module docstring promises "a value that looks like one is refused" (`ce:7-8`). Where the value goes:
  - MCP `list_compute_envs`/`get_compute_env` return the full config (`actions/__init__.py:226-235` → `ce:683`).
  - the launch bundle carries `nextflowConfig`/`preRunScript` to the agent (`station/launch.py:198-205`, via `abf_launch/build.py:328,405`).
  - in a typed field the scan's miss is then echoed by `_shown` (up to 60 characters; `ce:332-333`). `credentialsId` (`_CRED_NAME`, `ce:69`) accepts all three token shapes, and that field's own message says "never the credential itself" (`ce:629`). `snapshot()` hands it to the agent (`ce:936,940,944,948`) and `view()` lists it (`ce:675`).
- **Reproduction (measured).** `looks_like_credential` returns False for all of these: `tower { accessToken = 'eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxIn0.c2lnbmF0dXJl' }`, `env { GITHUB_TOKEN = 'ghp_…36' }`, `GH_TOKEN=ghp_… nextflow run x`, `NXF_TOWER_TOKEN=eyJ…`, `AZURE_STORAGE_KEY=…`, a bare `ghp_…`, `AIzaSy…(39)`, `xoxb-…` and `tower.accessToken = '…'`. It returns True for `token = 'x'`, `export NXF_TOWER_TOKEN=x` and `aws { accessKey = … }`. `clean()` ACCEPTS `nextflowConfig="tower { accessToken = '<jwt>' }"`, `preRunScript="GH_TOKEN=ghp_…"`, an environment value that is a bare `ghp_…`, and `credentialsId` = `ghp_…`, `AIzaSy…` or a JWT. It refuses `credentialsId` = `AKIA…` and `sk-ant-…`. With `project='ghp_…'` on Google Batch, the error ends with `(got 'ghp_a1B2c3D…')`. (An environment variable *named* `GH_TOKEN` is refused, by name, through `common.is_secret_name`.)
- **Constraint on the fix.** `platform/tests/test_model_key_refusal.py:66-83` (TC-015) pins the first six patterns as unchanged and the tail list exactly. The candidate's fix ("replace the leading `\b` in pattern 6") would therefore break TC-015. Append new patterns instead, and extend the tail list in that test in the same PR. That adds to the assertion; it does not weaken it.
- **Proposed fix.** Append, after the existing twelve: a keyword-assignment pattern with no leading boundary, e.g. `(?i)(?:token|secret|password|passwd|api[_-]?key|access[_-]?key|secret[_-]?key|storage[_-]?key|account[_-]?key)\w*['"]?\s*[=:]\s*\S`; `\bgh[pousr]_[A-Za-z0-9]{36,}`; `\bgithub_pat_[A-Za-z0-9_]{22,}`; `\bAIza[0-9A-Za-z_-]{35}`; `\bxox[abprs]-[A-Za-z0-9-]{10,}`; `\beyJ[A-Za-z0-9_-]{8,}\.[A-Za-z0-9_-]{8,}\.[A-Za-z0-9_-]{8,}`.
- **Proposed RED test.** `platform/tests/test_ce_credential_shapes.py::test_unbounded_secret_assignments_are_refused` (parametrised over the strings above, through `clean` on `nextflowConfig`, `preRunScript`, `description` and an environment value); `::test_credentials_id_refuses_token_shapes`.
- **HOT?** No.
- **Suggested tier.** B (stricter Safety Net; more refusals a user sees; TC-015's list grows).

### F4 (P2): a samplesheet `https://` cell holding a GCS V4 signed URL or `user:password@` passes the only credential gate and goes to Nextflow as written

- **Evidence.** For a Slurm launch, an http(s) cell is "handed to Nextflow as written". Its only check is `compute_envs.looks_like_credential` (`station/launch.py:372-376`), and `abf_launch/build.py:242-243` skips such cells. The patterns cover an Azure SAS (`[?&]sig=`, `ce:127`) and an S3 presigned URL (through its `AKIA`/`ASIA` key id or `X-Amz-Security-Token=`). They do not cover GCS V4 (`X-Goog-Credential`/`X-Goog-Signature`) or basic-auth userinfo. The station's own refusal text, "the address looks like it carries a credential" (`station/launch.py:375`), shows that signed URLs are meant to be refused. (Datasets refuse every URL anyway, `actions/datasets.py:305-306`, so only the launch path is affected.)
- **Reproduction (measured).** `looks_like_credential` → False for `https://storage.googleapis.com/b/x.fq.gz?X-Goog-Algorithm=GOOG4-RSA-SHA256&X-Goog-Credential=sa%40p.iam.gserviceaccount.com%2F…&X-Goog-Signature=4f2a…` and for `https://alice:hunter2pass@ftp.lab.example/x.fq.gz`. It → True for the Azure SAS and for both S3 presigned forms.
- **Proposed fix.** Append (same TC-015 constraint as F3) `(?i)[?&]X-Goog-(?:Signature|Credential)=`, `(?i)[?&]X-Amz-(?:Signature|Credential|Security-Token)=` (so S3 no longer depends on the key-id shape) and `://[^/?#@\s:]+:[^/?#@\s]+@`.
- **Proposed RED test.** `platform/tests/test_ce_credential_shapes.py::test_signed_and_userinfo_urls_look_like_credentials`, plus a station-level case that `_check_samplesheet` raises `BundleError` for both URLs (the test file lives under `platform/tests/`; nothing in `abf_station/` changes).
- **HOT?** No.
- **Suggested tier.** B (stricter; more refusals).

### F9 (P3): the "scan first, then any message may repeat a value" design has two gaps: the `platform` value and config KEYS are never scanned, so a credential there is echoed (or, for a modelled type, stored)

- **Evidence.** The comment at `ce:639` says the credential scan runs "first of all, before any rule that could repeat a value". But `platform` is echoed before the scan (`ce:622-623`, `unknown type %r`) and is not in the scanned dict (`ce:640`). `credential_findings` checks dict keys only with `common.is_secret_name` (`ce:142`; `common.py:15`: `token|password|secret|key`), never with the value patterns. Typed platforms then echo an unknown key (`ce:199`, `:342`, `:429`, `:489`, `:553`). `_check_other` stores any key for a modelled type (`ce:598-608`), and `view()`/MCP list it. `CEError`'s docstring (`ce:59`) says the text "never repeats a rejected value". The typed checks deliberately show 60 characters of a bad value (`_shown`), so that contract already depends on the scan having run first.

### F10 (P3): `clean()` lets a raw `TypeError` out for a non-JSON config, accepts `NaN`, and the guard in `_check_other` is dead code

- **Evidence.** `ce:638` `json.loads(json.dumps(config))` runs outside any try, so a set raises `TypeError` before `_check_other`'s `except (TypeError, ValueError)` (`ce:603-606`) is reached. - **Proposed RED test.** `platform/tests/test_ce_clean_json.py::test_clean_refuses_unserialisable_or_nan_config_with_ceerror`.

- **Suggested tier.** C.
