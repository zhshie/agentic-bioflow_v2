### F1 (P2, CONFIRMED): `fetch_run_records` never returns the trace of a platform-launched run: launches add no `-with-trace`, and the nf-core trace lies in a subfolder, which `_TRACE` refuses

- **Evidence.** `F:76-77` strips the `<folder>/` prefix from the log's trace path, and `F:81` then requires `_TRACE` (`F:17`, `^[A-Za-z0-9][A-Za-z0-9._-]{0,100}\Z`), which allows no `/`. The platform sets `outdir = run_folder + "/results"` (`platform/abf_station/launch.py:466`). The nf-core template writes its trace to `${params.outdir}/pipeline_info/execution_trace_<ts>.txt`, which is inside the run folder but one folder down, so it is always refused. `launch.py` contains no `trace` at all (`grep -n trace` finds nothing), so no production launch adds `-with-trace`. The only `-with-trace` runs are in tests (`platform/tests/e2e_harness.py:108`, `test_launch_e2e.py:200`). The design promised more. specs/007b-launch/spec.md:116 says "以及 log 裡指名的 trace", and plan.md:17 says "the trace file named in the log line … which must be inside the run folder". research.md:42 says "Ampliseq writes its own trace. Other pipelines get `-with-trace`", but ampliseq's own trace is also under `pipeline_info/`. As a result, rebuild from fetched records never gets per-task rows for these runs. A small part of #14 is refuted. The refusal text `不在專屬資料夾內或名稱不合` says "outside the folder *or* name does not fit". That is an either/or, so it is not false, only unhelpful.
- **Reproduction (run).** `python3 -I /tmp/cb/ar07x/t14.py`. The run folder holds `results/pipeline_info/execution_trace_2026-11-04_10-00-00.txt`, and `.nextflow.log` names it by its absolute path. Output: `done ['.nextflow.log', '.nextflow/history'] ["trace 檔 'results/pipeline_info/execution_trace_2026-11-04_10-00-00.txt' 不在專屬資料夾內或名稱不合，已拒絕"]`.
- **Fix.** Choose one and write it into FR-011. (a) Have the head script pass an explicit `-with-trace trace-<run>.txt` (a top-level plain name). `fetch` then accepts exactly that name, which also closes F7. (b) Accept a relative path below the run folder. Every component must match `_TRACE`, none may be `..`, and the first component must not be `work`, `pipeline`, `.nextflow*` or a `_NOT_RECORDS` name. Read it with a `realpath -z` comparison against the folder, so that no link is followed. With either choice, F2 must also be fixed, or the fetched trace is still not used.
- **RED test.** `platform/tests/test_station_cancel.py::test_tc034b_an_nfcore_trace_under_results_pipeline_info_is_read` for (b), or `platform/tests/test_launch_nextflow.py::test_head_script_names_its_own_trace_file` for (a).
- **HOT?** No: `fetch.py` and `launch.py` are FORBIDDEN (maintainer), and `test_station_cancel.py` is not HOT. **Tier:** B (it changes what is read from the site and amends FR-011).

### F2 (P2, CONFIRMED): rebuild looks for a fetched trace at the site's absolute path, not in the records folder, so the copy that fetch brought back is never read

- **Evidence.** Nextflow's log line names the trace by its absolute path. The fixture `test_station_cancel.py:148` writes `trace file: %s/trace-1.txt % f`, and nf-core runs do the same. `fetch` stores the file under its bare name (`F:89`; `records.store_files` writes `records/<run>/<name>`, `platform/abf_platform/records.py:58`), and copies the log unchanged. `rebuild._parse_log` keeps the absolute text (`platform/abf_platform/rebuild.py:55-56`). `_build_run` then does `trace = folder / log["trace"]` (`rebuild.py:133`), and a pathlib join with an absolute path discards `folder`. On a platform host that is not the site, the trace is "gone" (`rebuild.py:137`), and task counts are zero. The e2e test hides this: `test_launch_e2e.py:189-219` asserts `tasks.total == 7` after a fetch and rebuild. It passes only because the fake site's folder is on the same disk, so the absolute path exists there.
- **Reproduction (run).** `/tmp/cb/ar07x/rec/run-a/` holds `.nextflow/history`, `trace-1.txt`, and a `.nextflow.log` that names `/work/u/runs/run-a/trace-1.txt`. Running `rebuild._runs_of_folder(Path('/tmp/cb/ar07x/rec/run-a'), notes)` gives `notes: ['/tmp/cb/ar07x/rec/run-a: trace file /work/u/runs/run-a/trace-1.txt of run run-a is gone, task numbers are unknown']` and every total 0, although `trace-1.txt` is in the folder.
- **Fix.** In `_build_run`, when `folder / log["trace"]` is not a file and `log["trace"]` is absolute, use `folder / PurePosixPath(log["trace"]).name` if that name is a file. That is exactly the name `fetch` stored. Do not rewrite the fetched log.
- **RED test.** `platform/tests/test_rebuild_records_trace.py::test_rebuild_from_fetched_records_finds_trace_when_site_path_is_absent` (new file). Use a unit test, not `test_launch_e2e.py`, which is on the dynamic HOT list.
- **HOT?** No: `rebuild.py` is neither HOT nor FORBIDDEN. This is the one fix in this report that cloud-burn may make. **Tier:** C.

### F3 (P2, CONFIRMED by code): the site inventory can take longer than the whole preflight deadline, and a late answer throws away a passing verdict

- **Evidence.** The inventory call is given `INVENTORY_TIMEOUT = 180` (`H:441`, `H:485`). `Site.call` adds 15 s to that (`platform/abf_station/site.py:85`), and the call runs only after up to eight check round trips of 20+15 s each (`site.py:19`). The whole preflight job has `DEADLINE_SECONDS["preflight"] = 180`, counted from when the job is queued (`platform/abf_platform/jobs.py:30`, `:158`). An answer after the deadline takes the late branch (`jobs.py:1253`). Only the on-time branch calls `compute_envs.apply_preflight` (`jobs.py:1263`). So a slow `module -t avail`, followed by up to 200 `module show` calls (`H:449-451`), leaves the environment unavailable even when every check passed. That contradicts `H:274-276` ("never changes the verdict") and specs/settings-pick-installed/plan.md:61. The agent also runs one job at a time (`platform/abf_station/agent.py:169-183`), so every job queued behind the preflight, a cancel included, waits up to about 195 s more. Constants as printed: `180 20 180`.
- **Reproduction.** Not run against a slow site; none is available. With a FakeSite whose inventory call sleeps longer than the time left before the deadline, the job is recorded `expired` and `apply_preflight` is not called (code path `jobs.py:1253-1257`).
- **Fix.** Give the inventory only the time that is left: `ctx.job_started` already exists (`agent.py:176`). Subtract the elapsed time and a margin from the preflight deadline, cap the result (for example 60 s), and answer `status: "error"` when no time is left. Alternatively, send the verdict first and read the inventory as its own job.
- **RED test.** `platform/tests/test_station_site_inventory.py::test_a_slow_inventory_never_delays_the_preflight_answer_past_its_deadline`.
- **HOT?** No for `handlers.py` (FORBIDDEN, maintainer). Yes if the deadline is shared through `jobs.py`. **Tier:** C (local cap), or B if the deadline is sent in the job.

### F4 (P2, CONFIRMED): `list_site_files` says an existing folder "does not exist" when an entry is removed while `find` lists it, and the entries already read are thrown away

- **Evidence.** `H:586` runs `find <dir> -mindepth 1 -maxdepth 1 -printf '%y\t%s\t%T@\t%f\0'`. When `rc != 0` and stderr holds "No such file", `H:590-591` answers `not_found`, "the folder does not exist on the site", and stdout is never parsed. `find` stats every entry. One that vanishes between `readdir` and `lstat` makes `find` print `find: '<dir>/x': No such file or directory` and exit 1, although `H:575-585` has just found the folder to be a directory. A run or work folder changes all the time during a run.

Result: `{('done', None): 396, ('error', 'not_found'): 4}`. Raw `find` (GNU findutils 4.9.0) exited nonzero 22 times in 1000. With `-ignore_readdir_race` added it exited nonzero 0 times in 1000. A missing start folder still exits 1 with "No such file" under that option, so `not_found` stays correct for the folder itself.
- **Fix.** Add `-ignore_readdir_race` to the `find` at `H:586`. GNU find is already assumed there, through `-printf`. If belt and braces are wanted, also parse stdout when it is NUL-terminated and stderr names only paths below the folder.
- **RED test.** `platform/tests/test_station_owner.py::test_list_site_files_entry_vanishing_mid_listing_is_not_reported_as_missing_folder`. A fake site can return `SiteResult(1, b"f\t0\t1.0\ta\0", "find: '<dir>/x': No such file or directory")`.

### F6 (P3, CONFIRMED): `fetch_run_records` follows a run folder that is a symbolic link, although its header says it "never follows a link"

- **Evidence.** `F:43` checks the folder only with `launch.run_folder_ok`, which `launch.py:37-39` calls "a pure string check". `F:46` runs `cd <folder> && find -P .`, and `cd` follows a link. `F:26` reads `find -P <folder>/<rel>`, where `-P` covers only the last component. ### F8 (P3, CONFIRMED by measured call count): `fetch_run_records` makes one site call per distinct trace line, with no cap on files or total bytes

### F10 (P3, CONFIRMED; downgraded from P2): a read root that resolves to `/` is accepted, because `clean_root` refuses `/` only as text

- **Fix.** In `listing` (and wherever `real_roots` is used, as in `readlog.py:51-53`), refuse with "a read root leads to the top of the file system" when any real root is `/`.
- **RED test.** `platform/tests/test_station_owner.py::test_list_site_files_a_read_root_that_resolves_to_the_top_of_the_file_system_is_refused`.

## Refuted

- **#7 "the agent's second lock takes its read roots from the job, so one platform mistake opens both" (P2), refuted.** Taking roots from the environment is the documented design. PLATFORM.md:213 says "What may be listed: the environment's work folder and launch folder, the extra `readRoots` of its config, and the deployment's `storage_root`", and :731 says "the environment's read roots, which is the environment owner's to keep". Under owner binding (`jobs.py:113-123`; PLATFORM.md:725-730), the user who sets `readRoots` is the owner of the agent and of its site account, and MCP has no tool that edits an environment. The "second lock" in `R:1` is a second, separately written *judgement* of the values (shape, `..`, inside-roots, links), which `R:23-81` really is, separate from `compute_envs.py:205-222`. It does not claim a second source of data. Listing `/etc` after naming `/etc` as a read root is the intended behaviour. One part survives as a wording nit: `launch.py:211`, "The agent computes the same list from its own settings", is loose, because only `storage_root` comes from the agent's settings (`R:153`). It is folded into follow-up T9.
- **#11 "`modules` accept absolute paths and a leading `-`, so preflight runs modulefile code" (P3), refuted.** Only the environment owner sets `modules`. That owner is the agent's own site account, and there is no MCP tool for editing an environment or starting a preflight. A relative module name already loads any modulefile on `MODULEPATH`, including the user's own module folders, so an absolute path adds no capability that the actor lacks. A name such as `-f` reaches `module` as an option (`--force`), which selects no command. The measured facts are true (`_module_problem('/tmp/evil.lua') is None`), but nothing is gained across a boundary. `compute_envs.py:255`'s wording ("a module name is not a path") could still be made exact.
- **#13 "`list_site_files` checks links and lists in separate site calls (TOCTOU)" (P3), refuted.** The three calls are real (`H:565`, `H:575`, `H:586`). Winning the race needs write access on the site inside a read root, and the listing goes only to the owner of the environment and agent, whose own account could list that folder directly. Nobody learns anything they could not already learn. PLATFORM.md:712 accepts the same limit for links in shared read roots. As optional hardening, the one-call form `cd -P -- <real> && test "$(pwd -P)" = <real> && find . …` would also remove one round trip. That is not a finding.
