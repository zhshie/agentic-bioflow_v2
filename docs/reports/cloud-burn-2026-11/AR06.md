## Method

1. **Three lenses.** Three independent reviewers produced 20 candidates: (a) correctness and state (resource-limit merge, Kubernetes names, resume overrides, the deadline knob), (b) trust boundary (samplesheet and params paths, web cells, the reserved owner, URLs written into scripts) and (c) drift and cleanup (docstrings, dead code, imports, refusal wording).
2. **Refutation.** For each candidate I re-read the cited code at the sha and looked for a spec, doc or test that makes the behaviour intended. I re-ran every measured claim with my own scripts (`python3 -I`, `sys.path` set to the worktree's `platform/`, nothing written to the worktree). The default was "refuted" unless the evidence held. No Nextflow, cluster or cloud is available in this VM, so any step that needs one is marked as not run.
3. **Merging.** The 20 candidates (numbered #1–#20 in the order given) became 14 surviving findings. One candidate (#10) was refuted in full, and parts of eight more were refuted or corrected.

Candidate-to-finding map: F1 ← #7, #3; F2 ← #1, #15; F3 ← #2; F4 ← #8; F5 ← #9; F6 ← #4, #11, #16; F7 ← #5, #14; F8 ← #6; F9 ← #12; F10 ← #13; F11 ← #17; F12 ← #18; F13 ← #19; F14 ← #20. Refuted: #10 in full, plus parts of #1/#15, #3, #7, #8, #9, #13, #14 and #18 (see "Refuted").

## Surviving findings (most severe first)

### F1 (P1, CONFIRMED in Python): a samplesheet cell is judged only if its column name matches a heuristic or it starts with `/`, so a `file://` URI or a `../` path in an ordinary nf-core column (sarek `bai`/`crai`/`vcf`/`tbi`, ampliseq `forwardReads`) passes both locks and every cloud checker

- **Evidence.** `path_cells` (`L:337-343`) treats a cell as a path only if its column is in the caller's `path_columns`, matches `DEFAULT_PATH_COLUMN` (`L:62`: `fastq|fq|bam|cram|reads|file|path|reference[_N]` or `*_file`/`*_path`), or the cell starts with `/`. Every other cell is never judged. That covers both `_check_samplesheet` (`L:371-381`), which the agent re-runs in its rebuild (`L:1839`), and the platform's 116b `_confine` (`build:241`, the same helper). `path_columns` is optional and comes from the caller: MCP/HTTP `actions/__init__.py:1395,1418`, the CLI `--path-column`. Only a composed pipeline derives it from its own kinds (`abf_platform/pipeline_launch.py:141`). Nothing fills it from an nf-core `schema_input.json`.
- **What this breaks.** (a) The read-root invariant: rules:1-6 says "A path must be absolute ... free of '..', and inside one of the places the agent may read", and `L:209-211` says "The places a sample file may be". (b) specs/slurm-url-cells/plan.md:23: "`file:`, `s3://`, `gs://`, `az://` and any other scheme stay refused as today". TC-3 pins this for a path column (`platform/tests/test_slurm_url_cells.py:61-66`, `file:///etc/passwd` refused). (c) The 116b promise for HTTP callers (docs/PLATFORM.md:731, `build:193`). The head job runs `cd <run folder>` (`L:492`), so Nextflow resolves a relative cell against the run folder, and it opens `file://` URIs.
- **The cloud checkers have the same gap.** `_check_gcb_samplesheet` (`L:835`), `_check_aws_samplesheet` (`L:1013`), `_check_azure_samplesheet` (`L:1195`) and `_check_k8s_samplesheet` (`L:1389`) loop over the same `path_cells`. Their docstrings say "every cell that is read as a path is s3://<the bucket of workDir>/<object>" (`L:997`, likewise for the others). For Google Batch, AWS and Azure the head process runs on the platform host (`L:874`, `:1052`, `:1234`), so a relative cell there points at files of the platform host.
- **Reproduction (measured).** Slurm `render_bundle`, roots `['/work/u/abf']`. Refused: `fastq_1=/etc/shadow` (outside the roots), `fastq_1=../../../etc/shadow` (`..`), `fastq_1=file:///etc/shadow` (relative). Accepted: `bai=../../../etc/shadow`, `vcf=file:///home/other/x.vcf`, `forwardReads=../../x.fq.gz`, `r1=../../etc/x.fq`. With `path_columns=['bai']` the `bai` cell is refused. `DEFAULT_PATH_COLUMN` matches none of `bai crai vcf tbi table spring_1 forwardReads reverseReads fasta bed gtf peaks bigwig`. `render_aws_bundle`: `bai=../../../../etc/passwd` and `vcf=file:///etc/passwd` are accepted, while `bai=/etc/passwd` is refused ("must be s3://bkt/…"). Not run: Nextflow actually opening the file (there is no Nextflow here). That sarek and ampliseq read those columns as files is documented nf-core behaviour, not measured.
- **Severity.** P1 because the gate fails on routine nf-core column names, not on exotic shapes, and because both locks share the one helper. That is the "one mistake opens both" that rules:1 exists to prevent. For a deliberately hostile caller the gain is bounded (see Context above).
- **Proposed fix.** In `_check_samplesheet` and the four cloud checkers, judge every cell in every column, web cells excepted, for three shapes. Refuse a cell that (1) starts with `file:` (any case) or has a `scheme://` prefix other than http(s) (the shape of `build:197` `SCHEME`); (2) starts with `~`; or (3) has a `..` segment. Refuse with the existing sentences (`rules.path_reason`). A relative cell without `..` or `~` stays inside the run folder, which is inside the work folder (a read root), so the fix needs to go no further. That keeps values like `treated/control` in a `condition` column accepted. `_confine` gets this for free, because `render_bundle` runs before it (`build:180`).
- **Proposed RED test.** `platform/tests/test_launch_bundle.py::test_a_cell_in_any_column_with_a_file_scheme_tilde_or_dotdot_is_refused` (Slurm, parametrised over `bai`/`vcf`/`forwardReads`/`r1`), plus `platform/tests/test_aws_launch.py::test_a_relative_or_file_cell_outside_the_path_columns_is_refused` (and the same for Google Batch, Azure and Kubernetes).
- **HOT?** No (`launch.py` and the new tests only; `build.py` needs no change). The file is FORBIDDEN, so it is the maintainer's lane.
- **Suggested tier.** B (a safety-gate change; more refusals a user sees).

### F2 (P2, CONFIRMED): a `resourceLimits` line inside a `withName`/`withLabel`, a `profiles {}` block or a `/* … */` comment is read as the global limit and written as `process.resourceLimits` for every process of a cloud run

- **Evidence.** `_user_limits` (`L:713-739`) takes any non-`//` line containing `resourceLimits` (`L:716`). `_LIMITS_LINE` (`L:700`) allows leading whitespace and an optional `process.`, and the enclosing block is never looked at. `_resource_limits_line` (`L:748-766`) then writes the result as the one global `process.resourceLimits` into `gcb.config` (`L:787`), `aws.config` (`L:972`) and the Azure config (`L:1154`). Those files are read after `nextflow.config` (`L:770-771`, `L:806`), so the limit meant for one selector, or for one unselected profile, caps every process. The docstring promises the opposite (`L:714-715`): "Reads one narrow shape only …; anything else raises, because a guess could send a wrong config to a paid cloud." A second effect, reasoned from Nextflow's rule that a selector beats a generic `process` setting and not run: the user's selector-level limit stays in `nextflow.config`, so a selector limit above the environment's `maxvCpus`/`maxMemoryGB` lets that one process escape the platform's ceiling.
- **Tests.** No test has a scoped limit (`git grep resourceLimits platform/tests | grep -i 'withLabel\|withName\|profiles\|/\*'` → nothing). `test_aws_launch.py:1330` pins a bare top-level `resourceLimits = […]` as read, and `:1357` pins the one-line `process { resourceLimits { cpus = 4 } }` as refused.
- **Reproduction (measured).** `_resource_limits_line({'name':'x','maxvCpus':16,'maxMemoryGB':64,'nextflowConfig':T})` → `process.resourceLimits = [cpus: 2, memory: 4.GB]` for each `T` = `process {\n  withName: 'BIG' {\n    resourceLimits = [cpus: 2, memory: 4.GB]\n  }\n}\n`, the same with `withLabel: 'process_low'`, `profiles {\n  test {\n    process.resourceLimits = [...]\n  }\n}\n`, and `/*\nprocess.resourceLimits = [...]\n*/\n`. End to end, `render_aws_bundle` with `maxvCpus 64`, `maxMemoryGB 256` and the `withLabel` text → the last line of `aws.config` is `process.resourceLimits = [cpus: 2, memory: 4.GB]`.
- **Correction to the candidates' fix.** "Accept the unprefixed `resourceLimits =` form only inside `process {`" would break the pinned top-level bare form (`test_aws_launch.py:1330`). Keep that form.
- **Proposed fix.** In `_user_limits`, track brace depth and `/* … */` over the whole text, ignoring `//` comments. Accept a hit only at depth 0 (keeping today's prefixed and bare forms) or at depth 1 directly inside a top-level line that is exactly `process {`. Any other position raises `_limits_unreadable(ce)`.
- **Proposed RED test.** `platform/tests/test_aws_launch.py::test_cap_a_resource_limit_inside_a_selector_profile_or_block_comment_is_refused` (parametrised over the four texts above), plus one GCB and one Azure case through their bundles.
- **HOT?** No (FORBIDDEN path).
- **Suggested tier.** C (a bug fix inside the function's own stated contract; tests first).

### F3 (P2, CONFIRMED for the mapping; the delete is reasoned, not run): two different run names give the same Kubernetes Pod and Secret name, and a confirmed cancel of one run can delete the running head Pod of the other

- **Evidence.** `k8s_pod_name` (`L:1263-1266`) replaces `_` with `-`, cuts the result to 63 characters and strips trailing `-`. `RUN_NAME` (`L:33`) allows `_`, `-`, a trailing `-` and up to 64 characters. So `a_b` ≡ `a-b`, `ab-` ≡ `ab`, and any two 64-character names that share their first 60 characters collide. `k8s_secret_name` (`L:1269-1271`) inherits the collision. Run names are unique only as exact strings (`jobs.py:797-827`; `store.py:256-258`: "run_name is not unique"). The Pod and Secret carry no label (`k8s:99`, `k8s:114`). A launch refuses only while a Pod or Secret of that name exists (`k8s:162-168`). A cancel has no run-state check: `request_cancel` (`actions/__init__.py:1489-1501`) → `prepare_cancel` (`build:296-336`), which sets `pod_name = k8s_pod_name(row["run_name"])` (`build:335`). The agent checks only `pod != launch.k8s_pod_name(run)` (`k8s:204`) and then deletes (`k8s:218`).
- **Scenario.** Run `a_b` finishes and its Pod is cleaned away. Then `a-b` is launched in the same namespace (it may be another user's environment on the same namespace, since the namespace comes from the launch record, `build:334`). A later confirmed cancel of `a_b` finds `nf-a-b` present and deletes `a-b`'s head Pod. The listing also shows one Pod name for two runs (`abf_launch/cli.py:400`).
- **Reproduction (measured).** `k8s_pod_name('a_b') == k8s_pod_name('a-b') == 'nf-a-b'`; `k8s_secret_name('a_b') == k8s_secret_name('a-b')`; `k8s_pod_name('ab-') == k8s_pod_name('ab') == 'nf-ab'`; `k8s_pod_name('r'*60+'xxxx') == k8s_pod_name('r'*60+'yyyy')` (both names pass `RUN_NAME`). The delete itself needs a cluster and was not run.
- **Correction to the candidate's fix.** A hash suffix (`nf-<prefix>-<sha[:8]>`) changes the name for runs already launched. `build:335` recomputes the name at cancel time, so a cancel of an older run would then look for a Pod that never existed and answer "Pod 已不存在，視為已停止" while the real Pod keeps running.
- **Proposed fix.** In `render_k8s_bundle`, refuse a run name that contains `_`, ends in `-` or is longer than 60 characters. Every name accepted from then on maps to exactly `nf-<run>`, which is one-to-one, and existing runs keep their names. As defence in depth (in `k8s_launch.py`, FORBIDDEN): label the Pod and Secret `abf-run=<run>` and have the cancel check the label before the delete.
- **Proposed RED test.** `platform/tests/test_k8s_launch.py::test_a_run_name_whose_pod_name_is_not_one_to_one_is_refused` (`a_b`, `ab-`, 61–64 characters), and `::test_distinct_accepted_run_names_never_share_a_head_pod_name`.
- **HOT?** No for the fix (`launch.py`, `k8s_launch.py`: FORBIDDEN). `build.py:335` needs no change.
- **Suggested tier.** B (new refusals of run names a user sees on Kubernetes).

### F4 (P2, CONFIRMED): the agent's second lock never judges a params value against the read roots; over HTTP the platform's `_confine` is the only lock

- **Evidence.** `_check_params` (`L:385-407`) checks names, types and control characters only. The rebuild in `run_launch` (`L:1838-1847`) and `run_resume` (`L:2019-2021`) therefore accepts any path in params. The only params path check is the platform's `_confine` (`build:252-269`, through `_param_path`, `build:211-228`), which runs only when `area is not None` (`build:183`), i.e. for HTTP callers. The agent re-resolves only the entries the platform recorded (`_check_upload_paths`, `L:1780-1804`), so it cannot notice a value the platform failed to judge. rules:1 calls the agent's allow-list "a second lock on purpose … so one mistake cannot open both", and specs/116b-owner-gaps/plan.md:33 makes "Bob's `params` pointing at Alice's file" a red test.
- **Correction to the candidate.** "For terminal/stdio callers none" is documented, not a defect: docs/PLATFORM.md:737 and specs/116b-owner-gaps/plan.md:16 say "The terminal and stdio are unchanged". The surviving defect is the missing second lock over HTTP.
- **Reproduction (measured).** `render_bundle(..., params=P)` accepts `{'fasta': '/etc/shadow'}`, `{'igenomes_base': '/home/other/refs'}`, `{'fasta': '../../../etc/shadow'}` and `{'fasta': 'file:///etc/shadow'}`, while `fastq_1=/etc/shadow` in the samplesheet is refused.
- **Proposed fix.** Give `_check_params` the roots. When the bundle carries `upload_paths` (the mark of an HTTP launch, `build:183-184`), refuse in the agent a string value that starts with `/`, `~` or `file:`, or has a `..` segment, unless `rules.path_problem` is None and `rules.inside(rules.normalize(v), roots)`. This mirrors the absolute and `..` branches of `_param_path`. Keying on `upload_paths` keeps the terminal unchanged as documented, at the cost of trusting one platform-made key. Extending the check to the terminal changes PLATFORM.md:737 and needs the maintainer's ruling.
- **Proposed RED test.** `platform/tests/test_station_launch.py::test_an_http_launch_param_path_outside_the_read_roots_is_refused_by_the_agent` (a job whose bundle carries `upload_paths` with no entries and `params.fasta=/etc/shadow`, while the platform side is bypassed).
- **HOT?** No for the agent change (FORBIDDEN path). Yes if extended to the terminal (`docs/PLATFORM.md`).
- **Suggested tier.** B for HTTP-only; A for the terminal too.

### F7 (P3, CONFIRMED): `ABF_STATION_MIN_REMAINING=nan` or a negative value turns the deadline guard off

- **Evidence.** `_min_remaining` (`L:1683-1687`) accepts any `float()`. `_left(...) < nan` is always False, and `< -5` is False for any non-negative time left, so neither the precheck (`L:1874`) nor the last check before `sbatch` (`L:1898`) refuses. The cloud launchers use the same helper (per the candidate: `gcb_launch.py:164`, `aws_launch.py:80`, `azure_launch.py:99`, `k8s_launch.py:148`, `clean.py:125`). The knob is the operator's, hence P3.
- **Correction to #14.** "'inf' behaves similarly" is wrong. `inf` makes every check refuse (it fails closed): measured `0.0 < inf` → True.

- **Proposed fix.** `return v if math.isfinite(v) and v >= 0 else MIN_REMAINING`.
- **Proposed RED test.** `platform/tests/test_station_launch.py::test_a_non_finite_or_negative_min_remaining_falls_back_to_the_default`.
- **HOT?** No (FORBIDDEN path).
- **Suggested tier.** C.

### F8 (P3, CONFIRMED): an `extra_config` of only spaces or tabs counts as an edit, so a plain resume becomes an edited one

- **Evidence.** `_normalize_overrides` tests `extra.strip("\n")` (`L:1537`). `_check_extra_config` skips lines that are blank after `strip(" \t")` (`L:1479-1481`), so `'   \n'` passes and is kept as `changes['extra_config']`. `render_resume` then switches to the edited form (`L:1579-1587`): `params-N.yaml`, a whitespace-only `extra-N.config` and a different `head-N.sh`. `L:1603` says a resume without changes keeps the bundle and hash it always had. The platform's `edits_of` uses the same test (`build:537`), so both sides agree today. A fix on one side only would make the agent's rebuild refuse every such resume (`L:2036`).

- **Proposed fix.** Use `extra.strip()` in both `L:1537` and `build:537`, in the same change.
- **Proposed RED test.** `platform/tests/test_resume_render.py::test_whitespace_only_extra_config_is_the_plain_resume`, plus a platform-side case in `platform/tests/test_resume_edit_params_platform.py`.

- **Suggested tier.** C.

### F10 (P3, PLAUSIBLE): samplesheet cells may contain LF, so one checked row is written as a multi-line CSV record

- **Evidence.** `_bad_char` (`L:97-102`) rejects NUL, ESC, CR and bidi characters only, so `_check_text` on a cell (`L:365`) lets `\n` through. The platform's own reader produces such cells from a quoted CSV field (`build:43-55`). `_csv_text` (`L:470-473`) writes a valid RFC 4180 record across two physical lines. A reader that splits on lines would see an extra row whose cells were never judged; with the cell `x\nevil,/home/other/secret.fq,` that row has an absolute path in `fastq_1`.

## Refuted

- **#10 in full: "parameters can load arbitrary Nextflow config (custom_config_base), which defeats the closed-set extra_config gate".** Three reasons. (1) The launcher already chooses the code that runs: any `owner/name` at an exact version is accepted (`L:322-328`, docs/PLATFORM.md:137), so a config-loading parameter adds no capability, on a first launch or a resume. (2) The closed set protects by order. PLATFORM.md:648: "`-c extra-<N>.config` comes after the platform's own `nextflow.config`, so the later file wins". A config pulled in by `includeConfig "${params.custom_config_base}/…"` is included from the pipeline's own `nextflow.config`, which Nextflow reads before the `-c` files on the last line of `head.sh` (`L:526`), so it cannot overrule `OVERWRITE_BLOCK` by assignment. (3) The docstring at `L:1463-1464` describes what an `extra_config` text may hold, and that holds. Whether arbitrary pipelines are meant for HTTP callers is follow-up T8 (tier A), not a defect of this gate.
- **Part of #7: "a multi-user caller can read files outside the read roots"** as the sole basis for P1. The mechanism holds (F1), but a hostile caller can already run a pipeline of their own choosing (see Context). F1 keeps P1 for the broken gate on routine inputs, not for a new capability.
- **Part of #3: severity P2 and "relative only".** Merged into F1: the same root cause, with `file://` added and the cloud checkers included.
- **Part of #8: "for terminal/stdio callers none".** That is documented: docs/PLATFORM.md:737 and specs/116b-owner-gaps/plan.md:16 say the terminal and stdio are unchanged. F4 is narrowed to the missing agent lock over HTTP.
- **Part of #9: "No test covers the web-cell credential refusal".** `platform/tests/test_slurm_url_cells.py:84-90` (TC-5) does. The pattern gaps themselves are the same as AR03 F3/F4.
- **Part of #1/#15: the fix "accept the unprefixed `resourceLimits =` form only inside `process {`".** It would break `test_aws_launch.py:1330`, which pins the top-level bare form. F2's fix keeps it.
- **Part of #2: the hash-suffix fix.** It changes the Pod name of runs already launched, so a cancel of those runs (`build:335` recomputes the name) would miss the running Pod and report it stopped. F3 proposes refusing non-injective names instead.
- **Part of #14: "'inf' behaves similarly".** `inf` fails closed (every check refuses); only `nan` and negative values disable the guard (F7).
- **Part of #13: any display concern.** The confirmation screen escapes the newline (`build:835-840`, `terminal.esc` measured). Only the line-splitting-reader concern remains, as PLAUSIBLE (F10).
- **Part of #18: "_tower … and its five callers".** There are four (`L:571`, `:871`, `:1049`, `:1231`).
