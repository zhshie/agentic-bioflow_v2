### AR11-01 · P1 · A channel whose only record is a map gets `[[id: …]]` instead of the map, and a map record that is not meta is given a made-up `[id: row.sample]`

*Candidate C1. Latent until 017e: composed launch is Python-only today.*

**Evidence**
- `pipeline_launch.py:80-81` turns every `map` record into `[id: row.sample]`. Then `:102-108` emits the value itself only when there is one part **and no meta** (`len(parts) == 1 and not has_meta`). Every other case is written `[ %s ]`. This is what `specs/017d-launch-composed/plan.md:66` prescribes, so the code follows the plan. The plan's premise ("map = meta, always first in a tuple") is false for these modules.
- A scan of the committed snapshot found 13 input channels whose only record is `type: map`:
  - `bigslice/downloaddb` 0, `cellranger/multi` 0, `fq/generate` 0, `fusioncatcher/build` 0, `fusionreport/download` 0 and `ncbigenomedownload` 0 are `meta`;
  - `jupyternotebook` 1, `quarto/notebook` 1, `quarto/prerender` 1, `quartonotebook` 1 and `rmarkdownnotebook` 1 are `parameters`;
  - `blobtk/plot` 3 is `extra_args`;
  - `vcfanno` 3 is `resources`.
- Their `main.nf` declarations are all plain `val meta`, `val(meta)`, `val parameters` or `val extra_args`, with one exception: `vcfanno` declares `path resources`. None is a `tuple`.
- `fq/generate` declares `val meta` and uses `def prefix = task.ext.prefix ?: "${meta.id}"` and `tuple val(meta), path("*.fastq.gz"), emit: fastq` (committed sources, module `fq/generate`).
- Groovy 4.0.21 run on this review:

  ```
  def meta = [[id: 's1']]
  meta.id          -> [s1]   (java.util.ArrayList)
  "${meta.id}"     -> "[s1]"
  meta.single_end  -> [null], truthy
  ```

  The plain map's `single_end` is null, which is falsy. So the output files are named `[s1]_R1.fastq.gz`, and the list-shaped `meta` travels downstream. There, any `meta.single_end ? … : …` takes the single-end branch: the wrong result, not an error.
- The non-meta maps get `[[id: row.sample]]` as their notebook parameters or extra args. That is content nobody typed. `vcfanno`'s `path resources` gets a list holding a map, which Nextflow refuses at run time.
- `validate` passes all of these (`OPEN_INPUT` warnings only).

**Reproduction** (run)
- `normalize({'nodes':[{'id':'g','module':'fq_generate'}],'edges':[]})` gives `[]`, and `validate(...)['ok']` is `True`.
- `build_project(c, 'demo', 1, ['sample'])` produces this `main.nf` line:

  ```
  ch_g_in0 = ch_rows.map { row -> [ [id: row.sample] ] }
  ```

  It is followed by `FQ_GENERATE(ch_g_in0)`.

**Fix**
- In `build_project`, emit the value itself for any one-part channel (`elif len(parts) == 1:`). Keep `[ … ]` for two or more parts.
- Accept a `map` record only as the first record of a channel and only when its name starts with `meta`. Any other `map` record (`parameters`, `extra_args`, `resources`) is a `ProjectError` with `UNSUPPORTED_MODULE`: "this input cannot come from a samplesheet; wire it or use another module".
- Amend `specs/017d-launch-composed/plan.md:66` to match.
- The scratch probe of the one-line change kept all 266 related tests green.

**RED test**: `platform/tests/test_pipeline_launch_map_records.py`, new file:
- `test_a_meta_only_channel_is_the_map_itself`: `fq_generate` from the real snapshot; expect `row -> [id: row.sample] }`;
- `test_a_map_record_that_is_not_meta_is_refused`: `jupyternotebook` input 1; expect `ProjectError` with code `UNSUPPORTED_MODULE`.

HOT: no. `pipeline_launch.py` is not HOT; the test is a new file. Tier: **B**. It changes generated code and a plan line.

### AR11-02 · P2 · Whether an open input is a path is decided from meta.yml, not from the module's `path()` qualifier, so 4 string-typed records skip the samplesheet path gate and Nextflow still stages them

*Candidate C6, downgraded from P1. Latent until 017e. The same person can already do more through AR11-03.*

**Evidence**
- `build_project` decides path-ness only from the catalogue `type`:
  - `_FORMS`/`_PATHS` (`pipeline_launch.py:32-34`);
  - a `string` record becomes the bare `row.<name>` (`:90`);
  - `path_columns` keeps only `file`/`directory` kinds (`:141`).
- `validate.py:13` maps `string` to `val`, so validation agrees.
- The station judges a cell as a path only when its column is in `path_columns`, its column matches `DEFAULT_PATH_COLUMN`, or the cell starts with `/` (`abf_station/launch.py:62`, `:337-343`). The HTTP confinement walks the same `path_cells` (`abf_launch/build.py:241`).
- A scan of the snapshot (every supported module whose `input:` block could be parsed) found 6 records whose meta.yml type is scalar while `main.nf` declares `path(...)`:
  - `samshee` 1 `file_schema_validator` (string);
  - `demuxem` 0 `input_raw_gene_bc_matrices_h5` (string);
  - `demuxem` 0 `input_hto_csv_file` (string). Its name ends in `_file`, so `DEFAULT_PATH_COLUMN` catches it;
  - `ganon/buildcustom` 1 `input_tsv` (string);
  - `plotsr` 2 `genomes` (string);
  - `concoct/extractfastabins` 0 `csv` (boolean). It becomes `.toBoolean()` and fails at run time, so it is no bypass.

  So 4 records are ungated.
- Nextflow's `TaskInputResolver.normalizeToPath` (nextflow master, `modules/nextflow/src/main/groovy/nextflow/processor/TaskInputResolver.groovy:171-195`, read from the copy a reviewer fetched to `/tmp/cb/scan/`) runs `obj.toString().trim()`. It accepts a string that starts with `/` or has any URL protocol, and stages it.

**Reproduction** (run)
- `samshee` gives `normalize` `[]` and `validate` ok `True`.
- `build_project(..., ['sample','samplesheet','file_schema_validator'])` gives `path_columns == ['samplesheet']`, and the `main.nf` line is:

  ```
  ch_s_in1 = ch_rows.map { row -> row.file_schema_validator }
  ```
- Two rows with `file:///srv/u/bob/secret.json` and ` /srv/u/bob/secret.json` (leading space) in that column:
  - `path_cells` returns only the two `samplesheet` cells;
  - `_check_samplesheet(rows, ['samplesheet'], ['/srv/u'])` accepts both rows unjudged.

**Why P2 and not P1**
- The composed launch has no surface yet.
- The person who would craft such a cell is the launching person. AR11-03 shows they can already run any shell command as the site account through `ext.args`, and nf-core launches allow the same through string params (`abf_station/launch.py:402-404`).
- The gap matters on its own once AR11-03's posture is decided toward confinement, and before 017e opens composed launch over HTTP. There, `docs/PLATFORM.md:731` promises that every path cell is judged.

**Fix**
- At snapshot time, record each input record's `main.nf` qualifier: parse the `input:` block in `module_sources.build_snapshot` or a catalogue pass.
- In `build_project`, treat a record declared `path`/`file` as a path column whatever its meta.yml type. Alternatively, mark a module whose type and qualifier disagree as unsupported (5 modules today).
- Defence in depth, for the maintainer (`abf_station` is FORBIDDEN): `path_cells` should judge `cell.strip()`, and treat any cell with a non-http(s) scheme (`file:`, `s3:`, `ftp:`) as a path. Nextflow trims and accepts any protocol.

**RED test**:
- `platform/tests/test_pipeline_launch_path_records.py::test_a_string_record_declared_path_in_main_nf_is_a_path_column_or_refused` (samshee, real snapshot), new file;
- station side, maintainer: `test_path_cells_judges_trimmed_and_scheme_cells`.

HOT: no for the platform half. The station half is FORBIDDEN. Tier: **B** for the platform half, **A** for the station half (gate change).

### AR11-03 · P2 · `ext.args*`/`ext.prefix` values are run by bash on the compute node as the site account, and the docstring of `pipeline_launch` says nothing a person typed reaches the Groovy

*Candidates C7 and C15, merged. This is a posture decision, reported as a FINDING per RULES §2 (A-tier). Latent until 017e.*

**Evidence**
- `_KEY` admits `ext.args`, `ext.args2`…`9` and `ext.prefix` (`compose.py:23`).
- `_bad_value` refuses only non-strings, values over 1000 characters and Cc/Zl/Zp characters (`:40-48`).
- `_quote` escapes for a Groovy single-quoted string only (`:250-255`), and the value is written as `ext.args = '…'` (`:337`).
- The plan's threat model is Groovy interpolation alone: `specs/017b-compose/plan.md:77` ("…`$` → `\$`（防止 Groovy 插值）…") and `:267`.
- nf-core modules interpolate the value into the task's bash script. The committed `fastqc/main.nf` has `def args = task.ext.args ?: ''`, `${args} \\`, `def prefix = task.ext.prefix ?: "${meta.id}"` and `touch ${prefix}.html`.
- Groovy 4.0.21 run on this review:
  - `ConfigSlurper` parses `ext.args = '--quiet \$(cat /etc/passwd > leak.txt)'` to the string `--quiet $(cat /etc/passwd > leak.txt)`;
  - interpolating that into the `fastqc` script gives the line `--quiet $(cat /etc/passwd > leak.txt) \`. Bash runs the command substitution.
  - `ext.prefix = '../../x'` makes `touch ../../x.html` write outside the task directory.
- The module docstring `pipeline_launch.py:8` says: "Nothing a person typed is ever put into the Groovy." That is literally false:
  - `build_project` includes `render`'s `nextflow.config` with the person's `ext.*` values (`:59`, `:129-130`);
  - node ids and the name, typed and checked by `_ID`/`_NAME`, are in `main.nf`.
- Context that keeps this at P2: nf-core launches already accept any string param value (`abf_station/launch.py:402-404`), and nf-core pipelines conventionally pass `extra_*_args` params into `ext.args`. That second part is general nf-core practice and was not re-measured here. So "the launching person can run shell as the site account" is not new with compose. It is an unrecorded property of the platform, and it makes the samplesheet confinement (116b, `docs/PLATFORM.md:731`) bypassable by the launching person.

**Reproduction** (run)
- `normalize` of `{'ext.args': '--quiet $(cat /etc/passwd > leak.txt)', 'ext.prefix': '../../x'}` on `fastqc` gives `[]`.
- `render` writes `ext.args = '--quiet \$(cat /etc/passwd > leak.txt)'` and `ext.prefix = '../../x'`.
- A Nextflow run is not possible here. The Groovy steps above are.

**Fix**: the maintainer decides the posture (A).
- (a) Confine `ext.*`. Split with `shlex`, and require every token to match a conservative charset, for example `^[-A-Za-z0-9_.=,:+/@%]+$`: no `$`, backtick, `;`, `|`, `&`, `<`, `>`, `(`, `)` or quotes. Restrict `ext.prefix` to `^[A-Za-z0-9_.-]{1,64}$`, with no `/` and no leading `.`. If the 116b confinement is meant to hold, the nf-core params need the same.
- (b) Record that a launching person's parameters are their own shell on the site account, and that path confinement guards mistakes, not a hostile launcher.
- Either way, reword `pipeline_launch.py:8`: the person's `ext.*` values go into `nextflow.config` only as escaped one-line single-quoted strings, and nothing else they type goes into `main.nf` beyond checked ids and the name.

**RED test** (option a):
- `platform/tests/test_compose_param_values.py::test_normalize_refuses_shell_metacharacters_in_ext_args`;
- `::test_normalize_refuses_slash_or_dotdot_in_ext_prefix`.

There is no test for the docstring.

HOT: no (`compose.py`, `pipeline_launch.py`). Tier: **A** for the posture, **C** for the docstring.

### AR11-04 · P2 · `render` does not re-check a stored graph against the catalogue: after a snapshot update, export writes the old sha into `modules.json` with the new commit's files, and edges to vanished channels are dropped or left dangling

*Candidates C2 and C10, merged. `render_pipeline` and `export_pipeline` are Python-only today.*

**Evidence**
- `render`'s docstring says "a graph that does not fit the catalogue … is a ValueError (the checks run twice on purpose)" (`compose.py:259-261`).
- What it checks: that each module is found and the `_ID` (`:268-271`), the params (`:272-275`), edge endpoints and the output's `_IDENT` form (`:278-280`), and cycles (`:281-283`).
- What it does not check:
  - the node `sha` against `data['sha']`;
  - whether an edge's output is a real output of the record;
  - whether an edge's input number is a real input.
- Arguments come only from the current record's inputs (`:308-311`), so an edge into an input the record no longer has is silently left out. An edge from an output that no longer exists is written as `X.out.<gone>`.
- `git_sha` is the stored node sha (`:325`). `specs/017b-compose/plan.md:75` assumes that equals the snapshot's sha, and `:49` says old shas are not supported in this version.
- `export_pipeline` takes the module files from `module_sources.load(data=data)` (`actions/pipelines.py:253`). That is checked against the current catalogue, not against the graph's sha. Validation never blocks export (`:240-242`).
- After the maintainer updates both snapshot files to a commit B, every stored version (nodes at A) therefore exports a zip whose `modules.json` names A and whose files are B. That breaks the invariant `module_sources.py:98-99` states.
- The launch is safe only because `prepare` re-runs `validate` first (`pipeline_launch.py:163-165`), which reports `GRAPH_STALE`.

**Reproduction** (run)
- `create_pipeline` of fastqc→multiqc under the committed catalogue.
- `d2`/`s2` are copies with sha `'f'*40`; `s2`'s fastqc `main.nf` is prefixed with `// NEW COMMIT`.
- Results:
  - `export_pipeline(db, pid, data=d2, sources=s2)` gives `ok True` and `validation None`;
  - the zip's `modules.json` fastqc `git_sha` is `5ed90b42e784`, while `modules/nf-core/fastqc/main.nf` starts with `// NEW COMMIT`;
  - `render_pipeline(db, pid, data=d2)` gives `ok True`;
  - `normalize(graph, d2)` reports "node mq: the sha is not the catalogue snapshot's sha".
- Hand-made canonical graphs:
  - with an extra edge `qc.zip → mq input 9`, `render` gives `MULTIQC(FASTQC.out.zip)` and the edge silently vanishes;
  - with the edge changed to `qc.no_such_out`, `render` gives `MULTIQC(FASTQC.out.no_such_out)`, which `normalize` refuses.

**Fix**
- At the top of `compose.render`, run `_, problems = normalize(canonical, data)` and raise `ValueError` on any problem. That covers the sha, the channels and cycles, and the ad-hoc checks at `:268-283` can then go.
- `render_pipeline`, `export_pipeline` and `build_project` already turn the `ValueError` into "save a corrected version".
- The scratch probe of the narrower sha-only check kept all 266 related tests green.
- Consequence to decide with the fix: after a snapshot update, every old version must be re-saved before it can be rendered or exported. That is consistent with plan `:49`, but it is user-visible.

**RED test**:
- `platform/tests/test_compose.py::test_render_refuses_a_graph_that_no_longer_fits_the_catalogue` (sha, input 9, missing output);
- `platform/tests/test_pipeline_export.py::test_export_refuses_a_version_pinned_to_another_catalogue_commit`.

HOT: no. `compose.py`, `test_compose.py` and `test_pipeline_export.py` are not HOT, and `actions/pipelines.py` needs no change. Tier: **B**.

## Refuted (3)

- **C4. A graph can make `nextflow.config` longer than the bundle's 200,000-character per-file limit.**
  - The measurement holds. 200 fastqc nodes with 1000-character `ext.args` give 211,872 characters. Ten nodes with all ten keys full of `'` give 203,022, because escaping doubles them. `normalize`, `validate` and `build_project` accept both, and `_check_project` refuses with `超過 200000 個字元`.
  - There is no defect beyond the wording. The refusal comes inside the same `prepare` call (`render_bundle` runs in `build.prepare_launch`), before any question is asked. It names the file and the limit.
  - `validate` is not a launchability check by design: an unsupported module is also found only at launch (`pipeline_launch.py:62-70`).
  - It is reachable only with crafted, extreme values.
- **C9. `get_pipeline` accepts the version `1.0`.**
  - The code path is true: `1.0 in [1]`, then `render`/`export` answer "save a corrected version" (measured).
  - No shipped surface delivers a float. The MCP `get_pipeline` and `get_validation` declare `version: int | None` (`mcp_server.py:165`, `:172`), and pydantic coerces `1.0` to `1` and refuses `1.5` (measured with `TypeAdapter(int|None)`).
  - `render_pipeline`, `export_pipeline` and `validate_pipeline` have no CLI, web or MCP caller.
  - Only a Python caller passing a float reaches it, and the call fails closed.
- **C16. `pipeline_validations.graph_sha256` is a dead column.**
  - It is written and never read (`git grep` confirms).
  - The column is specified by `specs/017c-validate/plan.md:72-84` and pinned by TC-063 and TC-064 (`platform/tests/test_pipelines_validation.py:79-81`).
  - Because versions are append-only (`actions/pipelines.py:36-39`), it is a harmless provenance record of the exact text that was checked. It is not a defect.
  - Removing it or giving it meaning is a spec change, not cleanup.
