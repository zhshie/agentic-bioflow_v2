## Method

1. **Three lenses.** Three independent reviewers produced 20 candidates (c1-c20 below, in the order given). Four of them (c6, c7, c12 and c20) are reviewers' own "refuted" entries; c12 and c20 hold 5 sub-items each. Their lenses were:
   - (a) state and lifetimes: queue states, deadlines, prune, reuse windows;
   - (b) trust and ownership: who may approve, cancel or forget what;
   - (c) promise vs code: docstrings, tool descriptions, docs, dead code.
2. **Refutation.** For each candidate I re-read the cited code at the sha and looked for a spec, doc or test that makes the behaviour intended. I re-ran every measured claim myself:
   - a fresh copy of `platform/` and `skills/` from the worktree in my own scratch directory;
   - a probe file of ten pytest cases on the repo's own `human_harness.World`, run with `/tmp/cb/venv/bin/python -I -m pytest` (mcp 2.3.0, pytest 9.1.1);
   - two stand-alone `python -I` scripts: the built server's tool count and byte budget, and the forget of void resume requests.

   I did not take the reviewers' probe outputs on trust. Where I could not run a case, the default was "refuted".
3. **Merge.** Duplicates were merged:
   - c4, c11 and c13 → F6;
   - c5, c16 and c12(1) → F10;
   - c7 and c14 → F3;
   - c3 and c20(2) → F5.

Result: **11 findings survive** (2 P1, 2 P2, 7 P3). Severities moved: c3 P2→P3, c13 P2→P3, c15 P2→P3. Everything else is listed under "Refuted" with the reason.

## Findings

### F1 (P1) A cancel job that misses its 90 s deadline stays `queued`/`claimed` forever. Every later cancel is told "queued as job N" for a job that can never run, and forget is refused for good.

- **Where.**
  - `confirm:253-266`, with the state filter at `confirm:262`.
  - `confirm:389-390` (forget_content's live-job check).
  - Callers: `actions:1497-1499` (MCP `cancel`, and the web's `/act/cancel` through `web:651`).
  - The same root cause hits a launch job at `actions:1620` (forget_check, R15).
- **Evidence.**
  - `find_cancel` matches `j.state IN ('queued', 'claimed')` from the state column alone (`confirm:262`). Its docstring promises that "after the job is done, failed, refused or expired a new cancel asks again" (`confirm:254-255`).
  - Nothing moves an overdue unclaimed job out of `queued`:
    - `claim` hands out only `deadline_at > now` (`jobs:962-963`);
    - `_expire` (`jobs:1290-1297`) runs only from `wait_for_result` (`jobs:1319`), and the MCP/web cancel never waits (`actions:1305-1310`);
    - a late answer turns a `claimed` job `expired` (`jobs:1253-1255`), but an unclaimed job never gets an answer;
    - the prune deletes only rows with `finished_at` set (`jobs:156`).
  - `DEADLINE_SECONDS['cancel_run']` is 90 (`jobs:31`), so 90 s with the agent unreachable is enough.
  - The rest of the code already lets the clock decide: `jobs.launch_job` says so in so many words (`jobs:779`, `jobs:789`).
  - `forget_content` uses the same raw-state test (`confirm:389`). Every forget entry refuses for good, the terminal's included, because `abf_cli:315` → `actions.forget` → `confirm.forget_content`.
  - The launch-job twin: `forget_check` answers "still starting" from the raw `queued` state (`actions:1620`). Its own comment says a launch that "ended without ever reaching the index (refused, failed, expired) may be forgotten" (`actions:1621-1622`).
- **Reproduction** (my probe on `World`, runnable):
  - Setup: `w.hand_over(by=ann)`; ann's MCP cancel with a form yes gives `sent: True`, job 3. Then `UPDATE jobs SET deadline_at = now-1 WHERE kind='cancel_run'`.
  - `jobs.claim(...)` → `None`.
  - A second MCP cancel → `{'ok': True, 'sent': True, 'state': 'queued', 'job_id': 3, 'message': '已交給代理排隊（工作編號 3）…'}`.
  - `confirm.forget_content(db, 'run-one', dry_run=True)` → `JobRefused: 該次分析仍有工作在排隊或進行中，無法刪除`.
  - After a prune dated one year later, job 3 is still `queued`.
  - Launch twin (probe C1b): a form launch whose job's deadline is a day past. `jobs.launch_job` says `unknown`, but `actions.forget_check(..., caller=ann)` → `('refused', '這個 run 還在準備中，不能刪除 (the run is still starting)')`.
- **Impact.** The person is told the cancel is queued, the run keeps using SU on the site, and no entry asks them again. The run's content can never be forgotten (keep-submissions).
- **Fix.** One notion of a live job: `state IN ('queued','claimed') AND deadline_at > now`.
  - `find_cancel` takes a `clock` and adds `AND j.deadline_at > ?`.
  - `forget_content` (`confirm:389`) and `forget_check` R15 (`actions:1620`) count a job as live only while its deadline is ahead.
  - Alternatively, mark overdue jobs `expired` in the same transaction (`UPDATE jobs SET state='expired', finished_at=? WHERE state IN ('queued','claimed') AND deadline_at <= ?`). The column then means what `launch_job` already assumes.
  - A late answer to a `claimed` job is still applied as expired (`jobs:1253-1256`), so nothing is lost.
- **RED test:** `platform/tests/test_confirm_live_jobs.py::test_a_cancel_job_past_its_deadline_is_not_reused_and_does_not_block_forget`, plus `::test_a_launch_job_never_claimed_and_past_its_deadline_can_be_forgotten` (a new file).
- **HOT?** Yes: `confirm.py`, `actions/`. The test file is new, so not HOT.
- **Tier:** B (it changes what a gate counts as live).

### F2 (P1) Seven days after hand-over the owner can no longer cancel their own run from MCP or the web

- **Where.**
  - `confirm:238-250` (`launched_by`).
  - Caller: `actions:1495-1496` (MCP and `web:651`).
  - The prune: `jobs:30`, `jobs:155-156`.
- **Evidence.**
  - `launched_by` reaches the confirmation only through `launches → jobs (l.job_id) → confirmations (j.confirmation_id)` (`confirm:245-247`).
  - The launch job finishes at hand-over (its `finished_at` is set at `jobs:1260`). The first `_insert_job` more than 7 days later deletes it (`jobs:156`), and the platform inserts jobs routinely (listings, record fetches, preflights).
  - From then on `j` is NULL, `c` is NULL, and `launched_by` is False. `request_cancel` then refuses "not launched from this platform by you".
  - The fallback for exactly this case already exists: `jobs.launch_confirmation` ("F7: the launch job may be gone; its confirmation is still found", `jobs:662-674`). `forget_content` uses it (`confirm:400-403`); `launched_by` does not.
  - The ownership that `enqueue_confirmed` enforces for a cancel is `launches.user_id` (`jobs:924-928`), so only `launched_by` blocks.
- **Reproduction** (my probe on `World`, with the real prune):
  - Setup: ann launches through a form; `slurm_job_id` is set; the launch job is `done` with `finished_at = now - 8 d`.
  - `launched_by` → `True`.
  - Then a real `jobs._insert_job` (a preflight job) runs. Launch-job rows: 0. `launched_by` → `False`.
  - `jobs.launch_confirmation(con, launches_row)` → `('confirmed', caller is ann)`.
  - MCP cancel → `{'ok': False, 'sent': False, 'message': '未取消：run-one 不是你從這個平台送出的…(not launched from this platform by you)'}`.
- **Impact.** Any run that outlives 7 days cannot be cancelled by its owner from the web or MCP. Examples: a long sarek or rnaseq cohort, a cloud run, or a `lost` run that may still be on the cluster. Only the administrator's terminal `abf-platform cancel` is left.
- **Fix.** In `launched_by`, read the newest `launches` row and take `jobs.launch_confirmation(con, row)`, then apply the same `state == 'confirmed'` and caller test. Do not switch to `launches.user_id` alone: that would also change F7's question.
- **RED test:** `platform/tests/test_review_fixes_2.py::test_r1_the_owner_can_still_cancel_after_the_launch_job_is_pruned`.
- **HOT?** Yes: `confirm.py`. `test_review_fixes_2.py` is not HOT.
- **Tier:** B.

### F3 (P2) A repeated `launch`/`resume`/`relaunch` call made 10 minutes or more after the request was created answers `sent: false, "未送出 … 請換一個名稱"` while the confirmed job exists (merges c14 and c7)

- **Where.**
  - `confirm:179-197`: the bound `c.expires_at > ?` at `confirm:192`.
  - `confirm:214` (`find_attempt`).
  - `expires_at = created_at + PENDING_SECONDS` is set at `confirm:101`.
  - Callers: `actions:1456-1462`, `actions:1520-1522`.
- **Evidence.**
  - The lookup that turns a repeated call into "the job that exists" is bounded by the pending request's expiry. That expiry counts from when the request was made, not from the yes.
  - Its own docstring promises "the answer is then the job that exists, never a new question" (`confirm:183-184`).
  - The tool descriptions tell the model to call again after the person pressed send, with no time limit: `mcp_server:184-186`, `:204-205`, `:228-229`, `:239-240`. So does `PLATFORM.md:694` ("The repeated call finds the person's yes and returns the job number of the job that exists").
  - After the window, `_finish_launch` falls through to `check_run_name` (`actions:1459-1462`). It answers with `name_problem`'s words (`jobs:816-828`), prefixed by 未送出 ("not sent").
- **Reproduction** (my probe on `World`, the page path):
  - (a) Yes at created+590 (job deadline +890, so the job is live), repeated call at +605 → `{'ok': False, 'sent': False, 'message': '未送出：the run name run-one was used already (run 名稱已用過)：上一次送出還在等代理處理，請等它有結果再說，或換一個名稱'}`. Job 2 is `queued`.
  - (b) Yes early, run submitted (Slurm 4242). A repeated call at +300 → `sent True, job_id 2`. At +700 → `'未送出：…它已送出過，Slurm 工作編號是 4242；請換一個名稱'`.
- **Why the refutation in c7 does not hold.**
  - TC-E06 (`specs/009c-human-channel/test-case.md:155`) is about "已核准但還沒被拿去排的列" (a row approved but not yet taken into the queue).
  - Since `approve` writes the job in the same transaction (`confirm:156-171`), such a row cannot exist for ELICITED or PAGE. TC-E06's own case no longer occurs.
  - Its test (`platform/tests/test_human_channel.py:419-430`) asserts only `sent False` and one job.
  - The defect is not a second job (none is queued, as c7 says) but the false "not sent" plus "choose another name". An AI that follows `mcp_server:184-185` ("When the answer says sent is false, tell the person what to do") can steer the person into a second launch of the same analysis under a new name.
  - A person who comes back to the chat more than 10 minutes after the first call is an ordinary case.
- **Fix.**
  - For `include_spent=True` and for `find_attempt`, bound the lookup by the job (exists, not refused or expired) rather than by `c.expires_at`.
  - Or, when `check_run_name` refuses, look up this caller's confirmed ELICITED/PAGE launch with the same hash and return its job.
  - At minimum, state the window in the four tool descriptions and at `PLATFORM.md:694`.
  - TC-E06 needs the maintainer's revision, because its `sent is False` would change.
- **RED test:** `platform/tests/test_human_channel.py::test_tce06b_a_repeated_call_after_ten_minutes_names_the_job_that_exists`.
- **HOT?** Yes: `confirm.py`, `actions/`, `mcp_server.py`, `test_human_channel.py`, `PLATFORM.md`.
- **Tier:** B (a test-case contract changes).

### F4 (P2) Over HTTP, one user's forget clears another user's job copy for a reused run name, and the first user can then never forget their own confirmation

- **Where.**
  - `confirm:384-391` (the jobs are picked by run name only).
  - `confirm:404-405` (`only_user` filters confirmations only).
  - `confirm:413-415`.
  - Callers: `actions:1630`, `actions:1644`.
  - Name reuse: `jobs:797-828`. Ownership: `jobs:535-548`.
- **Evidence.**
  - `jobs_of_run` selects every launch/cancel/clean job whose `args_json` names the run, whoever confirmed it (`confirm:387-388`), and `todo_jobs` clears all of them (`confirm:391`, `:413-415`).
  - The docstring limits `only_user` to "the confirmations" (`confirm:377-378`). The job rows of other users are therefore written by this user's forget, and stamped `forgotten_by` with this user's id.
  - A run name becomes free again after the agent refused its launch (`jobs:803-805`, `:816-828`). Ownership is the newest `launches` row only (`jobs:543`), so the former owner gets `notfound` from `forget_check` (`actions:1617-1618`).
  - Their confirmed row is never purged (`confirm:79-81` purges only void and expired-pending rows), so it keeps the bundle with no HTTP way to delete it.
- **Reproduction** (my probe on `World`):
  - ann's form launch of `x`; the job is set `refused` (what the agent does).
  - bob's form launch of `x` → `sent True` (the name was free); hand over (Slurm 77).
  - `confirm.forget_content(db, 'x', forgotten_by=bob, only_user=bob)` → 3 rows cleared:
    - ann's job 2: `args_json.forgotten = True`, `forgotten_by = <bob's id>`;
    - ann's confirmation: bundle **kept**, state `confirmed`;
    - `actions.forget_check(..., 'x', caller=ann)` → `('notfound', …)`.
- **Bounds.** ann's job row would be pruned 7 days after it finished anyway (`jobs:156`). What lasts is ann's confirmed bundle, which only the terminal (caller None) can still clear.
- **Fix.**
  - With `only_user`, keep only jobs whose `confirmation_id` points to a confirmation with `caller_user_id = only_user`, and apply the queued/claimed refusal to that same set.
  - Decide how a former owner forgets their own rows: match by confirmation owner plus `_named`, not by the newest `launches` row.
- **RED test:** `platform/tests/test_keep_submissions.py::test_forget_over_http_leaves_another_users_rows_of_a_reused_run_name`.
- **HOT?** Yes: `confirm.py`, `actions/`, `test_keep_submissions.py`.
- **Tier:** B (keep-submissions ownership semantics).

### F5 (P3) A reused pending request can expire while the form for it is still open; the person's yes is then refused (c3, downgraded from P2)

- **Where.**
  - `confirm:25` (`REUSE_MIN_SECONDS = 60`), `confirm:82-86` (reuse), `confirm:146-148` (`approve` expires it).
  - `elicit:14` (`TIMEOUT_SECONDS = 600.0`), `elicit:38`.
  - Caller: `actions:1295-1305`.
- **Evidence.**
  - `_ask` calls `create_pending`, which returns an open request with as little as 61 s left (`confirm:82-86`).
  - It then holds the client's form for up to 600 s (`elicit:38`).
  - `approve` voids the request as `expired` once `now >= expires_at` (`confirm:146-148`).
  - Reuse into a form needs an earlier page request for the same content by the same caller, for example a first call from a client whose form is not trusted (`actions:1278-1281`), or a client without forms.
- **Reproduction** (my probe on `World`, through `actions.request_launch` with a stepping clock):
  - A first call with no person → `pending`.
  - At +500 a second call with a form-capable person who answers yes 150 s into the form → `{'ok': False, 'sent': False, 'message': '未送出：this request has expired (申請已逾時)。請從 AI 重新送出 …'}`. The request is void, `'expired (逾時)'`.
- **Why P3.** It fails closed (nothing wrong is queued) and the AI is told to ask again. The cost is a lost yes and a second form.
- **Fix.** In `_ask`, when a form will be shown, do not reuse a request that has less than `elicit.TIMEOUT_SECONDS` left. Or pass the time left to `says_yes` and use `min(TIMEOUT_SECONDS, left - margin)`.
- **RED test:** `platform/tests/test_human_channel.py::test_tcc_a_form_never_waits_past_the_request_it_answers`.
- **HOT?** Yes: `confirm.py`, `actions/`. `elicit.py` is not HOT.
- **Tier:** C.
