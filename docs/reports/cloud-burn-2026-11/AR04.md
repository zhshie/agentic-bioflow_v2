## Surviving findings (most severe first)

### F1 (P2): one unauthenticated address can block every connector's OAuth consent for everyone. Ten registrations × 20 `/authorize` calls fill `MAX_PENDING_TOTAL`, and the block can be renewed every 10 minutes all day

- **Evidence.**
  - `authorize()` refuses every client once the undecided requests across all clients reach `MAX_PENDING_TOTAL` = 200 (`oauth:241-245`, `oauth:69`).
  - The only per-address limit is `RegisterRateCap`, on `POST /register` only (`oauth:124`, wired at `web:1338`). `GET|POST /authorize` needs no login and has no rate limit.
  - `REGISTRATIONS_PER_HOUR` = 10 (`oauth:55`) × `MAX_PENDING_PER_CLIENT` = 20 (`oauth:68`) = 200, exactly the global cap.
  - A request lives `REQUEST_SECONDS` = 600 (`oauth:52`). Once expired, it is purged at the next `/authorize` (`oauth:241`), and the same 10 clients can send 200 more requests.
  - Those clients survive `UNUSED_CLIENT_SECONDS` = 86400 (`oauth:67`, `oauth:189-190`), and the address may register 10 more every hour anyway.
  - The refusal reaches the legitimate connector as `error=temporarily_unavailable` on its own redirect. That includes a claude.ai client registered long before the attack.
  - PLATFORM.md:750 documents both caps, but not that one stranger can fill the shared one.
- **Reproduction (measured).**
  - Command: `cd /tmp/cb/ar04/plat && PYTHONPATH=/tmp/cb/ar04/plat /tmp/cb/venv/bin/python -m pytest tests/test_ar04_probe.py -k block -s` (a test using `oauth_harness.Rig`).
  - Steps: register a legitimate client; from `203.0.113.9`, register 10 clients and send 20 `/authorize` requests for each; then authorize the legitimate client.
  - Output: `pending made by one address: 200 -> legit authorize: 302 https://claude.example/cb?error=temporarily_unavailable&error_description=too+many+requests+are+waiting+for+a+person%3B+try+again+later&state=st-1`.
- **Proposed fix.**
  - Count pending requests per requesting address as well. The least-HOT way is to let the middleware already wired at `web:1338` (`oauth.RegisterRateCap`, or a sibling class in `oauth.py` that reuses its slot) count `GET|POST /authorize` per address too. For example, at most `MAX_PENDING_PER_CLIENT` per address per `REQUEST_SECONDS`. `web.py` then needs no change, and the global cap stays only as a backstop.
  - Storing the address on `oauth_requests` would need a schema change in `store.py` (HOT).
  - Do **not** make the global cap evict the oldest request: the same address would then evict the legitimate one.
- **Proposed RED test.** `platform/tests/test_oauth_consent.py::test_one_address_cannot_fill_the_pending_requests_of_everyone`.
- **HOT?** No for `oauth.py`. Yes for the limit sentence at PLATFORM.md:750.
- **Suggested tier.** B (a new documented limit on `/authorize`).

### F2 (P2): `RegisterRateCap` never prunes its address table. Past 10000 lifetime addresses, every new address's first `/register` is a 429 (`Retry-After: 3600`) and its second is let through, and every refused address is added, so the table has no bound

- **Evidence.**
  - `oauth:127` drops old timestamps only for the address that is asking. Nothing ever deletes a key from `self.seen`.
  - `oauth:128` refuses an address not yet in `seen` once `len(self.seen) >= MAX_TRACKED_ADDRESSES` (10000, `oauth:56`). That count includes addresses whose hour ended long ago.
  - The refusal branch then stores `self.seen[address] = live` (`oauth:129`), with `live == []` for a new address. This has two effects:
    - (a) the next request from that address passes the `address not in self.seen` test and is served (`oauth:134-136`);
    - (b) `seen` grows by one entry for every refused address.
  - The docstring (`oauth:115-116`) promises that live windows are kept and new addresses are refused past the cap, which is a bound. Neither part holds.
  - The only test is the per-address one (`platform/tests/test_oauth.py:200`, `test_tcb05_one_address_cannot_register_without_end`). Nothing tests `MAX_TRACKED_ADDRESSES`.
- **Correction to candidates #1 and #8.** They say "every new address gets 429 until restart" and "permanently close /register". Measured, the second attempt from the same address is admitted. The real effects are:
  - every new connector's first registration gets a 429 with `Retry-After: 3600`, so a client that honours it waits an hour;
  - memory grows with the number of distinct addresses (an IPv6 /64 supplies them);
  - every registration that gets through also creates an `oauth_clients` row, kept for 24 h (`oauth:189-190`).
- **Reproduction (measured).**
  - `/tmp/cb/venv/bin/python -I /tmp/cb/ar04/rate.py` (`MAX_TRACKED_ADDRESSES` patched to 3, injected clock). Addresses a, b, c → 201. Clock +7200 s, so every window is dead. Then `d after windows expired: 429`, `d again: 201`. Five more new addresses give `tracked 9 cap 3`.
  - `/tmp/cb/ar04/t2.py`, clock +10 days: `tracked 3 after 10 days, new address -> 429`.
- **Proposed fix.**
  - Before the cap test, drop addresses whose newest timestamp is at least 3600 s old. To keep it amortised, sweep only when `len(seen) >= MAX_TRACKED_ADDRESSES`.
  - In the refusal branch, write `live` back only when the address was already tracked; never insert an unseen one.
- **Proposed RED test.** `platform/tests/test_oauth.py::test_register_rate_cap_forgets_dead_windows_and_never_tracks_a_refused_address`.
- **HOT?** No.
- **Suggested tier.** C (it makes the documented "10 per address per hour", PLATFORM.md:750, hold).

### F3 (P2): a general run token (`abf-platform token new`) can create a run with another user's launched run name, and every name-keyed view then picks the forged row

- **Evidence.**
  - `create()` checks `runName` only for a token bound to a name (`receiver:155-156`). `cmd_token_new` makes `run_name` None (`cli:85-87`).
  - The run id is `sha256(sessionId/runName)[:16]` (`common:18-20`). A different `sessionId` therefore makes a new row, not the 403 at `receiver:168-169`.
  - `begin` takes `started_at` from the client's `workflow.start` (`receiver:195-197`). `status.find_run` returns the row with the newest `started_at` for that name (`status:104-112`).
  - Ownership is by name: `jobs.owned_run_names` (`jobs:535-544`), used by `list_runs`, `get_run` and `read_task_log` (`actions:80-87`, `:103-105`, `:959-960`). So the owner of the name sees the forged row as their own run:
    - in `list_runs`;
    - in `read_task_log`, which takes the `workdir` from the forged `failed_tasks` and queues a task-log job to the owner's agent (`actions:959-968`);
    - in `offer_cleanup` and its backfill, whose `succeeded` check reads `find_run` (`actions:1186-1189`, `:1204-1232`).
  - PLATFORM.md:39 ("A token can only write to the runs it created") stays literally true. The point of that rule, that one token cannot affect another's run, does not hold.
- **Correction to candidate #9.**
  - The forged `complete` never calls `offer_cleanup`: `receiver:274-282` calls it only for name-bound tokens.
  - A cleanup reached through the backfill is still only a pending request that the owner must press 送出 on.
  - The forger reads nothing back, because the name is not in their `owned_run_names`.
  - Precondition: the forger must hold a general token, which the operator issues locally to people who run Nextflow themselves (PLATFORM.md:33-39).
- **Reproduction (measured).** `/tmp/cb/venv/bin/python -I /tmp/cb/ar04/t4.py` (Starlette `TestClient` on `receiver.create_app`):
  1. A name-bound token for `alice-rnaseq-1` creates and begins the real run.
  2. A general token posts `/trace/create` with the same `runName`: `200 {'workflowId': 'ffe211dd8c5ee9af'}`.
  3. It then sends `begin` with start 2099-01-01 (200) and `complete` with `success: false` (200).
  4. `status.find_run(idx, 'alice-rnaseq-1')` returns the forged row, with status `failed`.
- **Proposed fix.**
  - In `create()`, a token whose `run_name` is None gets a 403 for a `runName` that has a launch record in `platform.db` (read only, through the existing `jobs.latest_launch`) or that already has a row made by another token.
  - Longer term: key ownership on run id or token rather than on the bare name. That change is HOT (`actions/`).
- **Proposed RED test.** `platform/tests/test_receiver.py::test_a_general_token_cannot_create_a_run_named_like_a_launched_run`.
- **HOT?** No for `receiver.py` (it only calls an existing `jobs.py` reader). Yes for any change to ownership keying in `actions/`.
- **Suggested tier.** B (a general token is refused a name it could use before).

### F4 (P3): revoking an expired OAuth access token at `/revoke` revokes nothing, so the grant's refresh token stays usable for up to 30 days, contrary to `revoke_token`'s "access and refresh go together"

- **Evidence.**
  - The SDK's revocation handler calls `provider.revoke_token` only when `load_access_token` or `load_refresh_token` returns a token (`sdk/server/auth/handlers/revoke.py:61-78`).
  - `load_access_token` filters on `revoked_at IS NULL AND expires_at > now` (`oauth:396-397`). `load_refresh_token` matches only kind `oauth_refresh` (`oauth:361-363`).
  - An access token more than an hour old is therefore found by neither loader, and the promise at `oauth:403` is never reached.
  - RFC 7009 §2.1 makes revoking the refresh token from an access token optional ("MAY"), but this docstring promises it.
  - `load_access_token` has no other caller here. The MCP door uses `store.lookup_oauth_access` (`http_auth:120`). The SDK's `ProviderTokenVerifier` (`sdk/server/auth/provider.py:379-380`) is not wired: `mcp_server:313-318` and `web.py` pass no `token_verifier` and no `AuthSettings`.
- **Reproduction (measured).** Probe `test_revoking_an_expired_access_token_ends_the_grant`, in the same pytest file as F1:
  1. `tokens_for('ann')`;
  2. clock +3601 s;
  3. `POST /revoke` with the access token → 200;
  4. refresh with the refresh token → **200** (`assert 200 != 200` fails).
- **Proposed fix.** Let `load_access_token` return the `AccessToken` for any `oauth_access` row with this hash, expired or revoked, since its only caller is revocation. `revoke_token` then always reaches the grant.
- **Proposed RED test.** `platform/tests/test_oauth_tokens.py::test_revoking_an_expired_access_token_ends_its_refresh_token`.
- **HOT?** No.
- **Suggested tier.** C.

### F7 (P3): the consent page's `Content-Security-Policy` splices in the redirect netloc that the registrant chose, and `;`, `,` and quote characters are accepted in that host

- **Evidence.**
  - `consent_request` builds `redirect_origin` as `scheme://netloc` from the stored redirect (`oauth:266-268`).
  - `_page` pastes it into the CSP (`web:149-154`), called from `consent_page` (`web:1286`).
  - `redirect_is_allowed` (`oauth:83-93`) accepts whatever pydantic's `AnyUrl` keeps.
  - Spaces are refused and CR/LF are stripped. So only value-less directives (`sandbox`), or a second comma-separated policy, can be injected. Both only tighten the policy, because CSP policies intersect.
  - Not exploitable. It is hygiene: a response header is built from a stranger's input.
- **Reproduction (measured).** Each of these is kept by `TypeAdapter(AnyUrl)`, gets `redirect_is_allowed` → True, and gives the origin shown:

  | Redirect | Origin pasted into the CSP |
  |---|---|
  | `https://a;sandbox/cb` | `https://a;sandbox` |
  | `https://x,script-src/cb` | `https://x,script-src` |
  | `https://a'b/cb` | `https://a'b` |
  | `https://a"b/cb` | `https://a"b` |

  `https://a b/cb` is refused.
- **Proposed fix.** In `redirect_is_allowed`, refuse a hostname that is not an LDH name or an IP literal (for example `re.fullmatch(r"[a-z0-9.-]+", host)` or an `ipaddress` parse). Such a client is then refused at `/register`.
- **Proposed RED test.** `platform/tests/test_oauth_review.py::test_r3_a_redirect_host_with_csp_punctuation_is_refused`.
- **HOT?** No (`oauth.py`; `web.py` is unchanged).
- **Suggested tier.** C.

### F8 (P3): whether an expired consent link answers 410 "已逾時" or 404 "無此申請" depends on unrelated `/authorize` traffic, because two purge rules disagree

- **Evidence.**
  - `_forget_idle_clients` keeps expired requests for one more day (`oauth:191`). That retention is what lets `consent_request` report `expired` (`oauth:270`), so that `consent_gone` serves 410 (`web:1281-1285`) and `consent_decide` returns `expired` (`oauth:285-286`).
  - `authorize()` deletes every request with `expires_at <= now` (`oauth:241`) on any client's `/authorize`. After that:
    - `consent_request` returns None, so the page is a 404 (`web:1290-1292`);
    - `consent_decide` returns `unknown` (`oauth:281-282`);
    - the 409 "已處理" page for a request that was decided and has since expired disappears too.
  - PLATFORM.md:750 says "expired requests are purged at every `/authorize`", so `oauth:241` is the documented rule. With it, the 410 page and the one-day retention work only while nobody else authorizes.
  - The 410 test (`platform/tests/test_oauth_consent.py:214-216`) passes only because nothing authorizes in between.
- **Reproduction (measured).** Probe `test_expired_request_stays_expired_after_another_authorize`, in the same pytest file as F1:
  1. Start a request; clock +601 s → 410.
  2. One `rig.start(client_id=cid)`.
  3. The same consent GET and POST → `after another authorize: 404 404`.
- **Proposed fix.**
  - Make `oauth:241` use the retention at `oauth:191` (`expires_at < now - 86400`).
  - Add `AND expires_at > ?` to both pending counts at `oauth:242-244`; otherwise expired rows would count toward the caps.
  - Update the PLATFORM.md:750 phrase (HOT).
- **Proposed RED test.** `platform/tests/test_oauth_consent.py::test_an_expired_request_still_says_expired_after_another_authorize`.
- **HOT?** No for `oauth.py`. Yes for PLATFORM.md:750.
- **Suggested tier.** C.

## Refuted

- **#5, "two clocks disagree when `ABF_PLATFORM_CLOCK_OFFSET` is set".**
  - PLATFORM.md:904 defines the offset as a read-side shift: it "shifts the clock the query side uses … so the tests can look at a run 'three minutes later'; leave it unset. It also moves the clock by which a run token expires."
  - Writers stamping real time while readers look X seconds later is therefore the design. A token minted now is expired when looked at 3600 s later. The ended-run grace (`store:168`, 300 s) is closed when looked at more than 300 s later.
  - `platform/tests/test_oauth_mcp.py:89-91` relies on exactly this: it sets the offset to 3601 and expects a 401.
  - No reproduction was offered. Not a defect.
- **#12, "`form_allowed` vets only the redirect host".**
  - Exploiting it needs one of two things: a leak of query strings on claude.ai (an open redirect, a third-party Referer), or an attacker who already listens on the victim's own loopback port. Neither is reachable from this platform.
  - PLATFORM.md:750 already says the exact Claude Desktop redirect URIs will be pinned after the manual check (TESTING.md #117), "until then the rule above is all that is enforced".
  - This is a tracked open item, not a new defect. It is listed as optional hardening in T8.
- **#14 and #6.1, "two first hellos can both pass the owner check".**
  - `agents.register` is called only from the receiver's agent routes (`agents:158`, mounted at `receiver:297`).
  - It is called synchronously inside `async` handlers, on the single uvicorn process that `abf-platform serve` starts (`cli:43`, no workers). Two hellos cannot interleave inside it.
  - A second receiver process on the same `platform.db` is not a documented setup. Upheld as refuted.
- **#6.2, "a job claimed just before the agent disconnects is lost".**
  - The code involved is in `jobs.py`, outside the unit.
  - A claimed job that gets no result ends as `expired` through `jobs._expire` (`jobs:1290-1297`) when the waiter's deadline passes.
  - Handing out at most once is the safe choice for confirmed launch jobs, where a re-offer could launch twice. Refuted for this unit.
- **#6.3 and #15(e), "agent and run tokens of a disabled user still work".** Nothing sets `users.disabled_at` at v3: a grep finds only `SELECT`s and `IS NULL` filters (for example `store:903`, `store:919`, `oauth:290`, `oauth:347`). Unreachable.
- **#6.4, "the `taskId:attempt` key splits if `attempt` is sent only sometimes".**
  - Speculative: no plugin is shown to send `attempt` for one message of a task and not for the next.
  - `receiver:99-101` records that nf-tower 1.17.5 may send no `attempt` at all, which is consistent within a run.
- **#6.5, "`is_remote` treats `::ffff:127.0.0.1` as remote".** That errs towards "remote". The flag only picks a warning text (`actions:1317`). Safe side.
- **#15(a), redirect parser differential.** None found. In F7's probe, `urlparse` and pydantic agree on the host for every punctuation case.
- **#15(b), `is_remote` trusts the Host header.** The flag only chooses the "this address only opens on the platform machine" text (`mcp_server:285-290` → `actions:1317-1321`). It gates nothing.
- **#15(c), `MAX_CLIENTS` counts only clients that exchanged a code.** Documented at PLATFORM.md:750 ("a client that never exchanged a code is forgotten after 24 hours").
- **#15(d), `/revoke` with another client's token.** The SDK revokes only when `token.client_id == client.client_id` (`sdk/server/auth/handlers/revoke.py:75`).
- **#15(f), PATs never expire.** By design (`store:766-767`).
- **#15(g), a PAT-opened session lending the form to an OAuth token.** The caller is built per request from that request's own token (`http_auth:137-139`). The session check compares user ids only (`http_auth:128-136`).
- **Part of #1 and #8.** "Until restart" and "no new connector can register" are wrong: the second attempt from a refused address is admitted (measured; see F2).
- **Part of #9.** "Feeds a clean_work request for the real run's work folder" is overstated. The forged `complete` never calls `offer_cleanup` (`receiver:274-282`), and a backfill offer is only a pending request that the owner confirms (see F3).
- **Part of #2/#7, the alternative fix "evict the oldest pending request".** Refuted as a fix: it lets the same address evict the legitimate request.
