## Method

Three reviewers each read the unit through a different lens and produced 21 candidate findings between them. This report is the refutation round. For each candidate:

- the cited code was re-read at the sha;
- the claim was reproduced with `python3 -I` scripts on throw-away `index.db`/`platform.db`/`tokens.db` files (the reviewers' scripts were re-run, and a new script was written where a claim was untested or disputed);
- the behaviour was checked against recorded decisions: `docs/CLOUD.md` limits, the cost-page plan rulings and TCs, and the aws-launch plan. A documented decision refutes a finding unless its premise is false.

Duplicates were merged. A claim whose evidence did not hold, or held only in part, was refuted or narrowed, and the reason is given in **Refuted**. Severity follows RULES §6:

- **P1**: a bug with wrong output under ordinary use.
- **P2**: a risk that needs a precondition, or is latent today.
- **P3**: cleanup or robustness.

Tiers:

- **A**: needs the maintainer's yes, because it modifies a recorded requirement or money policy.
- **B**: a user-visible fix the development lead merges.
- **C**: internal.

### AR08-01 · P1 · The NCHC SU card prices every run at the rates file's `default_site` (taiwania3), so with the shipped nano4 environment the card is a dash while each row shows its number

*Merged from candidates 4 and 14.*

**Evidence**
- `actions/__init__.py:182` sets `site = rates.get("default_site")` once, and `:192` passes it to `su.run_su` for every run in the card total.
- Each row goes through `_su_of_run` (`:210` → `:128`, `su.site_of_run`, `su.py:154-171`), which uses the environment's `suSite`.
- `configs/sites/su_rates.json` has `default_site: taiwania3` (partitions `ctest`, `ct56` …). The shipped nano4 template `configs/sites/nchc-nano4-ce.json:15` sets `"suSite": "nano4"`, whose partitions are `ngs*` and `big-mem*`, none of which exist under taiwania3.
- `docs/CLOUD.md:3` names nano4 as the Slurm site. So every month with a nano4 run shows the card as "—".
- Cost-page decision 10 (`specs/cost-page/plan.md:108`) chose `default_site` on the premise "目前只有 nano4 一個站台" (only one site, nano4). The data contradicts that premise: there are three sites, and the default is not nano4. The decision dates from 2026-10-25 (957f097b); nano4 was added on 2026-10-23 (683baa3e); `default_site` was set on 2026-10-18 (e762ea4c).
- `docs/PLATFORM.md:766` documents the same `default_site` rule.

**Reproduction** (`python3 -I`): a `slurm-platform` environment `nano4` with config `{suSite: nano4}`, and one succeeded run whose single task ran on queue `ngs7G` (4 cpus × 1 h).
- Card: `{'total': None, 'unknown_reasons': ['task T: 分區 ngs7G 沒有 SU 係數 (no SU factor for partition ngs7G)'], 'site': 'taiwania3'}`.
- Row: `('r1', 'nchc', 4.0, 0.0125)`.
- `su.site_of_run` returns `'nano4'`.

**Proposed fix**: work the card out per run with `su.site_of_run` (best: reuse the `_su_of_run` answer each row already computes; see AR08-02), and sum `usd_of` per run. Amend decision 10 and TC-073 (`test-case.md:111`, "`su.site` 等於 `default_site`"), and fix `docs/PLATFORM.md:766`.

**RED test**: `test_my_usage_su_card_uses_each_runs_own_su_site`

**HOT**: yes (`actions/`, `docs/PLATFORM.md`). **Tier**: A, because it amends a recorded plan decision and a confirmed TC.

### AR08-02 · P1 · The SU card adds partial sums: finished tasks of a running run, and a finished run with missing task rows, are counted as if complete. A running run with no rows yet blanks the card with a false reason

*Candidate 3, narrowed and strengthened.*

**Evidence**
- The card loop (`actions/__init__.py:188-198`) calls `su.run_su` for every HPC run. It does not apply the two checks `_su_of_run` applies to rows:
  - "not ended" (`:129-130`);
  - "fewer usage rows than succeeded tasks" (`:134-136`).
- The receiver writes a `task_usage` row as each task finishes (`receiver.py:104-115`). So a running run with some finished tasks gets a partial sum added to the total, and so does a finished run whose events were partly lost.
- A running run with no rows yet makes `run_su` return `NOT_STORED` (`su.py:176-177`). The card then says "the run record does not keep each task's cpus, realtime and partition", which is false: the run simply has not ended.
- The plan, the docs and the module all forbid a partial sum:
  - `specs/cost-page/plan.md:48`: "任何一個分析算不出 → None 並帶原因，不給部分和" (if any one analysis cannot be worked out, None with the reason, no partial sum);
  - `docs/PLATFORM.md:766`: "never a partial sum";
  - `su.py:191-192`.
- The rows on the same page say "unknown" for these runs.

**Reproduction** (`python3 -I`): three HPC runs on `ctest`.
- `done`: succeeded, 1 row, 4 SU.
- `going`: running, 1 finished row of 4 SU.
- `holey`: succeeded, `n_succeeded = 10`, 1 row.

`actions.my_usage(..., month='2026-10')` gives:
- card `total = 12.0`, `unknown_reasons = []`;
- rows: `holey` → None ("9 succeeded tasks have no usage record"), `going` → running, None, `done` → 4.0.

With `going` having no rows instead, the card is `None` with the `NOT_STORED` reason.

**Proposed fix**: build the card total from the `_su_of_run` result of each HPC run. Any unknown, including `RUN_NOT_ENDED`, makes the total None with that run's own reason, as plan.md:48 says. Then the card always equals the sum of its rows.

**RED tests**:
- `test_my_usage_su_card_is_unknown_not_partial_while_a_run_is_running`
- `test_my_usage_su_card_is_unknown_when_a_run_lacks_task_rows`

**HOT**: yes (`actions/`). **Tier**: B, because it makes the code match the plan; no requirement changes. If AR08-01 is done in the same change, the site part stays A.

### AR08-04 · P2 · The cloud cap counts runs still in flight as $0, so back-to-back launches each pass

*Merged from candidates 2 and 8.*

**Evidence**
- `month_used` (`cloud_cost.py:196-204`) adds nothing for a run whose price is None and only bumps `unknown_runs`.
- A run with no finished task has no `task_usage` rows (the receiver writes rows for COMPLETED/FAILED tasks only, `receiver.py:104-115`), so `run_tasks_cost` gives `NOT_STORED` (`:142-143`).
- A confirmed launch that the receiver has not seen yet has no `runs` row at all, so `status.list_runs` (`status.py:79-89`) does not list it.
- `cap_problem` (`:265-277`) compares `spent + this launch's estimate` with the cap. It is checked once, when the launch is requested (`actions/__init__.py:1448`, `:1463`), so every request sees the earlier runs at $0.
- `docs/CLOUD.md:36` says the rule is "已用 + 預估 > 上限" (used + estimate > cap), and :40-43 list the known limits. Neither mentions this parallel-launch gap.
- The gap is **latent today**: the shipped price list is empty (`data/cloud_rates.json` `regions: {}`; `docs/CLOUD.md:43`), so every estimate is None anyway. It becomes live as soon as prices are filled in.

**Reproduction** (`python3 -I`, rates with `n2-standard-4` at $0.20/h): bob, cap $5, a September basis run priced at $4. Three times in a row: `cap_problem(...)` returns `None`, then a launch and a running `runs` row with no task rows are added. After the third, `month_used(bob,'2026-10')` = `{'usd': 0.0, 'unknown_runs': 3}`.

A second probe: cap $10, estimate $8, five running runs, and the sixth `cap_problem` is still `None`. About $48 is committed against a $10 cap.

**Proposed fix**: in `cap_problem` only (not on the display), count every run of the month that has not ended, and every confirmed or approved Google Batch launch with no index run yet, at max(priced so far, its estimate). When anything is in flight and no estimate exists, refuse. Either way, write the rule into `docs/CLOUD.md`. A minimum interim step is to list the gap under "目前的限制" (current limits) in `docs/CLOUD.md`.

**RED test**: `test_runs_in_flight_count_against_the_cap_at_their_estimate` (in `platform/tests/test_cloud_cost.py`)

**HOT**: no (`cloud_cost.py`, `test_cloud_cost.py`, `docs/CLOUD.md`). **Tier**: A, because it changes what "已用" means in a money gate documented in `docs/CLOUD.md:36`. The docs-only interim step is B.

### AR08-05 · P2 · One unpriceable task removes the whole run from the cap, so its priced spend escapes the gate

*Candidate 9.*

**Evidence**
- `cost_of_tasks` is all-or-nothing (`cloud_cost.py:81`, `:116-122`).
- `run_tasks_cost` deliberately prices every COMPLETED and FAILED attempt (`:127`).
- The receiver stores `machine_type`, `price_model` and `realtime_ms` as NULL when the event lacks them (`receiver.py:35-37`, `:110-114`). A FAILED attempt that never got a VM is the plausible case.
- `month_used` then adds $0 for the run (`:201-202`), and `cap_problem` compares that $0 with the cap (`:272`).
- All-or-nothing is right for the display, which wants an honest "unknown". Inside the gate it fails open: the priced tasks are a known lower bound, and the gate throws them away.
- Latent today, for the same reason as AR08-04.

**Reproduction** (`python3 -I`): cap $10; one October run with a COMPLETED task of 100 h on `n2-standard-4` at $0.20/h ($20), plus one FAILED task with no machine type and no realtime. `month_used` = `{'usd': 0.0, 'unknown_runs': 1}`, and `cap_problem(...)` returns `None`.

**Proposed fix**: add a gate-only lower bound per run: the sum of the priceable tasks, plus the run's estimate when some tasks cannot be priced. Use that in `month_used` for `cap_problem`, and keep `cost_of_tasks`' all-or-nothing answer for the page.

**RED test**: `test_an_unpriceable_failed_attempt_does_not_hide_the_priced_spend_of_its_run_from_the_cap`

**HOT**: no. **Tier**: A, the same rule change as AR08-04; do both in one decision.

### AR08-07 · P2 · Month totals walk index rows but price by run name: two rows sharing a name price the newest row twice and drop the other

*Candidate 1, precondition narrowed.*

**Evidence**
- `_runs_of` and `month_used` iterate `status.list_runs(..., names=owned)`, which returns every row of each owned name (`status.py:79-89`). For each row they call `run_tasks_cost(index_path, r["name"])` (`cloud_cost.py:184`, `:200`).
- `run_tasks_cost` re-resolves the name with `status.find_run`, which takes the newest row (`status.py:104-115`), so the row in hand is discarded.
- The same shape appears in:
  - `su.month_total` (`su.py:195-199`);
  - the `my_usage` card loop (`actions/__init__.py:186-192`).
- A row id is `run_id(sessionId, name)` (`receiver.py:157`), so a second session with the same name gets its own row.
- Precondition:
  - Platform launches cannot collide: names are unique across users (`docs/PLATFORM.md:738`), run tokens are bound to one name (`jobs.py:981`, `receiver.py:132-141`, `:155`), and resume and relaunch get a new `-a<N>` name (`docs/PLATFORM.md:647`).
  - A second row needs an **unbound** token from `abf-platform token new` (`cli.py:85-91`, `docs/PLATFORM.md:34-38`). Only the host's administrator can make one. Its holder runs Nextflow outside the platform under a name a platform user already has.
- In that case the outside run is also attributed to the owner by name (board, `get_run`). That is a wider, pre-existing ownership-by-name property outside this unit.

**Reproduction** (`python3 -I`): alice launches `x` (10 h on n2-standard-4 = $2.00, row `id-a`), and a second row `id-b` named `x` holds 100 h ($20). `list_runs(names={'x'})` → `['id-b','id-a']`, and `month_used(alice,'2026-10')` → `{'usd': 40.0, 'unknown_runs': 0}`. Expected: $2.00, or at most $22.00.

**Proposed fix**: pass the listed row's id (`r["id"]`) to `run_tasks_cost` and `su.run_tasks` (a `run_id=` variant that skips `find_run`), so each row is priced once. Separately, decide whether rows whose `token_id` is not the platform-issued run token should count as the owner's at all.

**RED test**: `test_month_used_prices_each_listed_row_once_when_two_runs_share_a_name`

**HOT**: no for `cloud_cost.py` and `su.py`; yes for the `my_usage` half. **Tier**: B.

## Refuted

- **Candidate 12, item 1 (resume or relaunch bypasses the cloud cap).** `_request_attempt` does skip `_cloud_check`, but `_predecessor` refuses every Google Batch resume and relaunch (`abf_launch/build.py:452-453`, `GCB_NO_RESUME`). Nothing reaches Google Batch without the cap.
- **Candidate 12, item 2 (AWS/Azure launches skip the cap).** This is decided: `specs/aws-launch/plan.md:13` puts the estimate and cap (C-3) out of scope, and `cap_problem` returns None for other kinds by design (`cloud_cost.py:254-256`, `docs/CLOUD.md:3`). The real AWS defect is classification, which is AR08-03.
- **Candidate 12, item 3 (the gate reads env-default paths).** `_cloud_check` uses `store.default_*_path`, and the production servers build from the same defaults (`cli.py:30-38`, `:47-74`). The two paths cannot diverge in production.
- **Candidate 12, item 4 (an estimate of None lets a launch through).** Documented: `docs/CLOUD.md:19`, `:36` ("預估算不出來但還有剩就放行", an unknown estimate with room left is allowed).
- **Candidate 12, item 5 (cap lowered between request and approval).** Documented as a known limit: `docs/CLOUD.md:42`.
- **Candidate 12, item 6 (XSS or injection via `month`).** The month is validated by anchored regexes (`web_cost.py:16`, `:61`; `actions/__init__.py:165`, `:178`). `shift()` only emits `%04d-%02d`, every text goes through `web_board.esc`, and run ids are quoted (`web_board.py:328`).
- **Candidate 19 (`su.month_total` is dead in production) is not a new finding.** It is already reported in `docs/reports/sweep-2026-11.md:102-106`, with the same choice to wire it up or delete it. It is not wholly unused: TC-073 (`test-case.md:111`) compares `my_usage` with it. Deleting it needs that TC amended. The stale `docs/PLATFORM.md:766` wording is folded into AR08-01's fix.
- **Candidate 3, the part that says the dash itself is wrong, is refuted.** `plan.md:48` says that if any one run cannot be worked out, the card is None, so "—" while a run is running is the plan. What survives as AR08-02 is the false reason, and the partial sums, which the plan forbids and which the reviewer had not tested. They turned out to be the larger defect: the card shows 12.0 while its rows show 4.0.
- **Candidate 7 and candidate 11, the "infinite realtime from a bad trace" part, is refuted.** An infinite value cannot be stored. `json.loads` accepts `Infinity`, but the receiver's `_int` (`receiver.py:27-32`) calls `int(inf)`, which raises OverflowError, so the value never reaches `task_usage`. Only the negative and NaN-factor cases survive (AR08-12). The OverflowError itself is a receiver robustness note; see follow-up FU-8.
- **Candidate 1, the "anyone can post any name" claim, is narrowed.** Run tokens made by the platform are bound to one name (`jobs.py:981`, `receiver.py:132-141`, `:155`), and platform names are unique (`docs/PLATFORM.md:738`). Only an administrator-made unbound token (`cli.py:85-91`) can produce a same-name row. That is why AR08-07 is P2 with a stated precondition.
- **Candidate 6, the "breaks every Google Batch launch" claim, is narrowed.** `cost_of_tasks` is reached only through `run_tasks_cost` when a run has task rows (`cloud_cost.py:142-146`, the only caller). So only launches by users with a priced Google Batch run this month, or a succeeded run of the same pipeline, are affected.
- **Candidate 16's severity is lowered from P2 to P3.** It needs a damaged index (any `sqlite3.Error`), it is display only, and the gate fails closed on the same error.
- **Candidate 4's "no reproduction run" gap is closed.** It was reproduced (AR08-01) and merged with candidate 14.
