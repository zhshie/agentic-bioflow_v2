## 發現（共 3 項，皆為實際跑出來的）

### F1　samplesheet 的相對路徑只要欄名不在清單，就完全不受讀取範圍限制（中高）

- PR／commit：#260（`01e1f77`）改 `.match`→`.search`，#301（`9a8a425`）新增放行規則；清單本身沒有改，缺口在 `path_cells`。
- 位置：`platform/abf_station/launch.py:62`（`DEFAULT_PATH_COLUMN`）、`:341`（`path_cells`）、`:368`（`_check_samplesheet`）。
- 重現：`python3 -I docs/reports/audit-2026-11/01_samplesheet_relative_unlisted_column.py`
- 實際輸出：

```
fastq_1        refused   samplesheet 第 2 列第 2 欄（fastq_1）: 路徑 contains '..' (含 ..)
short_reads_1  ACCEPTED  cells judged as paths: []
long_reads     ACCEPTED  cells judged as paths: []
bai            ACCEPTED  cells judged as paths: []
input_reads    ACCEPTED  cells judged as paths: []
forward        ACCEPTED  cells judged as paths: []
```

- 應有輸出：同一個儲存格 `../../bob/secret_R1.fastq.gz` 不論放在哪一欄，都該被當成路徑檢查並拒絕（或至少相對路徑一律拒絕）。
- 影響：`path_cells` 只把「欄名符合清單」或「以 `/` 開頭」的格子當路徑；`short_reads_1`（nf-core/mag）、`long_reads`、`bai`、`crai`、`vcf` 等欄裡的相對路徑 `..` 不會被檢查。若 Nextflow 在 run 資料夾以相對路徑解析，就能讀到允許範圍之外的檔案。**這一段（Nextflow 實際怎麼解析）我沒有跑過**，所以嚴重度取決於站台上解析的位置。
- 備註：使用者可用 `path_columns` 手動指定，但預設路徑是「認得出才檢查」，對不認得的管線是 fail-open。

### F2　寫在局部範圍的 `resourceLimits` 會被升格成全域上限（中）

- PR／commit：#280（`0259726`）。
- 位置：`platform/abf_station/launch.py:700-745`（`_user_limits`、`_LIMITS_LINE`）、`:748`（`_resource_limits_line`）；寫入處 `:787`、`:972`、`:1154`。
- 重現：`python3 -I docs/reports/audit-2026-11/02_resource_limits_scope_hoist.py`
- 實際輸出（CE：`maxvCpus=64`、`maxMemoryGB=256`）：

```
global (control)   -> process.resourceLimits = [cpus: 2, memory: 256.GB]
inside withName    -> process.resourceLimits = [cpus: 2, memory: 4.GB]
inside a profile   -> process.resourceLimits = [cpus: 2, memory: 4.GB]
```

- 應有輸出：`withName: 'BIGJOB' { resourceLimits = [cpus: 2, memory: 4.GB] }` 只該限制那一個 process；`profiles { small { ... } }` 在沒選該 profile 時不該生效。平台應拒絕（「讀不懂」）或原樣保留，不該把它變成整個 run 的全域上限。
- 影響：`_LIMITS_LINE` 逐行比對、不看縮排與外層區塊，所以任何縮排區塊裡的那一行都被當成全域設定，再由平台附加的 `process.resourceLimits`（後讀，會整個蓋掉）寫成全域值。結果是整個 run 的每個 process 都被夾到 2 cpus／4 GB，大任務會變慢或記憶體不足。只在 CE 同時設了 `maxvCpus` 或 `maxMemoryGB` 且使用者的 nextflowConfig 有這種寫法時發生；不洩漏資料、不越權。

### F3　網址型憑證檢查漏掉「帳密寫在網址裡」與 GCS 簽章網址（低中）

- PR／commit：#301（`9a8a425`）。
- 位置：`platform/abf_station/launch.py:372-375`；啟發式清單在 `platform/abf_platform/compute_envs.py:120-129`（`_VALUE_PATTERNS`）。
- 重現：`python3 -I docs/reports/audit-2026-11/03_web_cell_credential_gate.py`
- 實際輸出：

```
refused   https://h.org/a.fq.gz?token=abc123
ACCEPTED  https://user:hunter2@h.org/a.fq.gz
refused   https://b.s3.amazonaws.com/a.fq.gz?X-Amz-Credential=AKIAIOSFODNN7EXAMP
ACCEPTED  https://storage.googleapis.com/b/a.fq.gz?X-Goog-Signature=0123456789ab
```

- 應有輸出：四筆都該 refused（程式碼的錯誤訊息承諾「網址看起來含有憑證，不送出」）。
- 影響：含 `user:password@host` 或 GCS `X-Goog-Signature` 的網址會被原樣寫進送到站台的 samplesheet 與 bundle。這是使用者自己貼的憑證寫進自己的檔案，沒有跨使用者外洩；缺口是「不送出憑證」這個承諾在這兩種寫法下不成立。
