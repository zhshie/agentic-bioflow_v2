# 雲端費用：預估、已用、每人每月上限

這份說明 Google Batch（`googlebatch-platform`）環境的費用怎麼算、上限怎麼設。nano4（Slurm）不受影響，完全不經過這裡。

## 一句話

平台會用 Google 公開的價目表，估一次雲端分析約花多少美元，加上你本月已經花的，如果會超過管理者替你設的每月上限，就在送出之前用白話拒絕。**金額一律是美元，不換算。**

## 算的是什麼，不算什麼

- **只含運算（虛擬機）費用。** 磁碟、網路出口、Cloud Storage 儲存都不算。
- 算法：每個 task 的實際執行時間（Nextflow 回報的 realtime）× 該機器型號每小時的價格。開機與關機的時間沒有算，所以數字會**略低於** Google 的帳單。所有金額都寫成「約」。
- 每個 task 用哪種機器、是不是 spot（Google 的可被收回的便宜機器），都是 Nextflow 回報的字串，平台只照它說的，不自己猜，也不用 CPU 數反推。

## 預估怎麼來

預估 = 取同一位使用者、同一個 pipeline、**最近一次成功**、跑在 Google Batch、而且算得出金額的那個 run，把它的運算費用當成這次的預估（那個 run 裡失敗重試的 task 也算，因為真的花了錢）。

**第一次跑某個 pipeline 沒有歷史**，預估就是「未知」，平台不會用資源上限去猜一個數字。後果要知道：上限只擋得住「本月已用滿」，**擋不住「這一次太貴」**；而且價目表填入之前，連「本月已用滿」也擋不住（見下方價目表一節）。所以請管理者替第一位使用者把上限設小一點，例如 5 美元。

## 上限怎麼設（只有管理者）

上限存在平台的 `tokens.db`，只有平台主機終端機上的兩條指令寫得進去，沒有任何網頁、MCP 工具或聊天指令能讀或改它：

```bash
abf-platform user add <名字> --lab <實驗室> --cloud-cap-usd 20   # 開帳號時一起設，單位美元
abf-platform user cloud-cap <名字> 25                           # 之後補設或調整，單位美元
```

- 數字要是 0 到 1,000,000 之間的美元數字；負數、文字、`nan`、`inf` 一律拒絕並說明，帳號與原來的上限都不變。
- **沒設上限就不能送到雲端**（安全預設）；程式裡沒有寫死任何預設值。上限 0 等於這個月不准送。
- 每個人各自一個上限；沒有實驗室共用、角色或群組上限。

## 拒絕的時候看到什麼

例如：「本月雲端費用上限 US$20.00，已用約 US$14.50，剩約 US$5.50；這次預估約 US$6.00，會超過。請找管理者調整上限，或下個月再送出」。判斷式是「已用 + 預估 > 上限」才拒絕，剛好等於上限放行；已用 ≥ 上限一律拒絕；預估算不出來但還有剩就放行。有 run 算不出金額時，已用會寫成「至少 US$X（另有 N 個 run 算不出來）」。

## 目前的限制

- **目前不會自動停止正在跑的雲端工作，只會擋下新的送出。** 要不要讓平台自己停掉超過上限的工作，是還沒裁決的問題，另開任務。
- 從網頁或 AI 送出到 Google Batch 時，平台在建立任何東西（確認、工作、紀錄）之前先查這個上限；確認畫面第二行寫這次的預估，或寫「無法預估」和原因。**例外：平台主機上管理者自己打的 `abf-launch` 終端機指令，以及沒有帳號的本機 stdio，不查上限**（它們是管理者的入口，沒有「這個人」可以套用上限）。這是一個已知的缺口：持有終端機的人可以用 `--user` 替任何帳號送出，繞過該帳號的上限；要補的話另開任務。
- 本人在確認頁按「送出」之前，確認有效期（約 600 秒）內如果管理者把上限調低，平台不會重新檢查：上限的把關點是「建立確認頁之前」，已經按了送出的那一次只是取回工作編號。這是已知限制。
- 價目表目前是空的，所以今天每一次預估都是「無法預估」，而且每個 run 的實際花費也算不出來，「本月已用」一律當 0 美元（有未計價的 run 時只會標「至少」）；因此上限今天只擋得住「沒設上限」「上限 0」，「本月已用滿」要等價目表填入後才會生效。
- 月份用**台北時間**切；Google 的帳單用**太平洋時間**切月，月初與月末兩邊最多差約半天。
- 實驗室在 Google 那邊設的帳單預算（台幣計）只是 Google 的事後提醒，**不是**平台的上限；兩者是兩層各自獨立的保護，平台程式裡沒有台幣，也沒有任何換算。

## 確認畫面長什麼樣

確認畫面第一行是標題，第二行是「費用：…由 Google 向實驗室的 Google Cloud 帳號收費」，第三行是費用預估，只有三種寫法，句尾都是同一句聲明（平台只擋下超過每月上限的新送出，不會自動停止已經在跑的工作；實際金額請看 Google 的帳單）：

1. 算得出：「費用預估：約 US$2.00（依你最近一次成功的同管線雲端 run <名字> 的實際運算時間推算；只含虛擬機運算費用，不含磁碟與網路；價目讀於 <日期>）。」
2. 算不出：「費用預估：無法預估（<第一個原因>）。」原因最多顯示 200 字；沒有原因時寫「原因不明」。
3. 這個入口沒有算預估（沒有帳號的本機入口）：「費用預估：無法預估（這個送出入口沒有算預估）。」

畫面上不顯示本月已用或剩多少；那三個數字只在拒絕的訊息裡。

## 價目表怎麼更新

價目表是資料，不是程式碼：`platform/abf_platform/data/cloud_rates.json`。

1. 打開 Google 的公開價目頁（Compute Engine 的 VM 價目、Spot VM 價目），**照頁面上的數字**填，不憑記憶。
2. 結構是「區域 → 機器型號 → `standard`／`spot`（美元／小時）」。
3. **每一筆（每個區域的每個機器型號）都必須有 `source`（`https://` 開頭的網址）與 `read_on`（讀頁面那天，`YYYY-MM-DD`）。** 缺任何一個，這一筆就當作不存在；`standard` 或 `spot` 只缺一個，就只缺那一個。查不到的機器型號不要列，沒有價目就是未知，不是 0。
4. 改完跑 `platform/tests/test_cloud_cost.py`：它會檢查每一筆的來源、日期、數字是否合理。

**目前出貨的價目表是空的**（`regions` 為空）：目前讀得到的 Spot 價無法核對、也沒有一般（on-demand）價，錯的價錢比沒有價錢更糟。所以在 `cloud-rates-fill`（之後用 Cloud Billing Catalog API 填入 us-central1、asia-east1 的 N2／E2 一般價與 Spot 價）完成前，所有雲端估費與「已用」都是未知（理由「尚未填入價目」）；上限今天只擋得住「沒設上限」「上限 0」，「已用滿」要等價目表填入後才會生效。上限已接進網頁與 AI 的送出流程（見上面「目前的限制」）。

## 資料從哪來

接收端（receiver）把每個完成 task 的機器型號（`machineType`）、計價模式（`priceModel`）與可用區（`cloudZone`）存進 `index.db` 的 `task_usage`；Nextflow 的 `google-batch` executor 實際會不會送這三個值，要由 `docs/TESTING.md` 的手動驗收第 2 步確認。task 沒有可用區時，退用該 run 的計算環境設定的 `location`。
