# Feature Specification: 本地模型評測（第 1.5 階段）

**Feature Branch**: `001-local-model-eval`

**Created**: 2026-09-29

**Status**: Draft

**Input**: User description: "第 1.5 階段本地模型實驗：在維護者的 48GB Mac 上，用一套固定、公開的題目，讓候選本地模型透過 Claude Code 各跑 20 次，以 Claude 為對照，回答『約 30B 的模型夠不夠用』，進而決定產品主機（Brain）的硬體與價格。見 `docs/ROADMAP.md`〈Local-model evaluation〉與 `docs/POSITIONING.md`〈模型與電腦〉。"

> 名詞見 `CONTEXT.md`。本規格給維護者（非工程師）看，所以用中文；編號（US、FR、SC）照 Spec Kit 慣例。

## 這個功能要回答的問題

產品要賣一台預裝好的主機（Brain）。模型要多大，決定主機多少錢：約 30B 的模型夠用，48–64GB 的機器就行；需要 120B 級，就要 128GB 級、價格約翻倍（`docs/POSITIONING.md`）。目前沒有任何公開測試量過本地模型做這類工作的正確率，所以要自己量。

這個功能**不改產品本身的任何行為**。它交付的是：一套固定題目、每題的正確答案、一個自動計分的方法，以及一份維護者能據以拍板的結果表。

## Clarifications

### Session 2026-09-29

- Q: 每題的正確答案由誰產生、誰確認？ → A: 官方資料（nf-core 測試資料、官方樣本表、已公開數值）優先直接採用；其餘由 Claude 起草、維護者逐題確認。
- Q: 診斷題怎麼判對錯？ → A: 模型從固定原因清單選一項並寫修法關鍵動作，機器比對；不用人工批改，也不用模型當評審。

## User Scenarios & Testing *(mandatory)*

### User Story 1 — 量一個候選模型，得到能拍板的答案（Priority: P1）

維護者在自己的 Mac 上選一個候選模型與一個推論引擎（跑模型的程式，例如 Ollama），下一個指令，讓整套題目每題各跑 20 次。跑完得到一張表：每題過了幾次、有沒有達到 18／20 的門檻，以及沒過的那幾次錯在哪裡。

**Why this priority**: 這是整個階段存在的理由。只要這一個故事做得到，就能開始量第一個模型；其他故事都是讓答案更可信。

**Independent Test**: 用任一個候選模型跑完整套題目，產出結果表，且表上每一格都能追回某一次作答的原始紀錄。

**Acceptance Scenarios**:

1. **Given** 題目、正確答案與候選模型都已就緒，**When** 維護者下指令開始評測，**Then** 每題各執行 20 次，結果表列出每題通過次數、是否達 18／20 門檻、整體結論。（正常）
2. **Given** 某題在 20 次內已經失敗 3 次，**When** 評測繼續進行，**Then** 該題停止重跑並標示「已確定未達門檻」，因為 18／20 已不可能達成，省下的時間用在其他題。（正常）
3. **Given** 一次作答的輸出格式不符（例如缺欄位、不是要求的格式），**When** 計分，**Then** 該次記為失敗，失敗原因寫明「格式不符」，而不是整個評測中斷。（例外）
4. **Given** 推論引擎在評測途中當掉或無回應，**When** 某次作答逾時，**Then** 該次記為「引擎失敗」，與「答錯」分開統計，評測繼續；引擎失敗次數過多時停下並明講是引擎問題。（例外）
5. **Given** 模型在作答中試圖送出分析（launch）或刪除檔案，**When** 該動作被攔下，**Then** 什麼都沒有真的被送出或刪除，該次記為失敗，失敗原因寫明「試圖執行不該執行的動作」。（例外）
6. **Given** 維護者想量 70B 以上、48GB 裝不下的模型，**When** 開始評測，**Then** 評測在開始前就說明記憶體不足、不支援，而不是跑到一半崩潰。（不在範圍）

---

### User Story 2 — 用 Claude 當對照組（Priority: P2）

同一套題目也讓 Claude 跑 20 次。這樣如果本地模型沒過，能分辨是「題目本身太難或正確答案有誤」還是「模型不夠強」。

**Why this priority**: 沒有對照組，本地模型的低分無法解讀；但先有 US1 才有東西可以對照。

**Independent Test**: 只跑 Claude 一個模型，得到與 US1 同格式的結果表。

**Acceptance Scenarios**:

1. **Given** 題目與正確答案已就緒，**When** 用 Claude 跑完整套題目，**Then** 得到與本地模型同格式、可並排比較的結果表。（正常）
2. **Given** Claude 在某題也未達 18／20，**When** 產出結果表，**Then** 該題被標示「對照組未過，題目或正確答案需要檢查」，該題不拿來判斷本地模型。（例外）
3. **Given** 評測的是 Claude，**When** 結果表產出，**Then** 表上註明「這組作答內容（題目、樣本表、錯誤訊息）已傳到 Anthropic」，本地模型組則註明「未離開本機」。（正常）

---

### User Story 3 — 分辨「引擎壞了」和「模型不行」（Priority: P2）

同一個模型分別用兩種推論引擎跑。已知 Ollama 與 Qwen3.6 的工具呼叫有未修的錯誤，只用一種引擎可能把引擎的毛病誤判成模型能力不足。

**Why this priority**: 這直接影響結論是否正確；錯把引擎問題當成模型問題，會多花一倍的硬體錢。

**Independent Test**: 同一個模型在兩種引擎各跑一次整套題目，結果表並排顯示兩者差異。

**Acceptance Scenarios**:

1. **Given** 同一模型在兩種引擎都跑完，**When** 產出結果表，**Then** 兩者並排，每題標出哪個引擎較好。（正常）
2. **Given** 某題在一種引擎通過、另一種未過，**When** 產出結論，**Then** 結論以較好的引擎為準，並註明另一個引擎的問題。（正常）
3. **Given** 某個引擎在這台機器上根本裝不起來或無法載入該模型，**When** 評測開始，**Then** 明講是哪一個引擎、哪一步失敗，只用另一個引擎的結果，不假裝兩個都測過。（例外）

---

### User Story 4 — 別人能重跑、能查證（Priority: P3）

題目與正確答案公開在本 repo，任何人拿同樣的模型與引擎重跑，能得到可比較的結果；每一次作答的原始紀錄保留在維護者自己的電腦，不進公開 repo。

**Why this priority**: 公開題目是產品定位的一部分（`docs/POSITIONING.md`〈護城河〉），但決定硬體不需要等它。

**Independent Test**: 在另一台電腦依照說明重跑任一題，得到同格式的結果。

**Acceptance Scenarios**:

1. **Given** 一份結果表，**When** 查閱任何一格，**Then** 能找到它來自哪次作答、哪個模型、哪個引擎與版本、哪天跑的。（正常）
2. **Given** 作答紀錄裡含維護者本機路徑或帳號資訊，**When** 準備公開的內容，**Then** 公開的只有題目、正確答案、計分方法與彙總結果，作答原始紀錄不會被提交到 repo。（例外）
3. **Given** 有人要求把評測做成產品功能讓實驗室成員使用，**When** 評估範圍，**Then** 說明本階段不交付任何產品功能。（不在範圍）

### Edge Cases

- 題目需要的公開測試資料下載失敗：評測開始前就檢查並停下，說明缺哪一份資料；不在半路才失敗。
- 模型一次作答超過設定的時間上限：記為「逾時」，與答錯、引擎失敗分開計。
- 同一題 20 次的結果完全一樣（模型輸出沒有隨機性）：照常計分，但結果表註明「20 次輸出相同」，因為這時重複 20 次沒有提供額外資訊。
- 正確答案本身被發現有誤：修正後，受影響的題目全部重跑，舊結果標示作廢，不混用。
- 上下文不足（題目加上 plugin 說明超過模型能讀的長度）：記為「上下文不足」，並回報實際需要多長。

## Requirements *(mandatory)*

### Functional Requirements

**題目與正確答案**

- **FR-001**: 題目集 MUST 固定為五類：①16S 擴增子：從實驗設計規格產生樣本表與參數 ②RNA-seq：同上 ③從一份預先埋好錯誤的失敗紀錄診斷原因與修法，全程不送出任何分析 ④DESeq2／phyloseq 統計數字 ⑤方法段文字，每一條引用都要查得到。
- **FR-002**: 每題 MUST 有一份事先定好的正確答案，存放於 repo，且在評測開始後不得更動；更動就視為新版本題目集。
- **FR-003**: 題目 MUST 只用公開測試資料，不用任何實驗室的真實資料。
- **FR-004**: 每題 MUST 要求模型以固定格式交出答案，使計分可以機械化完成，不需要人工閱讀判斷，也不用另一個模型當評審。診斷題（第③類）要求模型從一份固定的原因清單中選一個，並寫出修法的關鍵動作；機器比對所選原因與修法關鍵動作是否正確。

**執行**

- **FR-005**: 評測 MUST 透過與產品雛形相同的方式驅動模型——plugin 的指令、skill 與安全網照常載入——而不是直接把題目丟給模型。量的是「模型在這個工具裡做不做得到」。
- **FR-006**: 每題 MUST 預設執行 20 次；當失敗次數達到 3 次（18／20 已不可能），該題 MUST 停止重跑並標示「已確定未達門檻」。
- **FR-007**: 評測 MUST 支援在同一台機器上切換：候選模型、推論引擎、以及 Claude 對照組。
- **FR-008**: 評測過程中 MUST 不可能真的送出分析或刪除檔案；模型的此類嘗試 MUST 被攔下並記為失敗。
- **FR-009**: 評測開始前 MUST 檢查：模型能否放進記憶體、需要的測試資料是否都在、推論引擎是否可用；任一不符就在開始前停下並說明。
- **FR-010**: 本地模型的評測過程中，題目、作答與紀錄 MUST 不離開本機。

**計分與結果**

- **FR-011**: 每次作答 MUST 被歸入以下之一：通過、答錯、格式不符、逾時、引擎失敗、上下文不足、試圖執行禁止的動作。
- **FR-012**: 「管線設定正確」（第①②類）與「圖表數字與方法段正確」（第④⑤類）MUST 分開計分與呈現。
- **FR-013**: 結果表 MUST 列出每個「模型 × 引擎 × 題目」的通過次數、是否達 18／20、以及對照組結果，並給出一句結論：這個模型能做到哪一類為止。
- **FR-014**: 結果表的每一格 MUST 能追回產生它的作答原始紀錄、模型名稱與版本、引擎名稱與版本、執行日期。
- **FR-015**: 作答原始紀錄 MUST 存在維護者本機、不提交到 repo；repo 只收題目、正確答案、計分方法與彙總結果。
- **FR-016**: 如果對照組（Claude）在某題未達門檻，該題 MUST 被標示為需要檢查，且不用來判定本地模型。
- **FR-017**: 由 Claude 起草的正確答案 MUST 經維護者逐題確認後才能用於計分；未確認的題目不得進入評測。每份正確答案 MUST 註明來源是「官方」或「Claude 起草、維護者確認（日期）」。

### Key Entities

- **題目（Task）**：一類工作的一道具體題目，包含輸入（實驗設計規格、失敗紀錄或資料）、要求的答案格式、所屬類別（①–⑤）。
- **正確答案（Reference）**：每題的標準答案與判對規則；有版本。
- **候選組合（Candidate）**：模型＋量化方式＋推論引擎＋版本；Claude 對照組也是一種組合。
- **作答（Trial）**：某個組合對某題的一次執行，含原始紀錄與分類結果（FR-011）。
- **結果表（Scorecard）**：彙總所有作答，給出每題通過率與結論。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 維護者拿到結果表後，不需要其他資料，就能回答「約 30B 的模型夠不夠用、夠用到哪一類工作」，並據此選定 Brain 的記憶體等級。
- **SC-002**: 每個候選組合跑完整套題目（五類、每類 20 次，含提早停止）能在一個晚上內完成，不需要人守在旁邊。
- **SC-003**: Claude 對照組在每一類都達到 18／20；若有未達，該類題目在判定本地模型前先被修正。
- **SC-004**: 結果表上 100% 的格子都能追回原始作答紀錄。
- **SC-005**: 整個評測期間，實際送出的分析與刪除的檔案為 0。
- **SC-006**: 另一台電腦依公開說明重跑任一題，得到同格式、可並排比較的結果。

## Assumptions

- 評測在維護者的 Mac（M5 Pro、48GB）上執行；候選為 Qwen3.6-35B-A3B（4-bit）、Qwen3.6-27B（4-bit）、gpt-oss-20b（當下限），引擎為 Ollama 與 llama.cpp（`docs/ROADMAP.md`）。
- 模型能讀的長度至少設定為 64k，最好 128k（一次 16S 設定約需 39k，`docs/POSITIONING.md`）。
- 門檻是每題 20 次過 18 次（90%），2026-09-28 維護者決定。
- 正確答案的來源：能取自 nf-core 官方測試資料、官方測試樣本表或已公開數值的，直接採用；其餘由 Claude 起草，維護者逐題看過才生效（見 FR-017）。
- Claude 對照組使用維護者現有的 Claude Code 訂閱。
- 「一個晚上」以 10 小時計。
- 本階段不改 plugin 的任何行為；若評測發現 plugin 本身需要為小模型調整，另開新的 feature。

## Out of Scope

- 在 HPC 上真的跑管線；評測只檢查模型產生的設定與答案，不執行管線。
- 出貨任何模型、改用 Codex（那是第 2、5 階段）。
- 70B 以上、48GB 放不下的模型。
- 評測本地模型的速度或耗電（只記錄，不設門檻）。
- 把評測做成實驗室成員可用的產品功能。
- 採購硬體；本階段只產出決定硬體所需的資訊。
