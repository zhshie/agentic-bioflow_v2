## 請你判斷的三件事

1. **每條是不是你要的？** 重點看 TC-001 到 TC-006、TC-045、TC-048：沒有你按「確認刪除」，代理一條遠端指令都不送；按了之後只有 `work` 消失，`results`、`rawdata`、`analysis` 位元不變。
2. **有沒有漏掉的出錯情況？** 想像實驗室成員或壞資料會怎麼弄錯：路徑被竄改（TC-029 到 TC-044）、`work` 其實是捷徑（TC-051）、還有工作在這個資料夾裡跑（TC-054）、結果裡有指向 work 的捷徑（TC-053）、佇列問不到（TC-056）、逾時或未知失敗（TC-062、TC-063）。
3. **「不在範圍」對嗎？** 這次不做 Google Batch（TC-013）、不做刪整個 run／刪結果／旗標（TC-069）、不做批次或部分清（TC-070）、不用 `nextflow clean`（TC-071）、不重試（TC-072）、不改平台與其他代理檔案（TC-075、TC-076）、也沒有任何畫面或入口（建立申請在 f 片）。

## 我（撰寫者）不確定的地方

1. 樣板第 9 行的 `find results … | grep -q .`：若 `find` 本身出錯，會被當成「沒有連結」而往下 `rm -rf`（squeue 失敗則會停在碼 18）。這是你要的嗎？本合約沒有替它出題（計畫沒寫預期行為）。
2. 同一行的 `-lname '*/work/*'` 會把任何指向含 `/work/` 路徑的連結都當成指向 work（連指向 rawdata 的連結也算，當 workDir 在 `/work/…` 下時）。偏保守、不會誤刪，但可能讓某些 run 清不掉。要接受嗎？本合約只驗計畫的範例 12。
3. 路徑類拒絕的訊息用詞計畫沒規定；碼 20 的成功訊息也沒規定。我只斷言「拒絕＋白話非空＋沒送指令」與「done／cleaned 為 true／沒刪東西」。這樣夠嗎？
4. TC-023 假設測試能觀察到送去站台的逾時值；若假站台看不到，executor 應停手回報，不得改成只測字串。
5. 失敗／中止／失聯 run 不清理，是平台端（f 片）決定要不要建立申請；代理端只在叢集上看到「有工作還在這個資料夾」才擋。這樣分工對嗎？
6. 範例 15（擁有者不符）在假站台上要讓 `site_user` 與檔案實際擁有者不同，其餘成功案例要讓兩者相同；若做不到，請 executor 停手回報。
