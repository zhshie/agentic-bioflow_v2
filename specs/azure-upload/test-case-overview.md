## 請你判斷的三件事

1. **每條是不是你要的？** 特別看 TC-001／TC-007（Azure 的「上傳」打開、「清理」仍關）、TC-035～TC-039（上傳指令的形狀、金鑰只走環境變數、不進指令）、TC-059／TC-060／TC-062（核對雲端大小才刪暫存檔）、TC-079／TC-080（超過 2 GB 時給的 `az storage blob upload-batch` 指令與「在你自己的電腦上、用你自己的 Azure 登入」）、TC-087～TC-091（一份資料集不能混 `az://`、`gs://`、`s3://`、本機路徑）、TC-109／TC-110（沒有任何 MCP 上傳工具，也沒有新增使用者可見動作）。
2. **有沒有漏掉的出錯情況？** 想像實驗室成員會怎麼用錯它：傳到別人的前綴（TC-051、TC-092）、用別人的環境（TC-010、TC-094）、檔案太大（TC-055、TC-077）、平台主機沒裝 az（TC-070）、憑證檔不見（TC-065）、傳完核對大小不符（TC-059）、傳到一半檔案被換掉（TC-068）。
3. **「不在範圍」對嗎？** 這次不做：Blob 刪除與 azcopy、費用估算、Azure 環境的續跑與 `clean_work`、MCP 上傳工具、網頁按鈕、`list_site_files`、跨環境搬資料（Google 或 AWS 上傳的檔案搬到 Blob）、Azure SDK、教使用者怎麼登入 Azure。所以做完之後，Azure 環境其實還**沒有人能按得到上傳**，只是動作層、代理與文件備好了（網頁入口另案）。

## 我（撰寫者）不確定的地方

1. 計畫自承 `blob show` 的輸出形狀、`upload-batch` 的 `--destination-path`、只有 SAS 時 az 是否照環境變數運作，官方頁面都「查不到」。TC-048 釘計畫預設的 `blob show … --query properties.contentLength --output tsv`，TC-081 兩種目的地寫法都收。若執行者讀官方文件後發現要改（退到 `blob list` 或改目的地寫法），需先在帳本記一行並回報 developer-agent 重開 TC-048、TC-062～TC-064，這樣可以嗎？
2. `blob show` 失敗（逾時、讀不到數字）時，TC-062～TC-064 依 aws-upload 的 A4：結果算成功、訊息說「沒能核對雲端大小」、暫存檔保留。這是你要的嗎，還是 Azure 版寧可標失敗？
3. 上傳不經人工二次確認（裁決 18：檔案主人在網頁按「上傳」就排入），目前沒有網頁按鈕所以尚無入口（TC-110、TC-116）。等網頁入口接上時要不要再加確認？
4. 計畫「不做」寫「不做續跑」，我解讀成兩件：Azure 環境的 run 續跑仍被拒（TC-008），以及失敗的上傳不自動重試、不續傳（沒有任何 TC 要求重試，也沒有程式會重試）。若你指的只有前者，也已涵蓋。
5. 計畫幾處舊句已被後面的裁決取代：（a）範圍與 AZU-STATIC-01 的「cloud_store.py／datasets.py 全文小寫後無 azure」被裁決 13／20 改成「原文不得有小寫 azure」；（b）作法 4 的 argv「恰為」形狀被裁決 14／19 補上 `--auth-mode key`（有帳號金鑰時）與只有 SAS 時的規則；（c）AZU-AGT-06 的「訊息可含路徑」被裁決 21 作廢。本合約一律照後者出題；請 executor 不要照舊句寫測試。
6. 裁決 13 准許改 `test_aws_upload.py` 約 705 行的字表（把 `"azure"` 換成 `"import azure"`、`"from azure"`）。這是既有測試的有意修改，閱卷時會確認只改這一處、693 與 713 行的匯入禁令沒動、PR 說明有「以前／以後／理由」。
7. TC-012（泛用排工作入口不能排 `put_upload`）與 TC-120～TC-124 是由 backend 專長守則與憲法導出，計畫沒有逐字寫；預期行為取自既有 Google／AWS 版（`enqueue_put_upload` 是唯一入口），沒有發明新行為。
