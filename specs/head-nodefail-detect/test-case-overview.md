## 我（撰寫者）不確定的地方

1. 「log 裡找不到完成行」的完成行，指 Nextflow log 的哪一句？現有程式碼已用 `Execution complete -- Goodbye`；真站台 log 的比對列為 nano4 手動驗收（計畫裁決 N），不擋合併。
2. TC-001 的 `status` 為 `failed`，是指 `get_run` 回傳的 `status` 欄位值變成 `failed`（計畫「失敗先行測試」寫「`status` 為 Failed」，裁決 N 也確認）。
3. 發送紀錄的 `slurm_job_id` 在非 Slurm 後端可能是 pid、容器名稱或雲端工作編號；純數字的 pid 若被拿去問 Slurm，理論上可能對到別人的 Slurm 工作。計畫沒寫要不要限制只對 Slurm 後端問，合約沒有為此加案例。
4. 裁決 Q1 取代 P3 後，「事實是 RUNNING／PENDING／COMPLETED 時要不要重問」計畫沒寫，不出 TC（TC-040 只針對終結壞狀態事實）。
5. 裁決 P2 只談先前事實是終結壞狀態的情況；先前事實是 RUNNING、新一筆是 None 時如何顯示，計畫沒寫，不出 TC。
6. 裁決 P4 沒給夾具細節；TC-034 的夾具（目前 log 有完成行、輪替檔缺啟動標記且無完成行、排程器回 NODE_FAIL）是依「寧可問排程器」推得，若你想的情境不同請告知。
7. TC-024、TC-025 是手動案例，需要執行者在 `docs/TESTING.md` 手動段新增對應步驟（已在 ledger 記為完成，閱卷時查）。
8. 裁決 Q1 寫「不提供 resume／relaunch」，但裁決 N 與 v3 既有測試釘住「lost 的 run 仍提供 relaunch」。合約的解讀：覆蓋層撤掉後，`actions` 與沒有事實的普通 lost run 完全相同（不含 resume；relaunch 是否出現就照 v3 原樣），不得為了這條而改掉 v3 對 lost 的行為。若你其實要連 lost 的 relaunch 也拿掉，請告知，那會動到被釘住的既有測試。
9. 裁決 Q1 說事實年齡超過 6 小時「就不再問」，沒說之後畫面是否仍顯示 Failed；TC-041 只驗不再排抓取，不驗畫面。
10. 裁決 Q2 沒指定測試放哪個檔、「所有 Ended 欄位」包含哪些畫面；TC-038／039 只要求每個顯示 Ended 的地方都用與失敗通知相同的備用時間，由 executor 列舉並於註解寫明。
11. 裁決 Q4 的「TC-036」在本檔沒有內容（保留不用），原因是程式碼中原標 TC-036 的註解對應到新的 TC-038。
12. 裁決 R1 寫「以最後訊息時間或建立時間算」，沒說兩者並存且不同齡時取哪個；TC-044／045 的夾具讓兩者同齡，不判這個情況。
13. 裁決 R1 只談「仍沒有事實」；失聯超過 6 小時但事實是 RUNNING／PENDING／COMPLETED 時要不要繼續問，計畫沒寫，不出 TC。
14. 裁決 R2 的說明句寫成中文，但 `mcp_server.py` 的工具說明是英文；TC-047 只要求英文說明裡講得出「失聯（lost）的 run 會觸發一次唯讀的站台查詢」，不要求逐字中文。
15. 裁決 R2 把 `get_run` 改成非唯讀後，網頁聊天的工具分類（`chat_tools.classify_check`）與「寫入工具恰為 cancel／forget／launch／relaunch／resume」之類既有測試會受影響。合約的解讀：`get_run` 對使用者仍是免確認的查詢（TC-048），不是需要按「確認」的請求工具；既有測試只為 `get_run` 這一項同步修改（TC-049）。若你其實要讓聊天對 `get_run` 也先問，請告知。
16. 裁決 R3 的六項 backlog 沒有行為可測，TC-050 只靠閱卷者讀 diff；若 executor 順手修了其中某項，閱卷者會當成「範圍外改動」提出，但不一定視為失敗，請你決定。
