# 測試案例：圖庫三項後續（gallery-followups）

**規格**：`specs/gallery-followups/plan.md`（本案沒有獨立 spec.md，計畫與維護者 2026-11-13 的話即規格）　**總覽**：`test-case-overview.md`

前提：本合約照 verifier 的建議答案 R1～R4 寫成（見總覽「我不確定的地方」）。lead 若選別的答案，合約回到草稿重開。
詞：「對話轉達」＝本人在對話裡說「確認」，由 AI 帶 `request_id` 與 `user_confirmed=true` 再呼叫一次工具（MCP 用戶端的做法）。「確認視窗」＝內建聊天頁在工具回「等本人確認」時跳出的「確認送出嗎？」視窗，按鈕由本人自己按，等於在確認頁按送出。

類型只有三種：功能、例外、不在範圍。

## User Story 1 — 完成頁：已打包的圖，勾選框預設勾著（優先度 P1）

維護者原話：「5.要 其他按照你建議」；建議是「已打包的圖，勾選框預設勾著（現在都不勾，沒勾就按打包會清空交付包）」。例 1：圖庫有 a（已打包）、b（未打包）→ 開完成頁，a 的框是勾的、b 沒勾 → 什麼都不動直接按打包 → 交付包仍是 a。

## User Story 3 — 內建聊天可以打包與刪圖（優先度 P1）

維護者原話：第 5 列「網站內建聊天要不要也能存圖、打包、刪圖？」他答：「要」。既有規則：刪圖與「會取代既有圖的存圖」只能由本人在表單或確認頁核准；打包與存新圖可以由對話轉達的「確認」核准。
例 3：在內建聊天說「把 a、b 放進交付包」→ 出現申請 → 說「確認」→ 生效。
例 4：在內建聊天說「刪除 a」→ 說「確認」→ a 還在，回覆給確認頁網址；到確認頁按下才刪。
例 5：在內建聊天對別人的分析提出 → 與分析不存在同一句答覆。
`publish_figure` 無法由內建聊天交付圖檔位元組（程式查實，見總覽），依計畫後備方案留在排除清單。

| 編號 | 對應需求 | 類型 | 前置條件 | 步驟 | 預期結果 | 驗證方式 |
|---|---|---|---|---|---|---|
| TC-015 | 計畫「做什麼」3 | 功能 | 內建聊天的工具清單 | 列出聊天可用工具 | 有 `pack_figures` 與 `delete_figure`；輸入欄位與 MCP 伺服器上的相同，只少 `request_id` 與 `user_confirmed`；說明文字與伺服器上的相同 | 自動：`platform/tests/test_chat_tools.py` |
| TC-016 | 憲法 7.0.0；R1 | 功能 | 同上 | 檢查這兩個工具的名稱與欄位 | 沒有任何欄位能替本人說「是」（沒有 `request_id`、`user_confirmed`，名稱與欄位不含 approve／confirm／yes／void 字樣） | 自動 |
| TC-017 | 計畫「做什麼」3 第 3 點（後備）；R4 | 例外 | 同上 | 列聊天工具、讀 `CHAT_EXCLUDED` | 沒有 `publish_figure`；`CHAT_EXCLUDED` 恰為 `{publish_figure}`；程式註解說明原因（聊天頁沒有圖的位元組、也沒有工具能取得它） | 自動 |
| TC-018 | 計畫「走與 MCP 相同的 request_* 函式」 | 功能 | 同上 | 跑分類檢查；再加一個沒分類的假工具 | 真實工具全部通過；假工具使它丟錯並點名；聊天清單 ＝ 唯讀工具＋查詢工具＋申請類工具（含這兩個） | 自動 |
| TC-019 | 例 3 | 功能 | 圖庫有 a、b、c，交付包為空；本人在內建聊天 | 聊天呼叫 `pack_figures`（run、names＝a、b） | 回「尚未變更」、有確認頁網址與摘要；產生一筆本人名下等待中的申請；交付包仍為空，圖庫逐位元組不變 | 自動 |
| TC-020 | 例 3 | 功能 | TC-019 之後 | 本人按確認視窗的「確認」（＝到該申請的確認網址按送出） | 交付包恰為 a、b；c 仍在圖庫未打包 | 自動 |
| TC-021 | 計畫「轉達效力與 MCP 相同」 | 功能 | TC-019 之後 | 本人在對話說「確認」，AI 帶 `request_id` 與 `user_confirmed=true` 再呼叫同一工具（與 MCP 同一個函式） | 交付包恰為 a、b；申請記錄的通道是 CHAT；與用 MCP 做結果相同 | 自動 |
| TC-022 | R1 | 功能 | 打包申請的等待中結果 | 呼叫確認視窗的產生函式 | 回「確認送出嗎？」、`confirmation_url` 等於該結果的 `url`、摘要、按鈕「確認」「取消」；欄位恰為五個，沒有任何「是」的值 | 自動 |
| TC-023 | 例 4；計畫「刪圖被拒並給確認頁網址」 | 例外 | 圖庫有 a；聊天呼叫 `delete_figure` 後申請在等待 | 本人說「確認」，AI 帶 `request_id` 與 `user_confirmed=true` 再呼叫 `delete_figure` | 被拒；答覆含該申請的確認頁網址並說明刪除須由本人在確認頁按下；a 與它的程式碼檔、參數檔逐位元組仍在；申請仍在等待（沒作廢、沒被用掉） | 自動 |
| TC-024 | 維護者規則；R2 | 例外 | `delete_figure` 的等待中結果 | 呼叫確認視窗的產生函式 | 回 None：聊天裡沒有可按的「確認」按鈕能刪圖；答覆文字只給確認頁網址 | 自動 |
| TC-025 | 例 4 | 功能 | TC-023 之後 | 本人到確認頁按送出 | a 被刪（含程式碼與參數檔），也離開交付包 | 自動 |
| TC-026 | 例 4；寫了會在聊天有更寬的路就失敗 | 例外 | 一個等待中的刪除申請 | 嘗試：①只帶 `user_confirmed=true` 沒有 `request_id`；②連續轉達 30 次；③別人帶這個申請編號轉達；④捏造的編號 | 全部被拒；沒有任何圖被動；申請不被用掉，也沒有洩漏別人的確認頁網址 | 自動 |
| TC-027 | 例 5 | 例外 | 本人 ann 在聊天；run 屬於 bob，另有一個不存在的 run | ann 對 bob 的 run 與對不存在的 run 各呼叫 `pack_figures` 與 `delete_figure` | 兩種情況答覆同一句；沒有產生申請；不洩漏 run 是否存在 | 自動 |
| TC-028 | 計畫「與 MCP 相同」 | 例外 | 圖庫有 a | 聊天呼叫：圖名不存在、圖名不合規、`pack_figures` 超過上限、`delete_figure` 一次兩張 | 各自與 MCP 同一句拒絕；沒有產生申請 | 自動 |
| TC-029 | 計畫「做什麼」3；R3 | 功能 | 聊天系統提示 | 讀提示 | 提示列出 `pack_figures`、`delete_figure`；說明刪圖不能在聊天裡確認、要請本人到確認頁按；仍說「沒有任何工具可以替本人說是」；不含 approve／confirm／yes／void 字樣；沒有提到 `publish_figure` | 自動：`platform/tests/test_chat_confirm.py`（改寫釘住處）、`test_chat_tools.py` |
| TC-030 | 維護者規則 | 例外 | 圖庫有 a、b，a 已打包；聊天提出一個打包與一個刪除，本人都還沒按 | 比對圖庫資料夾與 `index.json` | 逐位元組不變；沒有任何聊天可用的工具能在沒有本人按之前寫圖庫檔案（也就沒有任何取代既有圖的路） | 自動 |
