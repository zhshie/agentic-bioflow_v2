## 作法
1. **國網樣本表上傳**（`/upload`）：
   - 使用者有可用的 slurm 環境時，上傳頁原本的那句改成一個表單「上傳樣本表（CSV 或 TSV）」：一個檔案欄、必填、一次一個檔、上限 1 MB、副檔名 `.csv`／`.tsv`。
   - 存到 `<uploads_root>/<登入者>/sheets/<原檔名>`；檔名只留英數字、`.`、`_`、`-`（其他字元換成 `_`），同名＝加 `-2`、`-3`，不覆蓋。
   - 內容檢查：UTF-8 可解碼、至少一列標題加一列資料、每列欄數相同；不檢查路徑是否存在（站台上的檔，平台不連線）。不通過＝400 重畫上傳頁，錯誤句在表單上方，說明哪一條不符。
   - 成功＝303 回 `/upload?notice=sheet_saved`，顯示「✓ 已上傳樣本表 sheets/<檔名>，可於「送出新分析」第 4 步選擇。」並附連結「前往送出新分析」（`/launch`）。
   - 沿用既有 same-origin、登入、CSRF 規則；臨時密碼登入者照既有規則導向 `/welcome`。
   - 只有雲端環境、或兩種都有：雲端的上傳區照舊，國網樣本表表單另外一節排在其後。兩種都沒有：維持既有「沒有可用的運算環境」句（文字改成不只講雲端）。
   - `/launch` 第 4 步「尚無已上傳的樣本表」那句的連結文字與去處不變（仍是 `/upload`）。
2. **送出後**（`POST /c/<id>` 成功，kind 為 launch／resume／relaunch／cancel）：網頁送出的人看到「已送出。工作編號 N。」＋一句「站台開始執行後，進度會顯示在分析清單。」＋按鈕連結「查看進度」，指向該 run 的進度頁（`/?run=<run 名稱>`，與左欄點 run 名稱進入的網址相同）。把「你可以回到 AI，用同樣的參數再呼叫一次，它會告訴你工作編號。」整句拿掉——MCP 的工具自己會回報工作編號，不需要這句。`clean_work` 那句不變。錯誤頁的「請回到 AI 重新送出。」改成「請重新送出。」（網頁與 AI 都適用）。
3. **進度頁運算環境欄**：run 有對應的 `launches.ce` 時顯示那個名稱；只有在平台沒有這個 run 的送出紀錄（例如從平台外送出、由 Nextflow 紀錄重建）時才顯示「—」。先查目前「—」是哪裡取不到值（推測：讀的是 index 的欄位，而 nano4 的 run 沒有寫進那欄），修在取值處，不改資料庫結構。
4. 只用現有 class 與 DESIGN.md token；不改 STYLE（D13 釘 sha256）；CSP 不變。中英字串皆正式書面語、不含 DESIGN.md「用字」禁用字。

## 六項必填檢核（ui 計畫固定段）
1. 確認頁規則：確認與送出的邏輯不動，只改送出後的回應頁（作法 2）。
2. 失敗狀態：上傳檔太大／副檔名不對／不是 UTF-8／欄數不一致／沒有資料列／缺 CSRF 或跨來源（403）／未登入，各自的句子；送出失敗頁的句子（作法 2）。
3. 提示句位置：上傳錯誤句在上傳表單上方；成功句在頁首；送出後頁的按鈕在句子下方。
4. 要改的舊測試：見「範圍：檔案」的 grep；只加不刪。
5. 手機寬度：上傳頁與送出後頁 390 px 無橫向捲動。
6. 空狀態：上傳區還沒有任何樣本表＝上傳頁照常顯示表單；沒有任何可用環境＝作法 1 最後一點的句子。

## 專長守則（ui）

### executor

- 先讀專案根目錄的 `PRODUCT.md`（給誰用、要解決什麼）與 `DESIGN.md`（版面線框、tokens、每個畫面與狀態、維護者的原話例子）。讀不到就 BLOCKED，不自己發明設計。
- 只准用 `DESIGN.md` 定義的 tokens（色彩、字型、字級、間距、圓角）與版面。不新增任何視覺決策：不自創顏色、字型、間距數值，不順手「美化」。
- `DESIGN.md` 沒決定的事，一律寫進報告的「卡住的原因／要問的問題」，不猜。
- `DESIGN.md` 列出的每個畫面、每個狀態都必須做出來，包含空狀態、載入中、錯誤、失敗。少一個就不算完成。
- 遵守計畫寫明的前端限制（例如 CSP、禁用 inline style、不載外部資源、只在允許處使用 JS）。限制與設計衝突時停下來問，不自行取捨。
- 狀態絕不只靠顏色：一律「符號＋文字＋顏色」三者並用。
- 手機寬度可用（不橫向捲動、點擊目標夠大），鍵盤操作時焦點外框可見。
- 介面文字用使用者視角的白話，不露出內部術語、錯誤代碼或程式名詞；錯誤訊息說發生什麼事與下一步。

### verifier

**CONTRACT（出題）必須轉成測試案例（TC）：**
- `DESIGN.md` 的每個畫面、每個狀態都至少對應 1 個 TC（含空、載入、錯誤、失敗）。
- 維護者的原話例子逐字對應到 TC。
- 計畫列的前端限制各對應 TC（例如頁面不得含 inline style、不得請求外部網址、CSP 標頭存在）。
- 狀態表達 TC：每個狀態輸出的 HTML 同時含符號、文字，不得只靠 class 顏色。

**ACCEPTANCE（閱卷）必須檢查：**
- 把每個有改動的頁面渲染成 HTML 檔（用專案的 test client，或計畫指名的 fixture）。做不到就標 UNVERIFIED，並寫明需要什麼才能驗。
- 對渲染出的 HTML 跑 Impeccable 偵測器（唯讀）：`sh "G:/我的雲端硬碟/謝馬爾/.claude/skills/impeccable/scripts/impeccable" detect <file.html>`。
- **FAIL**：違反 `DESIGN.md` 的 tokens／畫面／狀態；違反計畫寫明的前端限制；狀態只靠顏色；缺少 DESIGN.md 列出的畫面或狀態。
- **「需要人看的事」**：偵測器的其他發現（對比、常見字型、AI 範本味等）與品味問題。這些不判 FAIL。
- 報告固定一行：`專長守則檢查：……`（列出做了哪些檢查、結果）。
- 注意：「看起來好不好」的最終判斷屬於維護者，靠 developer-agent 附在 PR 的截圖（B 級）決定，verifier 不替他下結論。
