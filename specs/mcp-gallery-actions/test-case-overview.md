## 用白話講：這份合約在驗什麼

1. **你說「確認」之前，什麼都不會變。** 圖庫逐檔比對，三個管道（表單、確認頁、聊天）都驗（TC-001～007）。
2. **AI 沒辦法自己替你確認。**
   - 自己帶「已確認」卻沒先提出，不行。
   - 拿別人的申請編號，不行。
   - 拿打包的申請去刪除，不行。
   - 內容跟你看到的不一樣，不行。
   - 同一個確認重放第二次，不行。
   - 過了 10 分鐘，不行。
   - 對應 TC-033～041、TC-106。
3. **畫面把話說清楚。**
   - 打包：「加入 a、b；移出 c，c 仍留在圖庫，之後可以再打包。」
   - 清空：多一行「交付包將被清空」。
   - 刪除：會刪哪張、它的程式碼和參數、它現在在不在交付包內。
   - 中英文都驗，也驗三個管道的名單完全一致（TC-009～023）。
4. **你的兩句原話各有專門的案例。**
   - 「使用者說確認就行」：TC-026、TC-029、TC-113。
   - 「以後要回去拿當時未勾選的項目還是要可以」：TC-008（打包永遠不刪圖）、TC-030、TC-031（c 還在、可下載、可再打包）。
5. **確認的當下會再看一次圖庫。** 你在網頁上先刪了 b，確認時就拒絕並說「圖庫已變動，請重新提出」；三個管道都驗（TC-048～058）。
6. **網頁按鈕和 AI 同時操作不會互相蓋掉。** 用真的並行與 24 種順序驗（TC-059～062）。
7. **兩個新動作和網頁按鈕走同一個函式、結果逐項相同**（TC-068～072）。
8. **資料庫升級：舊資料原封不動、失敗會還原、跑兩次一樣、`jobs` 表不動**（TC-073～088）。
9. **既有的啟動、取消、續跑、重跑、清理、存圖不受影響**（TC-084、TC-085、TC-102）。

## 我（撰寫者）不確定的地方（已依建議寫進案例，你一句話就能改）

1. **P1 一個確認種類還是兩個？** 建議一個 `gallery_change`，用 `action` 欄位分打包與刪除。理由：L 級檔案少動一次，申請內容的雜湊含 `action`，打包的確認不可能被拿去刪圖。
2. **P2 清空交付包（`names` 為空）要不要多一行警告？** 建議要，只多一行醒目的話，不多一道確認。
3. **P3 刪除目前在交付包內的圖：拒絕還是只說明？** 建議不拒絕，只在畫面明寫「目前在交付包內，刪除後會一併移出」（和你的例 2 一致，也和網頁按鈕一致）。
4. **P4 聊天通道在圖庫已變動時要說什麼？** 建議也說「圖庫已變動，請重新提出」，不用現在籠統的「內容不同」。
5. **P5 重新檢查要多嚴？** 建議只要「會發生什麼」（連每張圖的識別，包括被同名取代）和畫面不同就拒絕。連期間多了一張不相干的新圖也拒絕。
6. **P6 打包結果和現況一模一樣（或空清單對空包）怎麼辦？** 建議不建申請，直接回「沒有需要變更」，不叫人去按一個什麼都不改的確認。
7. **P7 `delete_figure` 要標「破壞性」嗎？** 建議標（`pack_figures` 不標）。
8. **P8 按鈕用字：** 打包沿用「送出」，刪除沿用清理確認的「確認刪除」。
9. **P9 哪些 run 狀態可以提出？** 建議和 `publish_figure` 一樣，自己的 run 任何狀態都可（網頁只在成功的 run 才顯示按鈕，那是畫面限制）。
10. **P10 名稱比對：** 沿用網頁的完全相符（區分大小寫）。
