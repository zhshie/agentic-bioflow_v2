## 我（撰寫者）不確定的地方

1. 計畫裁決 1 讓「存一張圖」不經確認管道（只寫平台自己的 platform.db，與 012c 的 datasets 同類）。專長守則字面要求每個寫入都要確認；我依計畫判為不適用，只用 TC-126、TC-127 證明沒有送出路徑。這樣可以嗎？
2. 計畫說「同層一律先取 id 字典序最小者」，沒說清楚是「一層一層」還是「每次從可取的節點裡挑最小」；兩者在少數圖上順序不同。TC-055、TC-056 只用兩種讀法答案一致的圖，所以不受影響，但 `fan_in_and_twins/` 的標準答案由 executor 手算，可能選其中一種。要不要先指定一種？
3. 計畫說「三個以上來源就連續 `.mix(`」，沒寫 `A.mix(B).mix(C)` 還是 `A.mix(B, C)`。TC-053 只檢查三個來源都在、依序、以 `.mix(` 串接，不指定括號形狀。
4. 邊超過 1000、節點超過 200、大小超過 256 KiB 的 problem 文字計畫沒寫。TC-027 至 TC-029 只要求「被拒、中英並陳」，TC-028 另要求圖本身沒有別的毛病（拒絕原因只能是邊數）。
5. `fan_in_and_twins/` 與 `old_format_module/` 的標準答案計畫要求 executor 手算、developer-agent 看過再固定，而且「不可用程式輸出反過來當標準答案」。我無法從檔案判斷它是不是複製程式輸出；驗收時我會對照 ledger 的手算紀錄與本檔 TC-045 至 TC-058 的規則逐條核對。
6. 計畫對「節點上多餘的鍵」（例如節點有未知欄位）沒有規定，只規定頂層。我沒寫這個 TC。要不要補一句？
7. TC-142、TC-143 標為手動，但 `docs/TESTING.md` 目前沒有對應步驟（內容是 ledger 與 PR 說明）。驗收者會直接讀 ledger 和 PR 說明；如要正式化，需另開文件任務。
8. `list_pipelines` 的 `updated_at` 與 `get_pipeline` 找不到時的具體措詞，計畫沒有寫死，TC-086、TC-105 只要求欄位存在與 `found` 為假；別人的與不存在的「同一句」仍由 TC-111、TC-112 比對。
