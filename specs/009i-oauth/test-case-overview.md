## 請你判斷的三件事

1. **每條是不是你要的？** 你的承諾是計畫「給維護者」三句：用名字＋網頁密碼登入並按「允許」就能連線、允許不等於同意送出、授權頁絕不收權杖。看 TC-C04（拿權杖當登入全部無效）、TC-F01 至 TC-F03（允許後送出仍只建立等待中申請）、TC-D01（權杖由換碼得來）是不是你的意思。
2. **有沒有漏掉的出錯情況？** 想像別人或 AI 想繞過：拿 PAT 或 OAuth 權杖登入（TC-C04、F03）、偷到授權碼（TC-D02 至 D06）、重放更新權杖（TC-D08）、不帶 CSRF 的「允許」（TC-C08）、用 GET 發碼（TC-C09）、被停用的人（TC-C13、D10、E06）。
3. **「不在範圍」對嗎？** 這次不做：公開 https（009h）、多種權限範圍、接收器和代理的 OAuth、第三方登入、密碼重設、記住同意、任何確認通道的改動（TC-H01 至 TC-H07）。

## 我（撰寫者）不確定的地方

1. 沒給 `--public-url` 就啟動 `mcp --http` 時，401 的挑戰長什麼樣，計畫沒寫。TC-A05 只要求仍是 401、`Bearer`、不回顯、PAT 可用，不斷言有沒有 `resource_metadata`。
2. 授權碼被重複使用時，第一次已發出的權杖要不要一併作廢（RFC 建議作廢），計畫沒寫。TC-D03 只要求第二次被拒、沒有新權杖，不斷言舊權杖的下場。要不要作廢請說。
3. `abf-platform oauth revoke USER` 是否也撤銷該人的 PAT，計畫沒寫。我依指令名稱解讀為只管 OAuth 權杖（TC-E05），PAT 要用 `pat revoke`。
4. 使用者被停用後，他手上的 refresh 權杖也不能換新（TC-D10）。計畫只寫「disabled user fails both」指 PAT 與 access，這是我的延伸，請 developer-agent 確認。
5. 資源 metadata 的網址路徑（是否帶 `/mcp` 後綴）計畫沒定。TC-A01、A02、A04 只認「挑戰裡指的那個網址」，不寫死。MCP 行程如何得知網頁服務的公開網址（計畫沒寫；現況有 `web_base_url` 存在 platform.db）也不限，只驗結果。
6. 「註冊的每位址速率上限」的數字計畫沒寫。TC-B05 要求有一個命名的常數、寫進 `docs/PLATFORM.md`、且比 200 個名額上限更早擋下一個位址的灌註冊。
7. 網頁登入 cookie 是 `SameSite=Strict`。從 Claude 的瀏覽器導向 `/authorize` 屬跨站導覽，已登入的人可能多看一次登入表單。這不影響安全，所以沒出題。要避免請說。
8. 一筆同意申請不綁定「發起的人」：誰用網頁密碼登入、按了「允許」，權杖就屬於誰（TC-C14）。這是 OAuth 的正常設計，但表示唯一的防線是同意頁上顯示的連接器名稱與 redirect 主機（TC-C05）。這個取捨見下方「需要人看」。

## 需要人看的事（白話）

- **同意頁的說明你看得懂嗎？**（TC-C05）頁面上那句「可以讀你的 runs、可以請求送出，不能送出分析，每次仍要你按送出」，請你看實際畫面，是否清楚到你敢按「允許」。
- **「允許」按下去，等於把你的身分借給那個連接器。** 只要有人讓你登入後按「允許」，那個連接器就能以你的身分讀資料、提出送出申請（但不能替你按「送出」）。防線只有頁面上顯示的連接器名稱和 redirect 主機。這和 PAT 一樣強、只是壽命較短。你接受這個程度嗎？
- **Claude Desktop 端到端要等公開 https 網址（009h）。** 在那之前只驗證到本機測試客戶端（TC-I06）。這份合約不宣稱 Claude Desktop 已實測。
