## 我（撰寫者）不確定的地方

1. 計畫 F5 只寫「終端機確認的啟動」。終端機確認的取消（cancel），確認紀錄是否也保留內容？本合約沒有為取消另立 TC；你若希望取消也一併保留，請告訴開發者，會新增一條。
2. F2 沒說清楚：`forget` 當下，已經存在的、指向該 run 的等待中續跑或重跑申請，是要被作廢還是留著等到送出時被排隊檢查擋下。TC-131 只要求「之後按送出不會排任何工作」，沒有規定是哪一種。
3. F4 的「24 小時」邊界：TC-141 測 23 小時（仍拒絕）、TC-142 測 25 小時（允許），不釘剛好 24 小時那一刻。
4. F5 會讓 009e 現有的兩個「太久了」測試（續跑、重跑）可能必須改前置資料（把那一列造成舊格式）。計畫沒點名這兩個測試；TC-093 只允許「只改前置資料、斷言不動、ledger 列出」這一種，請 developer-agent 在計畫補一條點名。
5. 沿用先前的疑問（仍成立）：計畫說 `forget` 用跟 `cancel` 同一個辦法由 run 名找到 run；但現有 `cancel` 的對應會拒絕「沒有 Slurm 編號」或「環境、代理已變」的 run。這種已結束的 run 要不要也允許刪？（本合約只檢查一般的已結束 run。）
6. 沿用：規則 3 寫「走 `_ask`」，但 R8 說 `forget` 不寫確認紀錄，而 `_ask` 會先寫一筆等待中的申請。本合約只檢查看得到的結果（TC-034、035、036），不規定內部怎麼做。
7. 沿用：拒絕時的中英文說明，計畫只逐字寫出 R2、「還在準備中」與「內容已被擁有者刪除」；其他拒絕（running、lost、排隊中）只檢查「被拒絕且沒變動」，TC-050 另要求有中英說明。
8. 沿用：終端機回答不是 `y` 時，本合約假設跟 `cancel` 相同（什麼都不做）。
9. 已解決：先前的疑問「工作成功結束但 run 不在索引」現在由 F4（TC-140 至 143）覆蓋；先前關於「終端機確認的啟動 7 天後內容就沒了」的疑問，對新做的啟動由 F5 解決（TC-150 至 157），舊格式的列仍受 R16（一）限制（TC-064、158 至 160）。
