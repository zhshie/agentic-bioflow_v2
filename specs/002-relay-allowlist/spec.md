# Feature Specification: 對外白名單可由部署自己擴充（relay allowlist）

**Feature Branch**: `002-relay-allowlist`

**Created**: 2026-09-30

**Status**: Draft

**Input**: 憲法稽核 C 批（#31）：`scripts/nf_relay.py` 的對外白名單寫死在 plugin 程式裡，每條新管線都加過網域；使用者改不了 plugin 的檔案（`hooks/guard_plugin_files.sh` 會擋），碰到新網域只能找維護者——違反第 6 條（任何管線不需設定）與第 7 條（不需要找維護者）。

> 名詞見 `CONTEXT.md`。本規格給維護者看，用中文；編號照 Spec Kit 慣例。
> 本 feature 只處理白名單。稽核 C 批另兩件——樣本表欄位寫死、新電腦跳過公開測試資料驗證——各自另開 feature（建議 003、004），不在本規格內。

## 背景

叢集的計算節點不能上網，管線要下載的東西（容器映像、參考資料、外掛）都經過登入節點上的一個中繼程式（relay）轉出去。為了不讓共用的登入節點變成任何人都能用的開放出口，中繼程式只放行白名單上的網域。白名單現在是 plugin 程式碼的一部分，所以新管線需要一個新網域時，只有維護者能改、改完還要發版。

## Clarifications

### Session 2026-09-30

- Q: 誰可以確認把網域加進白名單？ → A: 操作者本人，經 Claude Code 跳出的確認（與送出分析同等級），並記錄日期與原因。
- Q: 額外白名單是每位成員各一份，還是實驗室共用？ → A: 每位成員（每個部署）各一份；中繼程式本來就是每位成員各跑一支（`scripts/egress_ctl.sh`）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 — 新管線需要新網域時，操作者自己就能放行（Priority: P1）

操作者跑一條沒跑過的 nf-core 管線，因為某個網域不在白名單上而失敗。plugin 指出是哪個網域被擋、為什麼可能需要它；操作者確認後，這個網域加進**自己部署的**額外白名單，中繼程式重啟後生效，重跑成功。整個過程不需要改 plugin 的檔案，也不需要找維護者。

**Why this priority**: 這是第 6、7 條被違反的核心；其餘都是它的安全配套。

**Independent Test**: 在測試環境模擬一個被擋的網域，走完「看到被擋 → 確認 → 放行 → 生效」，plugin 檔案沒有任何改動。

**Acceptance Scenarios**:

1. **Given** 一次失敗的 run，失敗時間點對得上一筆被擋的網域，**When** 操作者確認放行，**Then** 該網域寫進部署設定的額外白名單，中繼程式重啟後放行它，plugin 本身的檔案未被修改。（正常）
2. **Given** 額外白名單已有某網域，**When** 中繼程式啟動，**Then** 放行的網域＝plugin 內建清單＋部署的額外清單，啟動訊息列出兩者各自的來源。（正常）
3. **Given** 操作者要加的不是網域而是萬用字元、IP、整個頂級網域（如 `*`、`com`、`0.0.0.0`），**When** 嘗試加入，**Then** 拒絕並說明只接受具體網域。（例外）
4. **Given** 模型在沒有操作者確認的情況下試圖加網域，**When** 執行寫入的那一步，**Then** 被安全網攔下並要求確認。（例外）
5. **Given** 額外白名單的檔案壞掉或讀不到，**When** 中繼程式啟動，**Then** 照常只用內建清單啟動，並明講額外清單沒有載入、原因是什麼——不是悄悄忽略，也不是整個拒絕啟動。（例外）
6. **Given** 操作者要求把網域加進 plugin 內建清單（讓所有實驗室都生效），**When** 處理這個要求，**Then** 說明這要由維護者改 plugin 並發版，本功能只改這個部署自己的清單。（不在範圍）

### User Story 2 — 看得到誰在什麼時候放行了什麼（Priority: P2）

放行一個網域等於移動一條安全邊界。事後要能查到：這個部署額外放行了哪些網域、何時、是哪一次失敗促成的。

**Why this priority**: 共用登入節點上的安全邊界，改動必須可追溯；但先要能改（US1）。

**Acceptance Scenarios**:

1. **Given** 已放行過網域，**When** 查看部署狀態（`scripts/status.sh` 或 `settings.sh --summary`），**Then** 列出每個額外網域與加入日期、原因。（正常）
2. **Given** 操作者要移除一個額外網域，**When** 確認移除，**Then** 從清單拿掉，中繼程式重啟後不再放行。（正常）
3. **Given** 有人手動編輯清單、加了沒有日期或原因的項目，**When** 顯示狀態，**Then** 該項目照樣生效，但標示「來源不明」。（例外）

## Requirements *(mandatory)*

- **FR-001**: 部署 MUST 能有一份自己的額外白名單，存放在部署設定區，不在 plugin 檔案內；plugin 升級不得覆蓋它。
- **FR-002**: 中繼程式 MUST 放行「內建清單 ∪ 額外清單」，且只放行這兩者。
- **FR-003**: 加入網域 MUST 經過操作者本人明確確認（與送出分析同等級：Claude Code 跳出確認），不需要另一位管理者核准。
- **FR-004**: 只接受具體網域名稱（可含子網域，如 `download.example.org`）；拒絕萬用字元、IP 位址、單一標籤的頂級網域、空字串。
- **FR-005**: 每筆額外網域 MUST 記錄加入日期與原因（促成它的 run 或說明）。
- **FR-006**: 額外清單無法讀取時，中繼程式 MUST 以內建清單啟動並明講額外清單未載入與原因。
- **FR-007**: 狀態顯示 MUST 列出額外網域及其日期、原因；沒有日期或原因的標示「來源不明」。
- **FR-008**: 移除網域 MUST 經過確認，移除後重啟中繼程式即不再放行。
- **FR-009**: `commands/runs.md`、`commands/launch.md` 中「Once approved: allow it」的步驟 MUST 改為呼叫這個機制，不再暗示去改 plugin 檔案。
- **FR-010**: 額外清單 MUST 是每個部署（每位成員）各自一份；一位成員放行的網域不影響其他成員的中繼程式。

## Success Criteria *(mandatory)*

- **SC-001**: 一條需要新網域的管線，操作者從看到被擋到重跑成功，全程不需要維護者、不需要改 plugin 檔案。
- **SC-002**: plugin 升級或重裝後，部署的額外白名單仍在、仍生效。
- **SC-003**: 任何時候都能列出這個部署在內建清單之外多放行了哪些網域、何時、為什麼。
- **SC-004**: 沒有任何路徑能在未經確認的情況下把網域加進白名單。

## Assumptions

- 中繼程式是每個部署自己啟動的程式（`scripts/egress_ctl.sh`），執行身分是該部署的使用者。
- 「確認」沿用現有安全網的機制（Claude Code 跳出確認），不另做一套。
- 內建清單仍留在 plugin 內，作為所有部署共同的基線。
- 本 feature 不改「誰可以連進中繼程式」那一半的限制（只准計算節點）。

## Out of Scope

- 把網域加進 plugin 內建清單（仍由維護者改程式並發版）。
- 樣本表欄位寫死（另開 feature 003）、新電腦跳過公開測試資料驗證（另開 feature 004）。
- 其他叢集的中繼方式；第二個 site adapter。
