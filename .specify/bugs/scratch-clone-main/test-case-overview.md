## 給執行者的實作要求（verifier 計畫審查，驗收時逐點核對）

1. 「不要 main」時，做完副本要先切成不在任何分支上，再刪 `refs/heads/main`；刪之前要先確認它存在（沒有 main 時不得報錯）。「要 main」時維持現狀。
2. 新寫的程式不得含 `git show main:`、`rev-parse --verify -q main` 或 skipped 字樣（既有自檢 TC-009 會抓）。
3. `tests/platform_direction_docs_test.sh` 的 nomain 副本（其 TC-011 本來就以「沒有 main」為前提）必須套用同樣的處理；計畫中「若不依賴才不動」的分支在此不適用，因為該檔 nomain 模式的標籤與 TC-011 已明確依賴無 main。
4. 每條 TC 標「自動」者，測試內以註解寫上 TC 編號。
5. fix.md 要留下修補前在「分支叫 main」的檢出上重現的 FAIL 紀錄（TC-010）。

## 請你判斷的三件事

1. **每條是不是你要的？** 有沒有哪條的「預期結果」跟你想的不一樣。
2. **有沒有漏掉的出錯情況？** 想像實驗室成員會怎麼用錯它。
3. **「不在範圍」對嗎？** 這次不做的事，有沒有其實這次就該做的。

## 我（撰寫者）不確定的地方

1. 「在 main 上跑」目前只靠驗收者手動重現（TC-001、002、008、009、010），測試檔本身在 PR 上不會自己製造「來源在 main」的情況，所以日後有人弄壞這個修法，要等到合併後的 CI 才會發現。要不要之後另開一張把這個情況自動化？（本案計畫沒要求，所以沒寫成必過的自動案例。）
2. TC-006 要求 `platform_direction_docs_test.sh` 也有「nomain 副本沒有 main」的斷言，而該檔現在沒有這條。這是為了讓計畫「同樣處理」可以被檢查而做的最小補充，不改任何既有斷言；如果你認為只改副本做法、不新增斷言就夠，回覆一句即可，TC-006 改成手動核對程式。
