# Changelog

The v3 line (ADR 0006, 2026-10-15): the platform generation. `main` stays v2 (2.17.x) until v3.0.0.

## 3.0.0-dev (unreleased, branch `v3`)

- keep-submissions: a confirmed submission keeps its content (bundle and screen text) until its owner deletes it; no clock clears it any more (a void or expired pending request still loses its content after 7 days, `KEEP_CONTENT_SECONDS` is now `KEEP_UNSENT_SECONDS`). New `abf-platform forget RUN` and MCP tool `forget` delete it after a yes (terminal `y`, or the client's form), only for a finished run and only for its owner; the record of who sent it and when stays (`forgotten_at`, `forgotten_by`). See docs/PLATFORM.md, "Forget". Follow-up: merged with 009e (the tools are now eleven, `forget` among them); a resume or a relaunch of a forgotten run says 「內容已被擁有者刪除」; `forget` waits 24 hours for a launch that went out but is not in the run index; the confirmation of a terminal launch keeps the bundle and the screen text too (resume and relaunch read it first).
- mcp-tests-in-ci: the tests of `platform/tests/mcp/` (the tool-list snapshot and the write-tool contract) were run by no shard of `tests/platform_test.sh`; its file list now includes `tests/mcp/test_*.py`, and the shard-rule test (`test_platform_parts.py`) counts test files in subfolders too, so a folder that no shard collects fails it. The `pack_figures` tool description is shortened to the 600-character limit; no statement of it is dropped.
- replace-needs-click: a `publish_figure` request that would replace a figure already in the gallery (its bundle `replaces` is not empty) can be approved only through the client's form or by the person on the confirmation page; a relayed yes (`request_id` and `user_confirmed=true`) is refused, with the address of the confirmation page, and the request stays pending. The first answer for such a request names only the page. A publish under a new name, `pack_figures`, `delete_figure` and every other kind are as before. The tool description and the two parameter descriptions of `publish_figure` say so. See docs/PLATFORM.md.
- delete-needs-click: a figure delete (`delete_figure`, kind `gallery_change`, action `delete`) can be approved only through the client's form or by the person on the confirmation page; a relayed yes (`request_id` and `user_confirmed=true`) is refused, with the address of the confirmation page, and the request stays pending and unconsumed. A deletion cannot be undone and the platform cannot tell the person's own "confirm" from the AI saying so. The first answer for a delete names only the page; the tool description and the two parameter descriptions of `delete_figure` say `user_confirmed` has no effect (the parameters stay in the schema). `pack_figures`, `publish_figure` and every other kind are unchanged. See docs/PLATFORM.md.
- mcp-gallery-actions (gallery slice 3): two new MCP tools, `pack_figures(run_id, names, request_id?, user_confirmed?)` and `delete_figure(run_id, name, request_id?, user_confirmed?)` (25 tools now), so a person's own LLM client can pack and delete gallery figures once the person says yes (the form, the confirmation page, or the chat with `request_id` and `user_confirmed=true`). A new confirmation kind `gallery_change` that queues no job (`platform.db` is rebuilt once to let it in, as for `publish_figure`). Packing sets the delivery package to exactly the named figures; the others leave the package and stay in the gallery. At the yes the gallery is checked again under its lock and a change since the question refuses the request. The web buttons are unchanged; both paths call the same core functions. The browser chat is not offered the tools.
- desktop-systemd: the desktop platform in WSL starts at logon and restarts a crashed process under systemd user units: a new template `deploy/systemd/abf-station@.service.in` for the station agent (one instance per agent, `RestartPreventExitStatus=2 3` so a refusal to start stays failed), `deploy/station.env.example`, and `deploy/wsl/keep-wsl-running.ps1` (a Windows logon task `abf-wsl-keepalive` that keeps WSL open; prints the plan unless `-Apply`, `-Remove` removes it). docs/OPERATIONS.md, "Desktop platform in WSL" has the steps and what each one stops; docs/TESTING.md has the manual checks. The three existing units are unchanged; nothing on the desktop is changed by the repository.
- studio-embed: with the new deployment setting `ABF_STUDIO_URL` (`http://127.0.0.1:<port>` or `http://localhost:<port>` only; anything else stops `abf-platform web` at start with a message that names it; empty or unset is no setting) the downstream page of a succeeded run shows RStudio in an `<iframe>` whose source is exactly that address, with an "open in a new tab" link above it, a hint for a blank frame, two R lines to paste into the RStudio Console (fetch the tables, publish the current plot) and the terminal commands of before in a closed `<details>`. Only that page's CSP gains `frame-src <that address>`; every other page is as it was, and without the setting the downstream page is byte for byte as it was. The platform does not start, stop, probe or proxy RStudio (the page does not probe the address and the agent does not report it: two deliberate differences from ADR 0010 Decided 3). `abf-platform fetch-results <run> --r` prints only the R code (progress and errors go to standard error). A new unit template `deploy/systemd/abf-rstudio.service.in` runs RStudio Server as the person, on 127.0.0.1 only, port taken from `ABF_STUDIO_URL`; RStudio Server is not shipped (AGPL) and its package's own root service must be disabled first (docs/OPERATIONS.md, step 12 of "Desktop platform in WSL"). No new route, action, dependency or CSS. See docs/PLATFORM.md, "RStudio in the downstream page".
- gallery-followups: the finished page pre-ticks the box of a figure already in the delivery package (pressing the pack button untouched leaves the package as it is; the note beside the button says so); `publish_figure` is marked destructive (`destructiveHint` true, the other three annotations and `tools.json` unchanged); the browser chat is offered `pack_figures` (its 「確認送出嗎？」 window now reads the gallery result `url`) and `delete_figure` (no window: the reply gives only the confirmation page address, a delete is pressed there by the person), without the relay arguments; `publish_figure` stays out of the chat because the page has no figure bytes.
- cli-fetch-publish-figure (slice 1): two commands that run on a person's own computer, `abf-platform studio-connect --server <https address>` (keeps the platform's public address and the person's own personal token in `~/.abf/studio.json` or `ABF_STUDIO_CONFIG`: hidden prompt or `--token-stdin`, no `--token` option, mode 0600, checked before it is stored) and `abf-platform fetch-results <run> [--dir DIR]` (pulls the small result tables of one run, read only, through the platform's MCP tools `run_outputs` and `read_run_file`, into a folder on that computer and prints the R code that loads them in RStudio; web reports and binary files are listed as skipped). They are MCP clients of `/mcp` with the person's own token, open no database and run no script; exit codes 0, 1, 2 (not set up) and 3 (no connection); a site connection that is not open is told apart from a refused path. The downstream page of a succeeded run shows the two commands in place of the `jupyter lab` and `docker run` lines. No server change, no new dependency, no migration needed. `publish-figure` (a figure sent back to the gallery after the person's own confirmation) is slice 2 and waits for `mcp-publish-figure`. See docs/PLATFORM.md, "Commands on your own computer", and docs/OPERATIONS.md.
- cli-fetch-publish-figure (slice 2): the third command that runs on a person's own computer, `abf-platform publish-figure <run> <image file> [--code FILE] [--params FILE] [--caption TEXT]`. It proposes one figure to the gallery of one of the person's own runs through the MCP tool `publish_figure` and never gives the person's yes: it sends no `user_confirmed` and no request id, does not wait or poll, prints its own sentences ("not saved yet") and the link of the confirmation page as the platform gave it, and exits 0; the person opens the link and presses the button, and only then is the figure in the private gallery (not in the delivery bundle). A platform refusal is printed as its reason with exit 1. The limits of the gallery are checked on the computer first, taken from `abf_platform.actions.figures` as constants (nothing else of the server is used, no database is opened). The downstream page shows the third line. No server change, no new dependency, no migration needed. See docs/PLATFORM.md, "publish-figure".
- mcp-publish-figure (slice 1): a new MCP tool `publish_figure(run_id, figures, request_id?, user_confirmed?)` (23 tools now). The person's own LLM client proposes figures with their code and parameters; nothing is written until the person presses 送出 on the confirmation page (or answers yes in the chat), then the figures go to a private gallery of that run (`<figures>/<user id>/<run id>/`, `ABF_PLATFORM_FIGURES`), not into the delivery package. New confirmation kind `publish_figure` that makes no job (`confirm.NO_JOB_KINDS`); the `confirmations.kind` CHECK takes it and an old database is rebuilt once at start. Limits: 10 figures and 5 MiB per call, 30 per run, png/svg/jpg only, SVG with scripts or external links refused. The browser chat does not offer the tool.
- mcp-publish-figure-gallery (slice 2): the finished page of a succeeded run shows the owner's private gallery of figures stored with `publish_figure`: a preview of each (`GET /run/figure`, a picture only, sandboxed), the label 使用者與 LLM 產生, the code and parameters as text, tick boxes that are never pre-ticked, a delete button, and 打包所選的圖. The delivery package holds only what the person packed (the package is the figures ticked at the last press, none allowed); the `Figures` row says 無, 尚未打包 or 已打包. Web only: `POST /run/figures/pack` and `POST /run/figure/delete` need the login cookie, a CSRF token and the same origin, take no token, make no confirmation and no job; no MCP tool is added (23). The finished stage of a succeeded run alone gains `img-src 'self'`; no stylesheet change, no migration. See docs/PLATFORM.md. Review fixes: pack, delete and the confirmed write share one lock of the gallery folder, so none of them loses another's update; a damaged index is shown as such and refused with one sentence; the figure response forbids forms, a base address and framing, and an SVG opened as a document downloads; a failed index write leaves no temporary file; the page inlines only the first 200 lines or 20 KB of code and parameters and offers the full text as a plain-text download (`part=code|params`).
- mcp-chat-confirm: a third way for a person's yes through MCP, the person's own reply in the chat (channel `CHAT`). `launch`, `cancel`, `resume` and `relaunch` take `request_id` and `user_confirmed`: after the first call returns a pending request, the person answers in the chat and the AI calls the same tool again with `request_id` and `user_confirmed=true`; the platform accepts it only for the same user, the same content and kind, and within ten minutes, never over stdio. The browser chat does not offer the two arguments to its model. Constitution 7.0.0 (Principle I.2 and a Safety Net rule: four channels); its Approval: the maintainer agreed to the text on 2026-11-06. No migration needed. See docs/PLATFORM.md, "The confirmation page".
- refusal-visibility: a launch the site refuses for lack of an open connection now carries the site's own login line (`open_command`, kept by `jobs.clean_result` only in the strict shape and only for the environment's own host); the confirmation page and the board show the reason and that line in a `<pre>` and never say 已送出 for a refused or errored job. No new route, button or tool.
- owner-binding (#116 follow-up): **breaking for old deployments.** An agent token made without a user is refused (403) for an agent that has an owner; reissue it with `abf-platform agent-token revoke NAME` then `agent-token new NAME --user U`. `agent-token new` now requires `--user` once the platform has a user, and refuses a name whose agent belongs to someone else. `ce create|update --owner` claims the environment's unowned agent for that owner in the same transaction, and the start-up `assign_orphans` gives an unowned agent to the one owner of all the environments that use it (a data move, no schema change, no migration needed). New guard test `test_owner_guard.py`. No web change. See docs/TESTING.md, "Owner binding follow-up".
- resume-edit-params: `resume` (MCP and `abf-platform resume`) may carry `params` (only the keys to change, laid over those of the first launch) and `extra_config` (resource settings only: `cpus`, `memory`, `time`, `disk`, `maxRetries`, `errorStrategy`; CLI `--param`, `--params-file`, `--config-file`); it stays the same analysis. A composed pipeline and Google Batch still refuse a resume that carries changes; `relaunch` is unchanged (name alone). The opening sentence of the MCP server, the skills operational and runs, ADR 0009 (one amending line) and docs/SEQERA_PARITY.md say so. No migration needed. Not yet tried on NCHC.
- 011b: the running stage page of `GET /` (title with greyed 續跑／重跑, four summary cards, task bar and legend, this run's notices, tabs Tasks / Logs / Run info / Configuration / Metrics through `?tab=`) and the formal notice component (DESIGN.md "Formal notices"), also used in the Now page's 需要注意 card. Read-only; no new route, table or column. Logs, Configuration and Metrics are grey panels until their actions exist.

- 116: **owner binding.** Each caller sees and uses only their own compute environments, agents, runs and upload folder: `owner_user_id` on environments and agents, `user_id` on `launches`; what is another's or nobody's answers "not found". Over HTTP every samplesheet path cell must lie in the caller's own uploads folder; `launch --user NAME` names the account at the terminal; old rows go to the only user, else wait for `ce update --owner`. See docs/PLATFORM.md, "Whose it is".
- 011a: **the web shell, after web design v1 (`DESIGN.md`).** `GET /` on `abf-platform web` is a read-only three-column page: a dark top bar with the two cost lines "SU —" and "雲端 NT$ —" ("—" until 011d), my runs on the left, the "現在" page (running and needs-attention cards) or the five-stage board of one run in the middle, and my runs by stage with counts on the right; `GET /settings` is the settings frame, every section still "之後開放". `?lang=en` shows the board pages in English (default Chinese, no cookie, no script); times are `MM-DD HH:mm` in Asia/Taipei. It reads only through `list_runs` and `get_run` as the logged-in user; the stage is derived, never stored. A login with no `next` now lands on `/`. The page's content-security-policy is stricter (`style-src` is the sha256 of the one stylesheet, no `'unsafe-inline'`). `platform/tests/test_web_parity.py` is the parity check of the "owed parity" row.
- 116b: **owner binding, the gaps.** Over HTTP the path-like values of `params` must lie in the caller's own uploads folder (or under the read roots), a taken run name tells another user nothing (`this run name is taken; choose another`), links no longer lead out (the listing resolves them, the bundle records the real paths and the agent checks them again at job time), and `abf-platform runs assign RUN --user NAME [--force]` gives an old run to a user. See docs/PLATFORM.md, "Closing the gaps of 116".
- 009e: **resume or relaunch a failed or cancelled run.** `abf-platform resume RUN|relaunch RUN` and the MCP tools `resume` and `relaunch` (one argument, the run name): a resume goes on in the same folder with `-resume <session id>` and a new `-name`, a relaunch starts the first launch again in a new folder; both are attempt 2, 3 ... of the same analysis, both ask for a person's yes every time through the existing channels, and only the owner of the run may. `launches` gains `parent_run`, `attempt`, `attempt_kind` (in place, last). The kit asks for the two new tools. Not yet accepted on NCHC. See docs/PLATFORM.md, "Resume and relaunch".
- 009i: **minimal OAuth 2.1 for Claude Desktop's custom connector (#117).** `abf-platform web` is also the authorization server (the SDK's handlers: metadata, `/register`, `/authorize`, `/token`, `/revoke`, plus a consent page that takes the web password, never a token); `mcp --http --public-url` serves the protected-resource metadata and points a 401 at it; an OAuth access token (1 h, refresh 30 days, rotated) gives the same caller as the user's PAT. `abf-platform oauth revoke USER`. No new confirmation channel: the consent click writes no confirmation and `launch`/`cancel` still only make a pending request. Not tried with Claude Desktop itself until 009h (public https). See docs/PLATFORM.md and docs/TESTING.md.
- 009c: **constitution 5.0.0.** A person's yes may come through the terminal, the form of an MCP client, or the new confirmation page (`abf-platform web`, login with a web password set by `abf-platform user passwd` on a real terminal). The MCP server gains `launch` and `cancel`, which only write a pending request and ask the person; nothing is queued without a yes, and the repeated call returns the job that exists. `platform.db` and `tokens.db` are upgraded in place. The terminal commands are unchanged.
