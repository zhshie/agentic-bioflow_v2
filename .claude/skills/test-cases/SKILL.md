# Test cases: the exam the code must pass, written by someone who did not write the code

The constitution (Development Workflow, "Test cases before code", 2.1.0) requires that a
feature's test cases are written by the independent reviewer (`verifier`, CONTRACT mode)
from the spec, the maintainer's own examples and the plan, and that implementation does not
start until the overview says `合約已確認`. These are the rules the reviewer follows.

Why this gate exists: the tests Spec Kit's implement step writes are generated by the
same agent that writes the code. If the author also decides what counts as passing, it
will pick what it can already pass. The maintainer is not a programmer, so he does not
review test cases; his own examples, quoted in the spec, are what they must prove.

## Steps

1. From the repo root, run `.specify/scripts/bash/check-prerequisites.sh --json --paths-only`
   once and read `FEATURE_DIR` and `FEATURE_SPEC`.
2. Read `FEATURE_SPEC` completely, the plan, and `.specify/memory/constitution.md`. If the
   spec still carries `[NEEDS CLARIFICATION` markers, or quotes none of the maintainer's
   examples for a user-visible change, stop and say that goes back to him first.
3. If `FEATURE_DIR/test-case-overview.md` exists and says `合約已確認` or `已核可`, stop:
   confirmed cases change only when the developer-agent reopens the contract (a spec
   change), and then go back to `草稿`.
4. Fill the structure of `.specify/templates/test-case-template.md` for `test-case.md`:
   - one section per User Story, in the spec's order;
   - every acceptance scenario and every FR maps to at least one TC;
   - every one of the maintainer's examples maps to a TC that uses his words as input and
     expected result;
   - every item the spec puts out of scope maps to at least one `不在範圍` TC;
   - add the "憲法與安全網" section only when the feature can touch an invariant or a
     Safety Net rule, and then prove each touched rule with a TC;
   - one expectation per row; 繁體中文; no jargon without a one-line explanation.
5. Fill `.specify/templates/test-case-overview-template.md` for `test-case-overview.md`:
   counts per User Story and type computed from `test-case.md` (count them, do not
   estimate), the coverage checks answered with the missing IDs named, and every doubt
   written as a one-line question.
6. Set the status to `狀態：合約已確認（YYYY-MM-DD，verifier）` only when the plan has no
   blocking finding, every example is covered, and the doubts list holds nothing that
   changes what is checked. Otherwise leave `狀態：草稿` and say what blocks it.
7. When the maintainer himself reviews the cases and approves them in his own words, the
   status may instead read `狀態：已核可（YYYY-MM-DD，maintainer）`, quoting his words under
   "核可紀錄". This is optional, never required.

## Never

- Set `已核可` without his explicit words in the conversation.
- Let the author of the code write or edit the test cases.
- Write test code. Tests are written by the executor, one per TC marked 自動, each naming
  its TC ID in a comment so the acceptance reviewer can find it.
- Invent requirements the spec does not state. A gap in the spec is a doubt (step 5)
  that goes back to the maintainer, not a TC.
