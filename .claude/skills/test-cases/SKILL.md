# Test cases: the maintainer's gate before design

The constitution (Development Workflow, "Test cases before design") requires that a
feature's test cases are written after clarify and approved by the maintainer before
`/speckit-plan` runs. This skill writes them and stops. It never approves them.

Why this gate exists: the tests Spec Kit's implement step writes are generated by the
same agent that writes the code, and nobody reviews them. Test cases written from the
spec and approved by a person are the only review of *what will be checked* that
happens before the checking is written.

## Steps

1. From the repo root, run `.specify/scripts/bash/check-prerequisites.sh --json --paths-only`
   once and read `FEATURE_DIR` and `FEATURE_SPEC`.
2. Read `FEATURE_SPEC` completely and `.specify/memory/constitution.md`. If the spec still
   carries `[NEEDS CLARIFICATION` markers, stop and say `/speckit-clarify` comes first.
3. If `FEATURE_DIR/test-case-overview.md` exists and says `已核可`, stop: approved cases
   change only when the maintainer asks, and then go back to `草稿` (step 7).
4. Copy the structure of `.specify/templates/test-case-template.md` into
   `FEATURE_DIR/test-case.md` and fill it:
   - one section per User Story, in the spec's order;
   - every acceptance scenario and every FR maps to at least one TC;
   - every item the spec puts out of scope maps to at least one `不在範圍` TC;
   - add the "憲法與安全網" section only when the feature can touch an invariant or a
     Safety Net rule, and then prove each touched rule with a TC;
   - one expectation per row; 繁體中文; no jargon without a one-line explanation.
5. Copy `.specify/templates/test-case-overview-template.md` into
   `FEATURE_DIR/test-case-overview.md`: counts per User Story and type computed from
   `test-case.md` (count them, do not estimate), the coverage checks answered with the
   missing IDs named, and every doubt written as a one-line question. Status stays `草稿`.
6. Show the maintainer the overview's table, the coverage checks and the doubts, and
   ask the three questions in "請你判斷的三件事". Then stop. Do not run `/speckit-plan`.
7. When he asks for changes: edit `test-case.md`, keep existing IDs (strike through a
   removed row instead of deleting it), recount the overview, set status back to `草稿`
   if it had changed, and show him the changed rows only.
8. Only when he says in his own words that the cases are approved: set the status line
   to `狀態：已核可（YYYY-MM-DD，maintainer）` and quote his words, with the date and the
   TCs his review changed, under "核可紀錄". Then say `/speckit-plan` may run, and that
   the plan must cite `test-case.md`.

## Never

- Set `已核可` without his explicit words in this conversation.
- Write test code. Tests are written during `/speckit-implement`, one per TC marked 自動,
  each naming its TC ID in a comment so the acceptance reviewer can find it.
- Invent requirements the spec does not state. A gap in the spec is a doubt (step 5)
  or a return to `/speckit-clarify`, not a TC.
